## 2. 어셈블리 구조와 의존 방향

체크리스트 3.1절의 의존 방향을 asmdef로 강제했다.

```
ProjectR.Core       ← SWUtils.Runtime
ProjectR.Data       ← Core
ProjectR.Activity   ← Core, Data
ProjectR.Backrooms  ← Core, Data, Activity
ProjectR.Editor     ← 위 전부 + SWUtils.Editor   (Editor 전용)
ProjectR.Tests.EditMode ← 위 전부                (Editor 전용)
```

`Inventory`, `Streamer`, `Broadcast`, `UI`는 아직 만들지 않았다. 코드가 없는 asmdef는
빈 어셈블리만 늘리므로 해당 Phase에 도달할 때 추가한다. 의존 방향은 3.1절 표를 그대로 따른다.

`Backrooms`와 `Broadcast`는 서로 참조하지 않는다는 규칙은 Broadcast 추가 시점에 asmdef로 강제한다.

## 3. 직접 만들기로 결정한 것과 그 이유

체크리스트 4장은 SWUtils에 있는 기능을 직접 만들었을 경우 이유를 남기라고 요구한다.

### 3.1 난수 — `SWRandom` 대신 `System.Random`

`MazeFactory`는 전역 난수인 `SWRandom` 대신 시드로 만든 `System.Random` 인스턴스를 쓴다.

`SWRandom`은 전역 정적 난수라서, 맵을 만드는 동안 다른 시스템이 난수를 한 번이라도 뽑으면
같은 시드에서도 다른 미로가 나온다. 그러면 절차적 생성 버그를 재현할 수 없다.
시드 재현은 프로토타입 문서가 Phase 1에서 "반드시 만든다"라고 못 박은 두 항목 중 하나다.

### 3.2 타일 풀링 — `SWPool` 미적용

타일은 맵 한 판당 한 번만 만들어지고 탐험이 끝날 때 사라진다. 반복 생성되는 오브젝트가 아니고,
재생성은 로딩 화면으로 가려지는 구간에서만 일어난다. 11회 연속 재생성 측정에서
타일 수(576), 렌더러 수(2850), 라이트맵 장수(2)가 모두 일정하게 유지되어 누수도 없었다.

몬스터, 채팅 항목, 아이템처럼 반복 생성되는 오브젝트는 계획대로 `SWPool`을 쓴다.

### 3.3 프리팹 라이트맵 — 유니티 기본 기능 없음

유니티의 라이트맵은 씬 단위로만 저장된다. 실행 중에 조립하는 맵에는 그대로 쓸 수 없으므로
`BakedLightmapData` + `TileLightmapBaker`를 직접 만들었다. SWUtils에는 해당 기능이 없다.

### 5.1.1 넓은 홀을 뒤늦게 추가한 이유

처음 구현에서는 재귀적 백트래킹 결과를 그대로 썼는데, 시드 50개 · 28,800칸을 세어 보니
사거리가 0.3%뿐이고 사거리끼리 붙은 경우가 맵당 평균 0.0쌍이었다. 즉 **전부 4m 폭 복도**였다.

이러면 체크리스트가 요구하는 "최악 구간(넓은 홀, 시야 개방)" 프레임레이트를 잴 대상 자체가 없다.
성능 판정을 가장 유리한 구간에서 내리게 되므로 판정이 의미를 잃는다.

`MazeRoomCarver`가 생성 직후 직사각형 범위의 벽을 통째로 허물어 홀을 만든다.
홀은 기존 타일 5종으로 그대로 조립된다. 3x3 홀이면 가운데가 사거리, 가장자리가 삼거리,
모서리가 모퉁이 타일이 되므로 프리팹을 새로 만들 필요가 없다.

`MazeStatistics.LargestOpenAreaCellCount`가 **벽이 하나도 없는 2x2 덩어리**에 속한 칸만
트인 칸으로 보고 그 최대 덩어리 크기를 잰다. 삼거리는 통로가 셋이어도 폭이 한 칸이라
시야가 트이지 않으므로 트인 칸으로 세지 않는다. `MazeFactory`가 이 값을 검증 조건에 넣는다.

> 기록해 둘 함정: 처음에는 "통로가 셋 이상인 칸"을 트인 칸으로 정의했는데,
> 삼거리가 전부 걸려서 실제 홀이 없어도 조건을 통과하거나, 반대로 최소치를 올리면
> 재시도만 반복하고 홀은 안 생겼다. 정의를 2x2 덩어리로 바꾸고 나서야 의도대로 동작했다.

### 5.2 프리팹 5종으로 16가지 통로 조합을 덮는 방법

칸의 통로 조합은 열여섯 가지지만, 회전을 쓰면 다섯 종으로 전부 덮인다.

| 타일 | 기준 통로 | 회전 |
|---|---|---|
| Tile_DeadEnd | 북 | 4방향 |
| Tile_Straight | 북·남 | 2방향 |
| Tile_Corner | 북·동 | 4방향 |
| Tile_TJunction | 북·동·서 | 4방향 |
| Tile_Cross | 전부 | 1방향 |

프리팹 수를 줄이면 미리 구워 둘 라이트맵 장수도 함께 줄어든다. 실제로 라이트맵 2장(256x256, 512KB)에
다섯 종이 전부 들어갔다.

### 5.3 조명 굽기 파이프라인

```
[사전 작업]                                   [실행 중]

타일 프리팹 5종                                맵 생성 (1.35ms)
   │                                              │
   ├─ 굽기 전용 씬에 30m 간격으로 배치            ├─ 칸마다 통로 조합 → 타일 + 회전
   ├─ Lightmapping.Bake (약 5초)                  ├─ 24타일씩 프레임 분할 배치
   └─ 렌더러별 라이트맵 인덱스·영역을              └─ BakedLightmapData.Awake가
      BakedLightmapData에 저장                       라이트맵을 전역 목록에 등록하고
                                                     렌더러 인덱스를 이어 붙임
```

메뉴: `SWTools > 프로젝트R > 타일 조명 > 1. 굽기 씬 만들기` → Unity 라이팅 굽기 →
`2. 구운 결과를 프리팹에 저장`

**작업하면서 걸린 함정 세 가지를 기록해 둔다. 타일을 새로 만들 때 같은 실수를 반복하기 쉽다.**

1. **형광등 덮개가 면광원을 가린다.** 튜브 메시가 면광원 바로 앞에 있으면 굽기에 빛이 전혀
   들어오지 않는다. 튜브의 그림자 캐스팅을 끄고 광원을 튜브 아래로 내렸다.
2. **튜브의 발광 재질이 천장만 태운다.** 튜브가 천장에서 0.2m 거리라 GI에 넣으면 천장만 하얗게
   날아간다. 재질의 GI 플래그를 `EmissiveIsBlack`으로 두고 보이기용 발광으로만 쓴다.
3. **배치 씬의 라이트맵 방식이 굽기 씬과 다르면 화면이 탄다.** 굽기 씬은 NonDirectional인데
   배치 씬 기본값은 Directional이라, 셰이더가 방향 정보 없는 값을 방향 정보로 해석해
   천장이 새하얗게 나왔다. `BakedLightmapData.Apply`가 라이트맵 방식을 함께 맞춘다.

또 하나. 타일의 벽은 셀 안쪽으로 완전히 넣어야 한다. 벽을 셀 경계에 걸치면 이웃 타일의 벽과
정확히 겹쳐서, 안쪽 면이 아니라 빛이 닿지 않은 바깥 면이 보인다. 벽이 새까맣게 나오면 이 문제다.

### 5.3.1 조도 설정 — 공포 게임 톤

첫 굽기 결과가 지나치게 밝아 대비가 없었다. 원인은 광량이 아니라 **재질 반사율**이었다.
벽 알베도가 0.85로 거의 흰 종이 수준이라 빛이 벽에서 벽으로 계속 튀면서 구석까지 다 채웠다.
이 상태에서 광량만 낮추면 전체가 고르게 어두워질 뿐 대비는 생기지 않는다.

최종적으로 "공간은 거의 검고 천장 형광등만 보이는" 공포 게임 톤으로 맞췄다.

| 손잡이 | 최초 | 밝은 백룸 | 현재(공포 톤) | 리베이크 |
|---|---|---|---|---|
| 벽 알베도 | 0.851, 0.808, 0.549 | 0.46, 0.43, 0.29 | **0.20, 0.185, 0.125** | 필요 |
| 바닥 알베도 | 0.741, 0.694, 0.451 | 0.30, 0.28, 0.19 | **0.12, 0.112, 0.076** | 필요 |
| 천장 알베도 | 0.909, 0.886, 0.776 | 0.50, 0.48, 0.42 | **0.24, 0.23, 0.20** | 필요 |
| 면광원 세기 | 80 | 22 | **18** | 필요 |
| 면광원 range | 9 | 9 | **6** | 필요 |
| indirectScale | 2.0 | 1.0 | **0.25** | 필요 |
| maxBounces | 4 | 4 | **2** | 필요 |
| 환경광 | 0.02 | 0.02 | **완전 검정** | 필요 |
| 형광등 재질 | Lit + 발광 | Lit + 발광 | **Unlit HDR ×3.5** | 불필요 |
| 포스트프로세싱 | 없음 | (적용 안 됨) | **Neutral 톤매핑 / 블룸 / 대비 +8 / 채도 -12 / 비네트 0.45** | 불필요 |
| 안개 | 없음 | 없음 | **검정 ExponentialSquared 0.035** | 불필요 |

역할 정리:

- **어둠**은 알베도와 `indirectScale`에서 나온다. 광량을 내리는 게 아니다.
- **천장 빛의 존재감**은 형광등 재질(Unlit HDR)과 **블룸**에서 나온다.
- **깊이**는 검은 안개가 만든다. 멀리 있는 형광등이 어둠에 삼켜지면서 거리가 읽힌다.
- **미세 조정**은 `Assets/02_Res/Backrooms/BackroomsVolumeProfile.asset`의 Post Exposure로 한다.
  리베이크가 필요 없다.

**여기서도 함정 두 개를 밟았다. 둘 다 조용히 실패해서 알아채기 어렵다.**

4. **`VolumeProfile.Add<T>()`만으로는 저장되지 않는다.** 메모리에만 올라가고 에셋에는 안 붙어서,
   에디터를 다시 로드하면 프로파일이 텅 비어 있다. 화면에는 아무 변화가 없는데 코드는 성공을 반환한다.
   반드시 `AssetDatabase.AddObjectToAsset(component, profile)`으로 서브에셋으로 붙여야 한다.
   확인법: 다시 불러온 프로파일의 `components.Count`를 찍어 본다.
5. **`MaterialGlobalIlluminationFlags.EmissiveIsBlack`은 발광 렌더링까지 끈다.** 이 값은 "발광이
   검다"는 선언이라 유니티가 `_EMISSION` 키워드를 꺼 버린다. GI에서만 빼고 화면에는 그리려면
   `None`을 써야 한다. 다만 URP에서는 셰이더가 재질을 검증할 때 키워드가 다시 꺼지는 경우가 있어,
   형광등처럼 음영이 필요 없는 물체는 **Unlit 셰이더에 HDR 색**을 주는 편이 확실하다.

> 참고: 3번 함정("튜브의 발광이 천장을 태운다")은 최초 설정인 `BakedEmissive`에서 일어난 일이다.
> 이를 `EmissiveIsBlack`으로 막았더니 5번 함정으로 이어져 발광이 아예 안 보이게 됐다.
> 최종 해법은 Unlit이다.

### 5.5 라이트 프로브 이음새 보정 — 설계 변경

체크리스트에 "이음새 라이트 프로브 보정" 항목이 있으나, 구현하지 않고 대체안을 택했다.
**이유를 남겨 두고 판단을 넘긴다.**

- 라이트 프로브는 정적 지오메트리가 아니라 **동적 오브젝트**에 적용되는 기능이다.
  타일 사이 이음새의 밝기 차이는 프로브로 메울 수 없다.
- 프로브 위치와 SH 값은 씬 단위로 구워지고, 프로브 배치는 실행 중에 다시 만들 수 없다
  (tetrahedralization이 굽기 시점에 확정된다). 실행 중 조립하는 맵에는 원리상 쓸 수 없다.
- 실제로 렌더해 본 결과, 타일마다 같은 조명이 반복되는 균일한 인상이 백룸 분위기와 오히려 맞는다.
  이음새는 밝기 단차로만 보이고 거슬리는 수준이 아니다.

**대체안**: 배치 씬의 환경광을 아주 낮은 값(0.02)으로 고정해 동적 오브젝트(플레이어, 몬스터)가
완전히 검게 보이지 않도록 했다. Phase 2에서 손전등이 들어가면 동적 오브젝트 조명은 손전등이 맡는다.

이음새가 실제로 거슬린다는 판단이 나오면 대응 순서는 다음과 같다.
① 타일 경계에 어두운 걸레받이·문틀을 넣어 단차를 숨긴다 → ② 라이트맵 해상도를 올린다 →
③ Adaptive Probe Volume을 층 단위로 미리 구워 두는 방식을 검토한다.

### 5.6 판정

| 단계 | 검증 질문 | 측정 및 관찰 결과 | 판정 | 조치 |

**아직 정식 판정이 아니다.** 개발 PC가 목표 사양보다 훨씬 빠르고, 에디터는 빌드보다 느리지만
프로파일링 부하가 섞여 있어 그대로 환산할 수 없다.

정식 판정에 필요한 작업:

```
□ Windows 64비트 빌드 생성
□ GTX 1650급 실기에서 1080p 실행
□ 최악 구간(넓은 홀, 시야 개방) 프레임레이트 측정
□ 장시간(30분 이상) 플레이 시 메모리 증가 확인
```

다만 GPU 프레임 시간 0.56ms는 목표 사양 GPU가 10배 느리다고 가정해도 5.6ms(약 178fps)이므로,
현재 구조로 60fps를 못 맞출 가능성은 낮다고 본다. 생성 방식 전환(WFC / BSP) 준비는 보류한다.

**Phase 2 진행 전에 위 네 항목을 채워 이 표를 확정할 것.**
