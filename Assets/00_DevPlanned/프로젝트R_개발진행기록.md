## 2. 어셈블리 구조와 의존 방향

체크리스트 3.1절의 의존 방향을 asmdef로 강제했다.

```
ProjectR.Inventory  ← (없음)                     noEngineReferences
ProjectR.Core       ← SWUtils.Runtime
ProjectR.Data       ← Core, Inventory
ProjectR.Activity   ← Core, Data
ProjectR.Backrooms  ← Core, Data, Inventory, Activity, Unity.InputSystem, Unity.AI.Navigation, URP
ProjectR.UI         ← Core, Data, Inventory, Activity, Backrooms, Unity.InputSystem, UnityEngine.UI
ProjectR.Editor     ← 위 전부 + SWUtils.Editor   (Editor 전용)
ProjectR.Tests.EditMode ← 위 전부                (Editor 전용)
```

`Unity.InputSystem` 참조는 Phase 2에서 1인칭 조작을 넣으며 추가했다. SWUtils에는 입력 유틸이 없다.
`Unity.AI.Navigation` 참조는 Phase 3에서 실행 중 NavMesh를 구우며 추가했다(9.1절).
몬스터 코드도 백룸 전용이라 `Backrooms` 안의 `Monster` 폴더에 두었다.
1인칭 플레이어 코드는 백룸 전용이라 `Backrooms` 안의 `Player` 폴더에 두었다.
다른 활동에서 같은 조작을 쓰게 되면 그때 분리한다.

`ProjectR.UI`는 ESC 옵션 팝업을 만들며 2026.08.27에 생겼다(8.9절 4번).
UI가 아래를 전부 참조하고 아무도 UI를 참조하지 않는다는 방향을 asmdef로 강제한다.
그래서 백룸 쪽이 옵션 값을 알아야 하는 경우에는 UI를 참조하지 않고
`Core`의 `GameSettings`와 `SWEventBus`를 거친다.

URP 참조는 미로 확인 도구가 후처리 노출을 올리며 추가했다(11.5절).

`ProjectR.Inventory`는 Phase 4에서 2026.08.28에 생겼다(10.2절).
격자 계산부만 들어 있고 `noEngineReferences: true`라 유니티도 SWUtils도 참조하지 않는다.
어느 쪽도 참조하지 않아야 계산부와 유니티의 분리가 규칙이 아니라 컴파일 오류로 지켜진다.

`Streamer`, `Broadcast`는 아직 만들지 않았다. 코드가 없는 asmdef는
빈 어셈블리만 늘리므로 해당 Phase에 도달할 때 추가한다. 의존 방향은 3.1절 표를 그대로 따른다.

`Backrooms`와 `Broadcast`는 서로 참조하지 않는다는 규칙은 Broadcast 추가 시점에 asmdef로 강제한다.

## 3. 직접 만들기로 결정한 것과 그 이유

체크리스트 4장은 SWUtils에 있는 기능을 직접 만들었을 경우 이유를 남기라고 요구한다.

### 3.1 난수 — `SWRandom` 대신 `System.Random`

`MazeFactory`는 전역 난수인 `SWRandom` 대신 시드로 만든 `System.Random` 인스턴스를 쓴다.

`SWRandom`은 전역 정적 난수라서, 맵을 만드는 동안 다른 시스템이 난수를 한 번이라도 뽑으면
같은 시드에서도 다른 미로가 나온다. 그러면 절차적 생성 버그를 재현할 수 없다.
시드 재현은 프로토타입 문서가 Phase 1에서 "반드시 만든다"라고 못 박은 두 항목 중 하나다.

### 3.2 타일 풀링 — `SWPool` 미적용

타일은 맵 한 판당 한 번만 만들어지고 탐험이 끝날 때 사라진다. 반복 생성되는 오브젝트가 아니고,
재생성은 로딩 화면으로 가려지는 구간에서만 일어난다. 11회 연속 재생성 측정에서
타일 수(576), 렌더러 수(2850), 라이트맵 장수(2)가 모두 일정하게 유지되어 누수도 없었다.

몬스터, 채팅 항목, 아이템처럼 반복 생성되는 오브젝트는 계획대로 `SWPool`을 쓴다.

### 3.3 프리팹 라이트맵 — 유니티 기본 기능 없음

유니티의 라이트맵은 씬 단위로만 저장된다. 실행 중에 조립하는 맵에는 그대로 쓸 수 없으므로
`BakedLightmapData` + `TileLightmapBaker`를 직접 만들었다. SWUtils에는 해당 기능이 없다.

### 3.4 SWUtils 원본 수정 — 예외 한 건

체크리스트 2장은 SWUtils 원본을 고치지 말고 감싸서 쓰라고 요구한다. 여기에 예외를 한 번 두었다.
**SWUtils v1.1.0은 플레이어 빌드에서 컴파일되지 않는다.** 감싸는 것으로는 해결할 수 없는 종류의 문제라
원본을 고쳤다. 상세와 조치는 5.7절에 적었다.

### 5.1.1 넓은 홀을 뒤늦게 추가한 이유

처음 구현에서는 재귀적 백트래킹 결과를 그대로 썼는데, 시드 50개 · 28,800칸을 세어 보니
사거리가 0.3%뿐이고 사거리끼리 붙은 경우가 맵당 평균 0.0쌍이었다. 즉 **전부 4m 폭 복도**였다.

이러면 체크리스트가 요구하는 "최악 구간(넓은 홀, 시야 개방)" 프레임레이트를 잴 대상 자체가 없다.
성능 판정을 가장 유리한 구간에서 내리게 되므로 판정이 의미를 잃는다.

`MazeRoomCarver`가 생성 직후 직사각형 범위의 벽을 통째로 허물어 홀을 만든다.
홀은 기존 타일 5종으로 그대로 조립된다. 3x3 홀이면 가운데가 사거리, 가장자리가 삼거리,
모서리가 모퉁이 타일이 되므로 프리팹을 새로 만들 필요가 없다.

`MazeStatistics.LargestOpenAreaCellCount`가 **벽이 하나도 없는 2x2 덩어리**에 속한 칸만
트인 칸으로 보고 그 최대 덩어리 크기를 잰다. 삼거리는 통로가 셋이어도 폭이 한 칸이라
시야가 트이지 않으므로 트인 칸으로 세지 않는다. `MazeFactory`가 이 값을 검증 조건에 넣는다.

> 기록해 둘 함정: 처음에는 "통로가 셋 이상인 칸"을 트인 칸으로 정의했는데,
> 삼거리가 전부 걸려서 실제 홀이 없어도 조건을 통과하거나, 반대로 최소치를 올리면
> 재시도만 반복하고 홀은 안 생겼다. 정의를 2x2 덩어리로 바꾸고 나서야 의도대로 동작했다.

### 5.2 프리팹 5종으로 16가지 통로 조합을 덮는 방법

칸의 통로 조합은 열여섯 가지지만, 회전을 쓰면 다섯 종으로 전부 덮인다.

| 타일 | 기준 통로 | 회전 |
|---|---|---|
| Tile_DeadEnd | 북 | 4방향 |
| Tile_Straight | 북·남 | 2방향 |
| Tile_Corner | 북·동 | 4방향 |
| Tile_TJunction | 북·동·서 | 4방향 |
| Tile_Cross | 전부 | 1방향 |

프리팹 수를 줄이면 미리 구워 둘 라이트맵 장수도 함께 줄어든다. 실제로 라이트맵 2장(256x256, 512KB)에
다섯 종이 전부 들어갔다.

### 5.3 조명 굽기 파이프라인

```
[사전 작업]                                   [실행 중]

타일 프리팹 5종                                맵 생성 (1.35ms)
   │                                              │
   ├─ 굽기 전용 씬에 30m 간격으로 배치            ├─ 칸마다 통로 조합 → 타일 + 회전
   ├─ Lightmapping.Bake (약 5초)                  ├─ 24타일씩 프레임 분할 배치
   └─ 렌더러별 라이트맵 인덱스·영역을              └─ BakedLightmapData.Awake가
      BakedLightmapData에 저장                       라이트맵을 전역 목록에 등록하고
                                                     렌더러 인덱스를 이어 붙임
```

메뉴는 `Project R > 타일 조명 조절` 하나뿐이다. 굽기 관련 기능은 전부 이 창 안에 있다.
메뉴에 개별 명령을 늘어놓지 않는 이유는, 순서를 잘못 눌러 구워 둔 결과를 날리기 쉬워서다.

| 창 안의 버튼 | 용도 |
|---|---|
| 프리팹에서 현재 값 다시 읽기 | 창의 값을 프리팹 실제 값으로 되돌린다 |
| 적용만 하기 | 값만 프리팹·재질에 쓴다 (굽지 않음) |
| **적용하고 굽기까지** | 값 적용 + 굽기 + 프리팹 저장. 타일 5종 기준 약 3.4초 |
| 굽기 씬 도구 > 굽기 씬 열기 | 있으면 열고, 없으면 만든다 |
| 굽기 씬 도구 > 굽기 씬 다시 만들기 | 타일 구성이 바뀐 경우에만. 확인 대화상자를 거친다 |
| 굽기 씬 도구 > 구운 결과만 프리팹에 저장 | Auto Generate로 구운 뒤 결과만 옮긴다 |

**작업하면서 걸린 함정 세 가지를 기록해 둔다. 타일을 새로 만들 때 같은 실수를 반복하기 쉽다.**

1. **형광등 덮개가 면광원을 가린다.** 튜브 메시가 면광원 바로 앞에 있으면 굽기에 빛이 전혀
   들어오지 않는다. 튜브의 그림자 캐스팅을 끄고 광원을 튜브 아래로 내렸다.
2. **튜브의 발광 재질이 천장만 태운다.** 튜브가 천장에서 0.2m 거리라 GI에 넣으면 천장만 하얗게
   날아간다. 처음에는 GI 플래그를 `EmissiveIsBlack`으로 막았는데, 그게 5.3.1절의 5번 함정으로
   이어졌다. **최종 해법은 형광등 재질을 Unlit으로 바꾸는 것이다.**
3. **배치 씬의 라이트맵 방식이 굽기 씬과 다르면 화면이 탄다.** 굽기 씬은 NonDirectional인데
   배치 씬 기본값은 Directional이라, 셰이더가 방향 정보 없는 값을 방향 정보로 해석해
   천장이 새하얗게 나왔다. `BakedLightmapData.Apply`가 라이트맵 방식을 함께 맞춘다.

또 하나. 타일의 벽은 셀 안쪽으로 완전히 넣어야 한다. 벽을 셀 경계에 걸치면 이웃 타일의 벽과
정확히 겹쳐서, 안쪽 면이 아니라 빛이 닿지 않은 바깥 면이 보인다. 벽이 새까맣게 나오면 이 문제다.

### 5.3.1 조도 설정 — 공포 게임 톤

첫 굽기 결과가 지나치게 밝아 대비가 없었다. 원인은 광량이 아니라 **재질 반사율**이었다.
벽 알베도가 0.85로 거의 흰 종이 수준이라 빛이 벽에서 벽으로 계속 튀면서 구석까지 다 채웠다.
이 상태에서 광량만 낮추면 전체가 고르게 어두워질 뿐 대비는 생기지 않는다.

최종적으로 "공간은 거의 검고 천장 형광등만 보이는" 공포 게임 톤으로 맞췄다.

| 손잡이 | 최초 | 밝은 백룸 | 현재(공포 톤) | 리베이크 |
|---|---|---|---|---|
| 벽 알베도 | 0.851, 0.808, 0.549 | 0.46, 0.43, 0.29 | **0.20, 0.185, 0.125** | 필요 |
| 바닥 알베도 | 0.741, 0.694, 0.451 | 0.30, 0.28, 0.19 | **0.12, 0.112, 0.076** | 필요 |
| 천장 알베도 | 0.909, 0.886, 0.776 | 0.50, 0.48, 0.42 | **0.24, 0.23, 0.20** | 필요 |
| 면광원 세기 | 80 | 22 | **18** | 필요 |
| 면광원 range | 9 | 9 | **6** | 필요 |
| indirectScale | 2.0 | 1.0 | **0.25** | 필요 |
| maxBounces | 4 | 4 | **2** | 필요 |
| 환경광 | 0.02 | 0.02 | **완전 검정** | 필요 |
| 형광등 재질 | Lit + 발광 | Lit + 발광 | **Unlit HDR ×3.5** | 불필요 |
| 포스트프로세싱 | 없음 | (적용 안 됨) | **Neutral 톤매핑 / 블룸 0.55 / 노출 -2 / 대비 +8 / 채도 -12 / 비네트 0.45** | 불필요 |
| 안개 | 없음 | 없음 | **검정 ExponentialSquared 0.035** | 불필요 |

역할 정리:

- **어둠**은 알베도와 `indirectScale`에서 나온다. 광량을 내리는 게 아니다.
- **천장 빛의 존재감**은 형광등 재질(Unlit HDR)과 **블룸**에서 나온다.
- **깊이**는 검은 안개가 만든다. 멀리 있는 형광등이 어둠에 삼켜지면서 거리가 읽힌다.
- **미세 조정**은 `Assets/02_Res/Backrooms/BackroomsVolumeProfile.asset`의 Post Exposure로 한다.
  리베이크가 필요 없다.

현재 값은 2026.08.26 기준 프로젝트에서 읽은 실제 값이다. 이 중 Post Exposure(-2)와
Bloom Intensity(0.55)는 손으로 맞춘 값이다. 굽기 값을 바꿔 리베이크하면 이 둘도 다시 봐야 한다.

> 주의: 이 조도는 **손전등이 있어야 성립한다.** 형광등 사이 구간은 사실상 보이지 않는다.
> Phase 2 전에 맵을 눈으로 확인할 일이 있으면 Post Exposure를 올려서 본다.

### 5.3.2 조명 값을 보면서 고치는 방법

타일 프리팹의 Light는 **Baked 전용**이라 인스펙터에서 광량을 바꿔도 화면이 바뀌지 않는다.
실행 중 화면은 전적으로 프리팹에 저장해 둔 라이트맵이 만든다. 다시 굽고 프리팹에 저장해야
비로소 반영된다. 이 사실을 모르면 값을 아무리 만져도 변화가 없어 한참 헤매게 된다.

또 형광등이 타일마다 따로 들어 있어 손으로 고치면 다섯 곳을 모두 맞춰야 한다.

권장 작업 흐름:

```
[값을 크게 잡을 때 — 반복이 빠름]
Project R > 타일 조명 조절 > 굽기 씬 도구 > 굽기 씬 열기
  → Lighting 창의 Auto Generate를 켠다
  → 값을 바꿀 때마다 자동으로 다시 구워져 씬 뷰에서 바로 보인다
  → 마음에 들면 "구운 결과만 프리팹에 저장" 을 누른다

[값을 다듬을 때 — 다섯 종을 한 번에]
Project R > 타일 조명 조절
  → 광량 / 도달 범위 / 빛 색 / 벽·바닥·천장 반사율 / 형광등 밝기를 고친다
  → "적용하고 굽기까지" 를 누른다 (약 3.4초)

[리베이크가 필요 없는 것]
형광등 밝기(Unlit 재질 색), 포스트프로세싱, 안개
  → 값을 바꾸면 즉시 반영된다
```

조절 창은 값을 따로 저장하지 않는다. 원본은 어디까지나 프리팹과 재질이고,
창은 그것을 읽어 보여 주고 다시 쓰기만 한다. 두 벌의 설정이 어긋날 일이 없다.

**여기서도 함정 두 개를 밟았다. 둘 다 조용히 실패해서 알아채기 어렵다.**

4. **`VolumeProfile.Add<T>()`만으로는 저장되지 않는다.** 메모리에만 올라가고 에셋에는 안 붙어서,
   에디터를 다시 로드하면 프로파일이 텅 비어 있다. 화면에는 아무 변화가 없는데 코드는 성공을 반환한다.
   반드시 `AssetDatabase.AddObjectToAsset(component, profile)`으로 서브에셋으로 붙여야 한다.
   확인법: 다시 불러온 프로파일의 `components.Count`를 찍어 본다.
5. **`MaterialGlobalIlluminationFlags.EmissiveIsBlack`은 발광 렌더링까지 끈다.** 이 값은 "발광이
   검다"는 선언이라 유니티가 `_EMISSION` 키워드를 꺼 버린다. GI에서만 빼고 화면에는 그리려면
   `None`을 써야 한다. 다만 URP에서는 셰이더가 재질을 검증할 때 키워드가 다시 꺼지는 경우가 있어,
   형광등처럼 음영이 필요 없는 물체는 **Unlit 셰이더에 HDR 색**을 주는 편이 확실하다.

> 참고: 3번 함정("튜브의 발광이 천장을 태운다")은 최초 설정인 `BakedEmissive`에서 일어난 일이다.
> 이를 `EmissiveIsBlack`으로 막았더니 5번 함정으로 이어져 발광이 아예 안 보이게 됐다.
> 최종 해법은 Unlit이다.

### 5.5 라이트 프로브 이음새 보정 — 설계 변경

체크리스트에 "이음새 라이트 프로브 보정" 항목이 있으나, 구현하지 않고 대체안을 택했다.
**이유를 남겨 두고 판단을 넘긴다.**

- 라이트 프로브는 정적 지오메트리가 아니라 **동적 오브젝트**에 적용되는 기능이다.
  타일 사이 이음새의 밝기 차이는 프로브로 메울 수 없다.
- 프로브 위치와 SH 값은 씬 단위로 구워지고, 프로브 배치는 실행 중에 다시 만들 수 없다
  (tetrahedralization이 굽기 시점에 확정된다). 실행 중 조립하는 맵에는 원리상 쓸 수 없다.
- 실제로 렌더해 본 결과, 타일마다 같은 조명이 반복되는 균일한 인상이 백룸 분위기와 오히려 맞는다.
  이음새는 밝기 단차로만 보이고 거슬리는 수준이 아니다.

**대체안**: 배치 씬의 환경광을 아주 낮은 값(0.02)으로 고정해 동적 오브젝트(플레이어, 몬스터)가
완전히 검게 보이지 않도록 했다. Phase 2에서 손전등이 들어가면 동적 오브젝트 조명은 손전등이 맡는다.

이음새가 실제로 거슬린다는 판단이 나오면 대응 순서는 다음과 같다.
① 타일 경계에 어두운 걸레받이·문틀을 넣어 단차를 숨긴다 → ② 라이트맵 해상도를 올린다 →
③ Adaptive Probe Volume을 층 단위로 미리 구워 두는 방식을 검토한다.

**1번은 단순한 절차가 아니라 이 방식의 마지막 미검증 지점이었다.** 프리팹에 구워 넣은 라이트맵은
씬에 속하지 않은 텍스처라서, 빌드에서 참조가 끊기거나 스트립되면 실기에서 맵이 새까맣게 나온다.
확인 결과 **참조는 살아남았다.** 라이트맵 텍스처를 Resources나 Addressables로 따로 물릴 필요는 없다.

**2번의 대상은 넓은 홀이 아니라 긴 복도다.** 5.4절에서 측정해 보니 홀이 복도보다 가벼웠다.
체크리스트가 상정한 "최악 구간 = 넓은 홀"과 반대이므로, 실기 측정도 복도에서 해야 한다.
빌드는 `Builds/Win64/ProjectR.exe`에 있고, SWDebugConsole의 성능 오버레이가 FPS와 최소/최대,
메모리를 함께 보여 준다. 실기에 옮겨 켜고 복도를 걸으면 그대로 측정치가 된다.

**3번에서 진짜 누수가 나왔다.** 원래 걱정하던 라이트맵 재등록은 문제가 없었고, 전혀 다른 곳
— 정적 배칭이 만들어 내는 합친 메시 — 이 재생성마다 쌓이고 있었다. 상세는 5.8절에 적었다.
측정하지 않았으면 그대로 넘어갔을 항목이다.

참고로 복도 기준 GPU 0.80ms는 목표 사양 GPU가 5배 느리다고 가정해도 4ms(약 250fps)다.
현재 구조로 60fps를 못 맞출 가능성은 낮다고 본다. 생성 방식 전환(WFC / BSP) 준비는 보류한다.

**Phase 2 진행 전에 2번을 채워 이 표를 확정할 것.**

### 5.7 빌드 검증 — Windows 64비트

Phase 1 판정 1번이다. 에디터 플레이 모드로는 확인할 수 없는 지점이라 빌드해서 직접 실행했다.

#### 빌드 구성

| 항목 | 값 |
|---|---|
| 대상 | StandaloneWindows64 · Mono · 릴리스(개발 빌드 아님) |
| 씬 | HomeScene / LoadingScene / BackroomsScene |
| 출력 | `Builds/Win64/ProjectR.exe` (`.gitignore`에 `/Builds/` 추가) |
| 스크립트 심볼 | `SW_DEBUG_MODE` (Standalone) — 빌드에서도 로그와 디버그 콘솔이 살아 있다 |

#### 첫 빌드는 실패했다 — 원인은 프로젝트 코드가 아니라 SWUtils

**SWUtils v1.1.0은 플레이어 빌드에서 컴파일되지 않는다.** 에디터에서만 존재하는 API를 런타임
코드가 가드 없이 쓰고 있어서다. 에디터에서는 두 API가 모두 존재하므로 여태 드러나지 않았다.
빌드를 한 번도 하지 않았기 때문이다.

| 파일 | 오류 | 원인 |
|---|---|---|
| `Runtime/Util/SWVibration.cs` | CS0103 `Handheld` (4곳) | `Handheld`는 모바일 전용인데 `#else` 가지에 있어 스탠드얼론에도 컴파일된다 |
| `Runtime/Base/SWIODatabase.cs` | CS0103 `MarkDirty` (5곳) | `MarkDirty`가 `#if UNITY_EDITOR` 안에 정의되어 있는데 런타임 메서드가 호출한다 |

고친 방법은 최소한으로 잡았다.

- `Handheld.Vibrate()` 호출부의 `#else`를 `#elif UNITY_IOS || UNITY_EDITOR`로 바꿨다.
  PC 빌드에서는 진동이 아무 일도 하지 않는 것이 맞는 동작이다.
- `MarkDirty`를 `#if UNITY_EDITOR` 블록 밖으로 빼고 본문만 가드했다. 호출부 다섯 곳은 그대로 둔다.

> **조치 현황 (2026.08.27 마무리)**: `v1.1.1` 태그가 올라갔고 `manifest.json`도 `#v1.1.1`로 바꿨다.
> 두 수정이 패키지에 들어 있는 것을 확인했다 —
> `SWVibration`은 `#elif UNITY_IOS || UNITY_EDITOR`로 막혔고,
> `SWIODatabase`의 `MarkDirty`는 `#if UNITY_EDITOR` 블록 밖으로 나와 본문만 가드되어 있다.
>
> **이 위험은 실제로 한 번 재발했다.** 태그를 고치기 전 어느 시점에 패키지가 다시 받아지면서
> PackageCache가 수정 이전 `v1.1.0`으로 되돌아갔고, 그 상태로는 플레이어 빌드가 컴파일되지 않았다.
> 에디터에서는 멀쩡히 돌아가므로 **빌드를 시도하기 전까지 드러나지 않는다.**
> 앞으로도 SWUtils를 고치면 태그를 올리고 `manifest.json`을 함께 바꾸는 데까지가 한 작업이다.

#### 확인 방법 — 눈으로 보지 않고 자동으로

빌드한 실행 파일을 명령줄 인자로 자동 확인하도록 `BackroomsBuildVerifier`를 만들었다.
인자가 없으면 아무 일도 하지 않으므로 평소 실행에는 영향을 주지 않는다.

```
ProjectR.exe -projectr-verify
             -projectr-screenshot <경로>   화면을 찍어 저장 (선택)
             -projectr-soak <횟수>         이어서 재생성 메모리 측정 (선택)
```

절차는 백룸 진입 → 조립 완료 대기 → 카메라를 시작 칸에 놓고 열린 통로 쪽으로 돌림 →
라이트맵 상태 기록 → 화면 캡처 → 종료 코드 반환이다.
종료 코드는 0이 정상, 1이 라이트맵 실패, 2가 절차 실패다. 사람이 화면을 보고 판단하지 않아도 된다.

#### 결과 — 통과

### 5.8 장시간 메모리 — 누수 1건 발견 및 수정

Phase 1 판정 3번이다. 사람이 30분을 걸어 다니는 대신 맵 재생성을 연달아 돌려 같은 위험을
훨씬 빠르게 드러내는 방식을 택했다. `map.soak <횟수>` 명령과 `BackroomsSoakRunner`가 그 도구다.
재생성 500회는 0.6분이면 끝나고, 30분 플레이보다 가혹한 조건이다.

#### 측정 결과

| 항목 | 수정 전 (500회) | 수정 후 (500회) |
|---|---|---|
| 총 할당 | 117.6MB → 363.8MB | 119.3MB → 127.9MB |
| 정리(UnloadUnusedAssets) 후 | — | 122.9MB |
| 순증가 | **+246.2MB** | **+3.6MB** |
| 1회당 증가 | 약 0.49MB | 약 7KB |

| 관리 메모리 | +0.6MB | +0.4MB |

수정 전 증가는 평탄해지지 않고 **선형으로 계속 늘었다.** 할당자 여유분이 아니라 진짜 누수다.

#### 원인 — 정적 배칭이 만드는 합친 메시

`StaticBatchingUtility.Combine`은 실행 중에 타일 메시를 하나로 합친 **새 메시를 만들어 낸다.**
이 메시는 씬에 속한 에셋이 아니라 실행 중에 생긴 오브젝트이므로, 타일 게임오브젝트를 `Destroy`해도
같이 사라지지 않는다. 재생성할 때마다 한 장씩 쌓여 1회당 0.49MB씩 늘어난 것이다.

원래 이 방식에서 위험하다고 적어 둔 지점(라이트맵 재등록)은 수정 전후 모두 2장 고정이었다.
**걱정한 곳이 아니라 걱정하지 않은 곳에서 났다.** 측정하지 않았으면 그대로 넘어갔을 항목이다.

#### 수정

`BackroomsMapBuilder`가 합친 메시 참조를 들고 있다가 다음 조립 직전에 지운다.
프리팹 원본 메시를 잘못 지우면 두 번째 맵부터 통째로 사라지므로, 합치기 **전후의 메시가 실제로
바뀌었을 때만** 실행 중에 만들어진 메시로 본다. 바뀌지 않았으면 아무것도 지우지 않는다.

안전 확인: 에디터에서 30회 재생성한 뒤 메시필터 2,738개 중 빈 메시가 0개였고 화면도 정상이었다.
원본 에셋은 건드리지 않는다.

#### 남은 것

30분 연속 "플레이"는 아직 이동 수단이 없어 잴 수 없다. 걸어 다니는 동안에만 생기는 증가
(오디오, 몬스터, 아이템 등)는 그 시스템이 생기는 Phase 2와 Phase 3에서 다시 잰다.
지금 시점에서 잴 수 있는 위험은 재생성이었고, 그건 500회로 확인했다.

### 8.2 손전등은 실시간 라이트 규칙의 예외다

체크리스트 7장은 "실행 중 실시간 라이트를 추가하지 않았는가"를 묻는다. 손전등은 그 예외다.
맵 조명은 전부 구워 두었고, 실행 중에 켜지는 실시간 라이트는 **손전등 하나뿐**이다.
앞으로도 이 개수를 늘리지 않는다. 몬스터가 빛을 낼 일이 생기면 발광 재질로 처리한다.

### 8.3 조도 함정 — 광량 단위가 칸델라다

**처음에 손전등을 켜도 화면이 전혀 바뀌지 않았다.** 라이트는 켜져 있고 방향도 맞는데 아무것도
비추지 않았다. 원인은 프로젝트가 물리 광량 단위를 쓰고 있어서 `Light.intensity`가 **칸델라**라는 것이었다.
처음에 넣은 3.2는 사실상 0이다. 200까지 올려도 화면 평균 밝기가 0.0466에서 0.0490으로 움직였을 뿐이다.

| 광량(cd) | 화면 평균 밝기 | 판단 |
|---|---|---|
| 끔 | 0.0466 | 기준 |
| 200 | 0.0490 | 없는 것과 같음 |
| 1,000 | 0.0552 | 겨우 보임 |
| 2,500 | — | **채택** — 복도 끝이 읽히고 근거리는 살짝 날아감 |
| 5,000 | — | 복도는 좋지만 3m 벽이 하얗게 날아감 |
| 20,000 | 0.0977 | 과다 |

> 기록해 둘 함정 두 가지가 더 있었다.
> 1. **`PlayerFlashlight.Update`가 매 프레임 광량을 덮어쓴다.** 인스펙터나 코드로 라이트의
>    intensity를 바꿔도 다음 프레임에 `fullIntensity`로 돌아간다. 값을 바꾸려면 컴포넌트 쪽을 고쳐야 한다.
> 2. **에디터가 포커스를 잃으면 게임 뷰가 다시 그려지지 않는다.** 화면 캡처가 옛 프레임을 그대로
>    돌려주어, 바뀐 조명이 반영되지 않은 그림을 보고 한참 헤맸다. 판단은 카메라를 직접
>    RenderTexture에 렌더해서 내려야 한다.

### 8.4 사운드는 코드로 합성한 임시 소리다

체크리스트 4장은 SWUtils에 있는 기능을 직접 만들면 이유를 남기라고 요구한다.

프로젝트에 오디오 파일이 하나도 없는데, 프로토타입 문서는 "소리 없이 테스트하면 Q2의 답이 나오지
않는다"고 못 박고 있다. 그래서 형광등 험·발소리·물방울·먼 충격음·환풍기를 `ProceduralAudioBank`가
실행 중에 합성한다. 형광등 험은 60Hz 전원에서 나오는 120Hz와 그 배음으로 만들어 실제와 비슷하고,
발소리는 재질별로 잡음의 밝기와 감쇠를 다르게 준 근사치다.

`SWAudioManager`를 쓰지 않은 이유는 하나뿐이다. **`SWAudioLibrary`는 직렬화된 클립만 다루므로
실행 중에 만든 클립을 키로 등록할 수 없다.** 그래서 재생만 `AudioSource`로 직접 한다.
진짜 음원이 준비되면 라이브러리에 키로 넣고 `PlaySfxRandomPitch`(발소리)와
`PlaySfxAtPoint`(위치가 있는 소리)로 갈아 끼우면 된다. 재생 지점은 두 곳뿐이다.

같은 시드에서 항상 같은 소리가 나오도록 합성 난수는 고정 시드를 쓴다.

### 8.5 랜드마크는 무작위로 뿌리지 않는다

완전 무작위로 흩뿌리면 한곳에 몰리고 다른 구역은 텅 빈다. 그러면 "여기 아까 왔던 데다"가 성립하지 않는다.
그래서 맵을 6칸짜리 구역으로 나누고 **구역마다 하나씩** 놓는다. 24x24 맵에서 16개가 놓인다.
배치는 맵 시드로 정해지므로 같은 시드에서는 같은 자리에 같은 랜드마크가 나온다.

조명 유형(깜빡이는 형광등)은 구워 둔 조도를 바꾸지 못하고 등의 발광 색만 바꾼다.
그래도 시야에서 유일하게 움직이는 밝기라 가장 눈에 잘 걸린다.
재질을 복제하면 맵을 다시 만들 때마다 재질이 쌓이므로 `MaterialPropertyBlock`으로 처리했다(5.8절 교훈).

### 8.8 Phase 3 진행 전 처리 목록 — 2026.08.27 결정

Phase 2의 구현 항목은 전부 끝났고 자체 확인도 통과했다. 여기서 나온 점검 결과에 대해 아래와 같이
정했다. **전부 Phase 3에 들어가기 전에 처리한다.** 지금 당장 손대지 않는 이유가 있는 항목은
그 이유를 함께 적었다.

#### 처리하기로 한 것

**1. 랜드마크는 통째로 등장을 막는다.**

점검에서 벽 얼룩 유형이 허공에 뜨는 문제가 나왔다(손상 랜드마크 4개 중 3개가 벽 없는 방향).
칸의 벽 방향을 읽어 돌려놓으면 고칠 수 있지만, **고치지 않고 등장을 막기로 했다.**

이유는 랜드마크를 나중에 **파밍할 수 있는 오브젝트**로 다시 설계할 예정이기 때문이다.
Phase 4의 이상물체 수집과 성격이 겹치므로, 지금 배치 규칙을 손봐 봐야 그때 다시 짜게 된다.
만들어 둔 프리팹 4종과 `BackroomsLandmarkPlacer`는 지우지 않고 남겨 둔다. 배치만 끄면 된다.

> **대신 짚어 둘 것**: 프로토타입 문서는 "완전 무작위 공간은 무섭지 않고 짜증만 난다"라고 못 박고,
> 랜드마크를 Q2의 핵심 장치로 본다. 랜드마크를 전부 빼면 그 역할이 비는데, **7번(전등 고장과
> 어두운 구역)이 그 자리를 대신한다.** 실제로 만들어 둔 랜드마크 4유형 중 조명 유형이 가장 잘 걸렸다.
> 눈에 걸리는 표식이 하나도 없는 상태로 외부 테스트에 들어가지는 않는다는 뜻이다.

**2. ESC 옵션 팝업을 만든다.**

지금은 게임을 끌 방법이 창을 닫는 것뿐이고 커서가 화면에 갇혀 있다. ESC로 여는 옵션 팝업에 넣을 것:

```
□ 게임 종료
□ 음량 설정 (슬라이더)
□ 음량 켜고 끄기
□ 마우스 감도 설정
```

만들 때 쓸 것: 팝업은 `SWPopupBase`, 설정값 저장은 `SWPlayerPrefs`, 화면 겹침은
`SWMonoStackStateMachine`(체크리스트 4장 표). 마우스 감도는 `PlayerCameraLook`의 `sensitivity`,
음량은 `SWAudioManager`가 이미 들고 있으므로 팝업은 값을 읽고 쓰기만 한다.

이때 **`ProjectR.UI` 어셈블리가 처음 생긴다.** 의존 방향은 3.1절 표대로 위 전부를 참조하고,
반대로 다른 어셈블리가 UI를 참조하지 않는다.

또 팝업이 열려 있는 동안 조작 입력을 막아야 한다. `PlayerInputReader`가 디버그 콘솔에 대해
이미 같은 일을 하고 있으므로 그 자리에 조건을 하나 더 얹는다.

**3. 전등을 고장 내고, 아예 없는 구역을 만든다.**

지금은 **모든 칸에 형광등이 켜져 있어** 어두운 곳이 없다. 손전등이 의미를 가지려면 빛이 없는
구역이 있어야 한다. 두 가지를 나눠서 본다.

| 연출 | 지금 구조로 가능한가 | 필요한 작업 |
|---|---|---|
| 고장 난 등 (깜빡임) | **가능** | `FlickeringLamp`가 이미 있다. Unlit 재질 색만 흔들므로 다시 굽지 않아도 된다 |
| 등이 꺼진 어두운 구역 | **불가능** | 타일 프리팹과 라이트맵을 추가로 만들어야 한다 |

두 번째가 그냥 되지 않는 이유를 적어 둔다. **라이트맵은 프리팹 단위로 구워져 있다.** 타일 5종이
라이트맵 2장을 나눠 쓰고 있어서, 같은 프리팹을 쓰는 칸은 전부 같은 밝기다. 램프 메시만 꺼도
천장은 그대로 밝게 남아 "등이 없는데 환한 칸"이 된다.

그러므로 어두운 구역은 **어두운 버전 타일 5종을 따로 만들어 따로 구워야 한다.** 결과로 프리팹이
5종에서 10종이 되고 라이트맵 장수도 늘어난다(지금 2장 → 3~4장 예상). 조립할 때 칸마다 밝은 버전과
어두운 버전 중 하나를 고르게 하고, 어두운 칸이 몇 %나 어떤 덩어리로 나올지는 생성 설정으로 뺀다.

Phase 1의 성능 수치는 이 변경 뒤에 다시 봐야 한다. 라이트맵 장수가 늘면 드로우콜과 메모리가 함께 는다.

**4. 손전등 그림자는 가볍게 간다.**

여기에 성능을 많이 쓰지 않기로 했다. 지금은 Hard 그림자에 추가 라이트 그림자 해상도 2048이다.
해상도를 낮추는 것부터 하고, 그래도 무거우면 그림자를 끈다. 실기 측정 전에 미리 낮춰 둔다.

#### 나중으로 미룬 것

**5. 발소리 재질 구역 분할** — 재질 3종을 합성해 두었지만 맵에 콘크리트뿐이라 한 종류로 들린다.
진짜 음원을 넣을 때 제대로 손보기로 했다. 그때 `SWAudioLibrary` 이전(8.4절)도 함께 한다.

**6. 탈출 지점 단서** — 24x24 칸에서 위치를 알려 주는 것이 없다. 헤매게 하는 것이 Q2의 의도와
맞는지, 짜증으로만 작동하는지 판단이 필요해 미룬다.

**7. 상자 랜드마크가 칸 가운데를 차지하는 문제** — 1번에 따라 랜드마크 자체를 빼므로 함께 사라진다.

#### 작업 규칙

**빌드는 요청이 있을 때만 만든다.** 빌드가 잦으면 개발 진척이 나지 않는다.
`Builds/Win64`는 08-26 23:46 시점 빌드이며, 다음 빌드 요청 전까지 낡은 채로 둔다.

### 8.9 8.8절 처리 목록 완료 (2026.08.27)

8.8절에서 정한 네 가지를 순서대로 끝냈다. 아래는 실제로 한 일과 그 과정에서 정한 것이다.

#### 1. 랜드마크 등장 막기

`BackroomsMapBuilder` 오브젝트에 붙은 `BackroomsLandmarkPlacer` 컴포넌트를 껐다. 코드는 한 줄도 고치지 않았다.
컴포넌트가 꺼져 있으면 `Awake`도 `OnEnable`도 돌지 않으므로 `LandmarkRoot` 자체가 만들어지지 않는다.
프리팹 4종과 배치 코드는 그대로 남아 있어 파밍 오브젝트로 다시 설계할 때 꺼내 쓰면 된다.

#### 2. 어두운 구역 — 고장 난 등이 아니라 **등이 없는 칸**이다

여기서 방향을 한 번 바꿨다. 처음에는 어두운 타일에도 꺼진 형광등 메시를 남겨 두었다.
손전등을 비췄을 때 죽은 등이 보이면 "여긴 등이 나갔다"로 읽힐 것이라고 봤기 때문이다.
**그러나 연출용으로 죽은 등을 남기는 것보다 등이 아예 없는 칸으로 처리하는 편이 맞다고 정했다.**
"고장"은 깜빡이는 등(3번)이 이미 맡고 있고, 두 연출이 같은 뜻을 나눠 가지면 어느 쪽도 신호가 되지 못한다.

- 깜빡이는 등 = 여기 등이 있는데 상태가 이상하다 → 표식
- 등이 없는 칸 = 여기는 애초에 빛이 없다 → 손전등이 필요한 구역

그 결과 어두운 타일에서는 `FluorescentLamp`를 통째로 지웠다. 라이트맵도 함께 필요 없어졌다(아래).


**생성 쪽.** `MazeDarkZoneCarver`를 새로 만들었다. 어두운 칸을 무작위로 흩뿌리면 밝은 칸과
한 칸씩 번갈아 나와 "구역"으로 읽히지 않는다. 그래서 씨앗 칸을 고른 뒤 **통로를 따라** 번져 나가게 했다.
벽을 무시하고 사각형으로 칠하면 벽 하나를 사이에 두고 밝은 칸과 어두운 칸이 붙어 버린다.

생성 설정에 두 값을 노출했다. 체크리스트가 요구한 "몇 %나 어떤 덩어리로"에 그대로 대응한다.

| 설정 | 기본값 | 뜻 |
|---|---|---|
| `darkCellRatio` | 0.12 | 전체 칸 대비 어두운 칸의 비율 |
| `darkZoneCount` | 3 | 어두운 칸을 몇 덩어리로 뭉칠지 |

**시작 칸과 탈출 칸은 절대 어두워지지 않는다.** 시작하자마자 아무것도 안 보이거나 탈출 지점이 어둠에
묻히면 길 잃음이 긴장이 아니라 짜증으로만 작동한다. 단위 테스트로 못 박아 두었다.

**에셋 쪽.** 타일 5종의 **프리팹 변형(Variant)** 을 만들어 `Tile_*_Dark` 5종을 추가했다. 변형에서 바꾼 것은 둘이다.

```
FluorescentLamp   자식 오브젝트를 통째로 삭제 (등 메시 + Baked Light)
남은 렌더러       Contribute GI 끄고 lightmapIndex를 -1로 박음
```

원본을 복제하지 않고 변형으로 만든 덕에 벽·바닥·천장 값을 고치면 어두운 타일에도 그대로 따라온다.

**굽기.** `TileLightmapBaker`가 타일 폴더 전체를 훑으므로 굽기 씬을 다시 만들고 한 번 구우면 끝났다.
어두운 타일은 저장된 렌더러 0개·라이트맵 0장으로 나오고, 결과는 **라이트맵 2장 그대로**다.

> **처음에는 어두운 타일도 구웠다가 되돌렸다.** 8.8절이 "라이트맵 2장 → 3~4장으로 는다"고 예상해 둬서
> 그대로 따랐는데, 실제로 구워 보니 어두운 타일의 라이트맵은 **전 영역이 순수 검정**이었다.
> 백룸 씬의 환경광이 Flat + 검정(0,0,0)이라 **라이트맵을 아예 안 붙여도 결과가 똑같다.**
> 즉 검정을 저장한 텍스처 영역이 아틀라스를 차지하고 있었을 뿐이고, 그게 3장이 된 이유였다.
> Contribute GI를 끄자 2장으로 돌아왔다. 예상이 맞았는지가 아니라 **왜 늘어야 하는지**를 물었어야 했다.

> **인덱스 함정**: 변형은 원본 렌더러에 직렬화된 `lightmapIndex`를 그대로 물려받는다.
> `BakedLightmapData`가 비면 `Apply()`가 아무것도 하지 않아 그 인덱스가 남고,
> 실행 중 합쳐진 목록에서 **엉뚱한(밝은) 라이트맵**을 가리키게 된다. 그래서 프리팹에 -1을 명시적으로 박았다.
> 플레이 모드에서 어두운 칸 렌더러 67개가 전부 -1인 것을 확인했다.

> **`TileLightingTunerWindow`와 부딪히지 않는다**: 이 창은 타일 폴더의 모든 프리팹에 광량을 한꺼번에
> 적용하지만, 어두운 타일에는 Light가 아예 없어 `continue`로 건너뛴다. 다만 값을 **읽어 오는** 쪽이
> 첫 프리팹만 보고 있어 어두운 타일을 집으면 값이 비므로, 형광등을 가진 첫 타일에서 읽도록 고쳤다.

**조립 쪽.** `MazeTileLibrary`가 밝은 5종과 어두운 5종을 함께 들고, `TryGetTile`이 칸의 밝기를 받아 고른다.
어두운 타일이 비어 있으면 밝은 타일로 대신한다. 맵이 비는 것보다는 밝은 편이 낫다.

#### 3. 전등 고장 연출 — 랜드마크가 비운 자리를 대신한다

`BackroomsBrokenLampPlacer`를 새로 만들었다. 맵을 6칸 구역으로 나눠 구역마다 등 하나에
`FlickeringLamp`를 붙인다. 배치 규칙을 랜드마크와 똑같이 잡은 것은 의도적이다.
랜드마크를 뺀 자리를 그대로 이어받아야 하기 때문이다. 이미 꺼진 칸, 시작 칸, 탈출 칸은 건드리지 않는다.

**다시 굽지 않아도 된다.** 구워 둔 조도는 그대로고 등의 발광 색만 흔들린다.

다만 **속성 블록을 덮어쓴 렌더러는 정적 배칭에서 떨어져 나와 따로 그려진다.** 깜빡이는 등 하나가
드로우콜 하나다. 그래서 `FlickeringLamp`가 화면에 들어온 등만 흔들도록 `isVisible`을 먼저 확인하게 했다.
14x14 맵에서 깜빡이는 등은 8개였다. 실기 측정 때 이 몫을 함께 봐야 한다.

#### 4. ESC 옵션 팝업 — `ProjectR.UI` 어셈블리가 생겼다

의존 방향은 2장 표대로다. UI가 아래를 전부 참조하고, 아무도 UI를 참조하지 않는다.

**설정값을 어디에 둘지가 실제 문제였다.** 팝업은 UI에 있고 마우스 감도를 쓰는 `PlayerCameraLook`은
백룸에 있어 서로를 참조할 수 없다. 그래서 값을 **`ProjectR.Core`의 `GameSettings`** 가 혼자 들고,
바뀌었다는 사실만 `SWEventBus`로 알린다. 저장은 `SWPlayerPrefs`에 맡겼다.

```
OptionsPopup (UI)  →  GameSettings (Core)  →  SWEventBus  →  PlayerCameraLook (Backrooms)
                                           →  SWAudioManager
```

**입력 차단은 UI를 거치지 않는다.** `PlayerInputReader`가 `SWPopupManager.ActivePopupCount`를 보고
스스로 막는다. 디버그 콘솔에 대해 이미 하던 일에 조건 하나를 얹었을 뿐이다.

**ESC만은 `PlayerInputReader`를 거치지 않는다.** 거치면 팝업이 열린 순간 입력이 통째로 막혀
한 번 연 팝업을 다시 닫을 수 없다. `OptionsPopupController`가 `Keyboard.current`를 직접 읽는다.

작업 중에 버그를 하나 잡았다. `GameSettings`가 `SWAudioManager.HasInstance`를 확인하고 없으면
그냥 넘어가게 되어 있었는데, **아직 소리를 하나도 재생하지 않은 시점에는 매니저가 없어서
저장해 둔 음량이 영영 반영되지 않았다.** `Instance`로 만들어 두도록 고쳤다.

> **폰트는 임시다.** TMP 필수 리소스를 넣지 않아 한글 폰트 에셋이 없으므로 레거시 `UnityEngine.UI.Text`에
> 내장 `LegacyRuntime.ttf`를 썼다. 사운드와 같은 취급이다(8.4절). 진짜 폰트가 정해지면 TMP로 갈아 끼운다.

**`SWMonoStackStateMachine`은 쓰지 않았다.** 8.8절은 화면 겹침에 이것을 쓰기로 적어 두었지만,
`SWPopupManager`가 이미 활성 팝업을 목록으로 쌓고 `HideTop`까지 갖고 있어 겹침 관리가 중복된다.
지금 화면이 옵션 팝업 하나뿐이라 상태 기계를 얹으면 층만 늘어난다.
**화면이 여러 개로 늘어나 팝업이 아닌 전환이 생기면 그때 도입한다.** 체크리스트 4장 표의 해당 줄은 □로 둔다.

팝업은 `HomeScene`에도 같이 놓았다. 게임이 시작되는 화면에서 끌 방법이 없으면 반쪽짜리다.

### 8.10 빌드와 외부 테스트를 뒤로 미룬다 — 2026.08.27 결정

**Phase 2의 구현은 전부 끝났지만 판정(Q2)은 받지 않고 Phase 3으로 넘어간다.**

정한 것은 아래와 같다.

```
빌드        기능이 대부분 완성된 뒤에 한 번에 만든다
외부 테스트  그 빌드가 나온 뒤에 한다
중간 확인    개발자가 중간중간 따로 본다 (판정이 아니라 점검)
```

빌드가 잦으면 개발 진척이 나지 않는다는 8.8절 작업 규칙의 연장이다.
외부 테스터를 부르는 일도 한 번에 몰아서 하는 편이 사람을 덜 쓴다.

#### 이 결정이 무엇을 미루는지는 분명히 해 둔다

체크리스트 1장은 "앞 단계를 건너뛰고 뒤 단계를 시작하지 않는다"라고 못 박고 있고,
Phase 2의 완료 기준은 "외부 테스터가 몬스터 없이도 긴장한다"이다.
**그 기준을 지금 충족하지 않은 채로 Phase 3에 들어간다.** 문서를 고쳐 기준을 낮춘 것이 아니라,
기준은 그대로 두고 판정 시점만 뒤로 옮긴 것이다. 프로토타입 문서는 손대지 않았다.

감수하는 위험은 하나다. 프로토타입 문서와 체크리스트 Phase 2 판정란은 Q2에 실패했을 때
**"몬스터를 넣어도 해결되지 않는다"** 라고 적고 있다. 실패 시 대응이 아트 방향·공간 규모·사운드의
전면 재설계이므로, Q2가 미판정인 동안 쌓는 Phase 3 작업물은 그 재설계에 함께 휩쓸릴 수 있다.

이 위험을 줄이려고 정한 것:

- **몬스터를 넣기 전에 개발자 자체 확인을 한 번 더 한다.** 판정은 아니지만(8.7절), 어두운 구역과
  깜빡이는 등이 들어간 뒤의 분위기를 만든 사람이라도 한 번은 봐야 한다.
- **Phase 3 작업을 백룸 공간 설계에 덜 묶이게 짠다.** 몬스터 행동은 Behaviour Tree 에셋과
  Blackboard로 빠져 있으므로, 공간 규모가 바뀌어도 수치 조정으로 흡수되는 범위가 넓다.
- **Q2 미판정 상태를 잊지 않게 이 절과 체크리스트 Phase 2 판정란에 남겨 둔다.**

#### 빌드 블로커는 해소됐다

### 9.2 트리는 하나뿐이고 수치는 전부 Blackboard에 있다

체크리스트가 요구한 규칙을 그대로 지켰다. 몬스터 유형이 늘어나도 트리를 복제하지 않는다.

```
                        ┌─ 추격 판단 ─ 플레이어가 보이는가 → [추격 알림] 추격
                        ├─ 수색 판단 ─ 뒤져 볼 단서가 있는가 → [수색 알림] 수색
반복 ─ 행동 선택 ───────┼─ 매복 판단 ─ 매복할 것인가 ──────→ [매복 알림] 매복
                        ├─ [복귀 알림] 복귀
                        └─ [배회 알림] 배회
```

왼쪽이 우선한다. 대괄호는 Decorator다.

수치는 하나도 노드에 박혀 있지 않다. 감지 거리(14m), 시야각(110°), 청각 거리(22m),
배회·추격·수색 속도(1.9 / 3.9 / 2.4 m/s), 추격 유예(2.5초), 수색 지속(14초),
매복 확률(0.45)과 대기 시간(12초), 조우 거리(1.3m)가 전부 Blackboard Key다.
다음 몬스터는 같은 트리에 Blackboard Override만 얹으면 된다.

**추격 속도를 플레이어 달리기(4.6 m/s)보다 느리게 잡았다.** 직선에서는 무조건 도망칠 수 있다.
대신 달리면 소음 반경이 22m로 커져 다른 곳에 있던 몬스터를 부른다.
"들키지 않게 걷느냐, 들키더라도 달리느냐"가 플레이어의 선택이 되게 하려는 것이다.
Phase 3 판정이 "내가 잘했다고 느끼는가"이므로 도망칠 수 없는 설계는 처음부터 답이 될 수 없다.

### 9.3 감지는 노드가 아니라 컴포넌트에 두었다

감지를 Action 노드로 만들면 추격 중에는 감지가 돌지 않는다. 그 노드가 실행 중이 아니기 때문이다.
그래서 시야와 청각은 `MonsterSenses` 컴포넌트가 항상 돌리고, 결과만 Blackboard에 적는다.
노드는 적힌 결과를 읽기만 한다.

이렇게 나누면 두 가지가 따라온다.

- 광선은 0.1초마다 한 번만 쏜다. 트리가 몇 번 돌든 늘어나지 않는다.
- 감지 방식이 바뀌어도(소리 추적 몬스터 등) 트리는 그대로 두고 컴포넌트만 갈아 끼우면 된다.

시선 판정은 플레이어 몸의 표본 세 곳(머리·가슴·발)에 하나라도 닿으면 보이는 것으로 본다.
한 점만 보면 모퉁이에 걸쳤을 때 판정이 딱딱 끊긴다. 앉으면 표본 자체가 낮아져
벽이나 난간에 더 쉽게 가려진다. 은신 규칙을 몬스터가 아니라 플레이어 쪽에 둔 이유가 이것이다.
몬스터가 늘어나도 "앉으면 어떻게 되는가"는 한 벌만 존재한다.

### 9.4 이 트리는 실행 중인 노드를 바깥에서 끊지 않는다

`SWBehaviourSelectorNode`는 자식이 Running을 돌려주는 동안 그 자식만 계속 실행한다.
앞쪽의 더 급한 조건을 다시 보지 않는다. 그래서 **물러날 때가 되면 행동 노드가 스스로 끝낸다.**

- 배회는 플레이어가 보이거나 소리를 들으면 Success를 돌려준다.
- 추격은 놓친 뒤 유예 시간이 지나면 Success를 돌려준다.
- 수색은 플레이어가 보이거나 수색 시간이 다하면 Success를 돌려준다.

Success가 올라가면 반복 노드가 Selector를 처음부터 다시 시작시킨다.
**Failure가 아니라 Success로 끝내는 것이 중요하다.** Failure로 끝내면 Selector가
그다음 자식으로 넘어가 버려서 우선순위가 한 칸씩 밀린다.

이 방식은 반응이 최대 한 프레임 늦다. 대신 노드마다 "언제 물러나는가"가 그 노드 안에 적혀 있어
트리 그림만 보고 흐름을 읽을 수 있다. 지금 규모에서는 이쪽이 낫다고 판단했다.

### 9.5 판단력은 기억 한 줄로 만든다

기획서 7.5절이 말하는 네 가지 연출을 전부 넣었지만, 실제 코드는 대부분 한 줄짜리다.

| 연출 | 실제 구현 |
|---|---|
| 기억 | 수색 지점을 마지막 목격 위치 쪽으로 치우쳐 뽑는다 (`Random.value`의 제곱) |
| 학습한 척 | 앉아서 시야에서 사라진 자리를 최대 6곳까지 세어 두었다가 45% 확률로 먼저 본다 |
| 매복 | 수색이 헛수고로 끝난 직후에만 45% 확률로 탈출 지점에 가서 멈춘다 |
| 정보 노출 | 행동 모드가 바뀔 때 Decorator가 소리를 낸다 |

**매복은 확률만으로 판정하지 않는다.** 확률만 보면 배회 중에도 계속 매복으로 빠져
몬스터가 통로에서 사라진다. 수색 노드가 실패할 때만 표식을 켜고, 매복 판단 노드가
그 표식을 소비하면서 한 번 굴린다. 그래서 매복은 "쫓다 놓친 뒤"에만 일어난다.

**매복 중에는 완전히 멈춘다.** 발소리가 멀어지다 뚝 끊기는 정적을 만들려는 것이다.
기획서가 "가장 강한 연출"이라고 적은 것이 이것이고, 서성이면 소리가 이어져 효과가 사라진다.

---

### 9.6 소리를 Decorator로 뺀 이유

체크리스트의 규칙은 "행동 모드가 바뀌는 액션 노드는 진입 시 반드시 소리를 발행한다"이다.
행동 노드마다 소리 호출을 넣으면 노드를 새로 만들 때 빠뜨릴 수 있다.
그래서 **모드를 바꾸는 통로를 Decorator 하나로 만들고 행동 노드에는 소리 코드를 두지 않았다.**
트리 그림에서 소리가 빠진 가지는 눈에 보인다.

소리를 내는 시점은 노드 진입이 아니라 **자식이 Running을 돌려준 뒤**다.
곧바로 실패하는 행동(이미 돌아와 있어 복귀할 필요가 없는 경우 등)까지 소리를 내면
플레이어는 있지도 않은 행동을 읽게 된다.

모드 변화는 `MonsterAgent`가 알리고 `MonsterVoice`가 받아 소리를 낸다.
같은 모드로 다시 들어오는 것은 변화가 아니므로 소리가 나지 않는다.
소리는 8.4절과 같은 임시 합성음이며, 재생 지점은 `MonsterVoice`와 `MonsterFootsteps` 두 곳뿐이다.

### 9.7 천장이 바닥으로 구워지고 있었다 — 버그 1건 발견 및 수정

첫 실행에서 몬스터가 배회를 시작하자마자 멈춰 섰다. 값을 찍어 보니 목적지의 Y가 **3.2**였다.

```
destination=(32.5, 3.2, 5.5)   pathStatus=PathPartial   desiredVel=0.00
```

원인은 타일 천장이었다. NavMesh를 충돌체 기준으로 구우면 천장 슬래브의 **윗면도 걸을 수 있는 바닥**이
된다. 맵 전체에 두 번째 층이 생긴 셈이고, 무작위 배회 지점이 거기로 뽑히면
바닥에 있는 몬스터는 갈 수 없어 경로가 Partial로 끊긴 채 멈춘다.

벽은 문제가 되지 않았다. 두께가 에이전트 반지름(0.45m)보다 얇아 애초에 바닥이 만들어지지 않는다.
천장만 4×4 슬래브라 넓은 면이 그대로 남았다.

수정은 타일 프리팹 10종의 `Ceiling`에 `NavMeshModifier(ignoreFromBuild)`를 붙이는 것이다.
굽는 범위를 높이로 자르는 방법도 있었지만, 타일 높이가 바뀌면 조용히 깨진다.
컴포넌트로 두면 "천장 위에는 길이 없다"가 프리팹에 적혀 있게 된다.

부수 효과로 **굽기 시간이 절반 이하가 되었다.** 굽을 면이 절반으로 줄었기 때문이다.

```
수정 전   45.2ms
수정 후   10.4 ~ 14.3ms   (196칸 기준)
```

### 9.9 몬스터에는 충돌체를 달지 않았다

몬스터는 충돌체 없이 `NavMeshAgent`로만 움직인다. 지형은 NavMesh가 막고, 플레이어는 거리로 붙잡는다.
충돌체를 달면 캐릭터 컨트롤러를 밀어내는 일만 생긴다.

라이트 프로브는 이 프로젝트에 없다(5.5절). 백룸 씬의 환경광이 검정이므로
**몬스터는 손전등을 비추기 전까지 거의 보이지 않는다.** 의도한 것은 아니지만 이대로 둔다.
어둠 속에서 발소리만 들리다가 손전등에 잡히는 편이 낫다. 실제로 어떻게 보이는지는 9.8절의
"사람이 직접 해 본 판정"에서 함께 본다.

`BackroomsActivity` 생성자에서 받도록 열어 두었다.

### 10.2 계산부를 어셈블리째 갈라 놓았다

체크리스트는 "격자 인벤토리 계산부를 Unity와 분리해 작성"이라고만 적혀 있다.
같은 폴더에 두고 유니티 타입을 안 쓰는 것으로도 지킬 수는 있지만, 그건 사람이 계속 지켜야 하는 규칙이다.

`ProjectR.Inventory` 어셈블리를 따로 만들고 `noEngineReferences: true`로 두었다.
이제 `Vector2Int` 하나만 써도 컴파일이 깨지므로 분리가 규칙이 아니라 사실이 된다.
그 대가로 `SWLog`도 못 쓰지만, 계산부는 로그를 남길 것이 아니라 참·거짓을 돌려줄 것이라 손해가 없다.

의존 방향은 `Data` → `Inventory`, `Backrooms` → `Inventory`, `UI` → `Inventory`로만 흐른다.
`Inventory`는 아무것도 참조하지 않는다.

덕분에 배치 규칙 12가지를 에디트 모드 테스트로 그대로 검증했다(6장).

### 10.3 정의 에셋과 목록은 SWUtils 것을 그대로 썼다

이상물체 정의는 `SWIdentifiedObject`를 상속한다. 코드명·표시명·설명·카테고리가 이미 들어 있어
새로 만들 것은 형태(가로세로 칸 수), 등급, 색, 정산 수치 네 가지뿐이었다.

목록도 `SWIODatabase`를 그대로 쓴다. 코드명·ID 조회, 정렬, ID 자동 부여가 다 들어 있다.
`AnomalyLibrary` 같은 것을 새로 만들 뻔했는데, 2장 상시 확인 항목의 첫 줄이 그것을 막았다.

다만 정산 화면에서 정의를 찾을 때는 `GetDataByCodeName`을 쓰지 않고 목록을 직접 훑는다.
`AnomalyDefinition.DefinitionId`는 코드명이 비어 있으면 에셋 이름으로 물러서는데,
`GetDataByCodeName`은 그 물러섬을 모르기 때문이다. 8종뿐이라 훑는 비용은 없다.

### 10.4 이상물체 프리팹은 한 개뿐이다

종류가 8종인데 프리팹은 `Anomaly_Pickup` 하나다.
크기는 정의에 적힌 격자 형태에서, 색은 정의에 적힌 색에서 실행 중에 만든다.

종류마다 프리팹을 만들면 종류를 하나 늘릴 때마다 에셋 작업이 따라붙는다.
지금은 아트가 박스 수준이면 되는 단계이고, 무엇을 주웠는지는 크기와 색만으로 구분된다.
진짜 모델이 생기면 정의에 프리팹 칸을 하나 더하고 비어 있을 때만 상자를 쓰면 된다.

색은 재질을 복제하지 않고 `MaterialPropertyBlock`으로 바꾼다.
그래서 이 상자는 정적 배칭에서 빠지는데, 맵 전체에 아홉 개뿐이라 5.4절의 측정에 영향이 없다.
(깜빡이는 등이 같은 이유로 배칭에서 빠져 있다 — 8.9절)

### 10.5 정산 수치는 주울 때가 아니라 나올 때 센다

주울 때 후원금을 더하는 편이 방송 흐름에는 더 맞아 보인다.
그런데 그렇게 하면 버릴 때 빼야 하고, 버린 것을 다시 주우면 또 더해야 한다.
더하고 빼는 자리가 늘어날수록 어긋날 자리도 늘어난다.

`End()` 시점에 가방에 남아 있는 것만 세는 방식으로 통일했다.
가방이 곧 정산서이므로 버리기와 줍기는 가방만 건드리면 되고, 수치는 한 곳에서만 만들어진다.

실측: 거울 조각(620/120) + 컵(80/10) = 후원금 700 · 시청자 130.
거울을 버리고 나오면 후원금 80. 실패로 끝나면 전부 0.

### 10.6 버리는 것은 끌어내기가 아니라 오른쪽 클릭이다

격자 밖으로 끌어내면 버려지는 방식이 흔하다. 그런데 그 조작은 옮기려다 손이 미끄러진 것과
버리려고 끌어낸 것이 똑같이 생겼다. 버리기는 되돌릴 수 없으므로 두 조작을 갈라 두었다.

- 왼쪽 버튼으로 끌기 → 옮기기. 놓을 수 없는 자리면 원래 자리로 되돌아간다
- 오른쪽 클릭 → 버리기

버린 물건은 사라지지 않고 플레이어 발밑에 다시 놓인다.
사라지게 하면 "무엇을 버릴지" 고민하는 대신 아무거나 버리게 된다.
되돌아올 수 있어야 버리는 것이 결정이 된다.

버리기를 알리는 것은 활동이고, 월드 어디에 놓을지는 씬이 정한다(`AnomalyDropped`).
그래서 UI는 월드를 모르고, 배치 컴포넌트는 UI를 모른다.

### 10.7 저장은 세 곳에서만 한다

기획서 11.1절이 요구한 것은 두 가지였다.

- 활동 도중 강제 종료하면 활동 시작 시점으로 되돌린다
- 방송 시간은 되돌리지 않는다. 되돌리면 위기 회피 수단이 된다

이 둘은 저장 시점을 고르는 것만으로 동시에 만족한다.

```
활동 시작 직후  ← 방송 시간을 소비한 뒤에 저장한다
활동 정산 완료  ← 얻은 것이 여기서 처음 기록된다
하루 종료
```

활동 도중에는 저장하지 않으므로 강제 종료하면 활동 시작 시점으로 돌아간다.
그 시점에는 방송 시간이 이미 빠져 있으므로 도망쳐도 얻는 것이 없다.

실측: 방송 시간 240분 → 활동 시작(180분) → 이상물체 2개 습득 → 플레이 모드 강제 종료 → 다시 실행.
결과는 1일차 / 방송 시간 180분 / 이상물체 0 / 후원금 0.

저장은 `SWSaveDataManager`를 쓰되 클라우드 백업은 끈다(`backupToCloud: false`).
불러오기도 클라우드를 거치지 않는 경로를 쓴다. 클라우드를 거치면 완료가 콜백으로 넘어와
`Awake`에서 상태를 준비할 수 없기 때문이다.

테스트를 처음부터 다시 하려고 `state.reset` 명령을 함께 넣었다(7장).

### 10.8 실패 손실은 규칙 하나로 모아 두었다

`BackroomsActivity.Settle()`은 실패 여부와 상관없이 성공했을 때의 결과를 먼저 다 만든다.
그다음 실패했을 때만 `ILossPolicy`에 그 결과를 통째로 넘긴다.

이렇게 두면 기획서 7.7절의 완화 순서가 전부 구현체 교체로 끝난다.

| 완화 단계 | 바꿀 것 |
|---|---|
| 1단계 방송 사고 클립 보상 | 이상물체만 지우고 후원금은 일부 남기는 구현체 |
| 2단계 회수 기회 | 기절 지점 정보를 결과 표식에 남기는 구현체 |
| 3단계 보험 업그레이드 | 보유 업그레이드를 보고 남길 양을 정하는 구현체 |
| 4단계 일부 소실 | 가방 절반 또는 고가품 우선으로 지우는 구현체 |

`TotalLossPolicy`는 이상물체와 함께 후원금·시청자 변동도 0으로 만든다.
잃은 물건으로 번 돈이 남아 있으면 잃었다는 말이 성립하지 않는다.

실패 경로는 지금 몬스터 조우 하나뿐이다. 방송 시간 초과는 없앴다(10.9절).

### 10.9 방송 시간은 제한 시간이 아니라 행동력이다 — 2026.08.28 결정

처음에는 `BroadcastTimer`를 만들어 백룸 안에서 12분을 세고, 다 쓰면 강제 종료시켰다.
기획서 4.3절의 "시간 내에 탈출하지 못하면 강제 종료되고 감점 정산된다"를 그대로 옮긴 것이다.

**이 해석이 틀렸다.** 방송 시간은 백룸 안에서 흐르는 제한 시간이 아니라 **하루치 행동력**이다.
활동에 들어갈 때 그 활동에 정해진 만큼 한 번에 빠지고, 활동 안에서는 줄지 않는다.

그래서 세 가지를 바꿨다.

| 바뀐 것 | 내용 |
|---|---|
| 시간대(슬롯) | 없앴다. 방송 시간이 그 자리를 대신한다 |
| `GameState.RemainingSlots` | `RemainingBroadcastMinutes`(분)로 바뀌었다 |
| `IActivity.SlotCost` | `BroadcastCost`(분)로 바뀌었다 |
| `BroadcastTimer` | 지웠다. 백룸 안에 카운트다운이 없다 |

수치는 이전 흐름을 그대로 옮겼다. 하루 240분, 백룸 1회 60분이면 하루 네 번으로 예전 슬롯 4칸과 같다.
분 단위로 바꾼 이유는 활동마다 드는 시간이 다를 수 있게 하려는 것이다.
슬롯은 1이나 2밖에 될 수 없지만 분은 알바 90분, 미니게임 30분처럼 잘게 나눌 수 있다.

**기획서 4.3절과 11.1절을 이 결정에 맞게 고쳤다.** 코드만 고치고 기획서를 두면 다음에 읽는 사람이
없어진 타이머를 다시 만들게 된다.

4장과 8장에 남아 있는 "시간대 4→3" 같은 기록은 그때 실제로 잰 값이라 그대로 둔다.
지금 코드에서 같은 자리에 있는 것은 방송 시간(분)이다.

한 가지 잃은 것이 있다. Phase 4의 확인 항목 "타이머가 실제로 결정을 바꾸는가"에서
타이머가 사라졌다. **지금 나가자를 만드는 압박은 몬스터와 손전등 배터리 둘뿐이다.**
그 둘로 충분한지는 외부 테스트에서 봐야 한다. 부족하면 압박을 시간이 아닌 다른 것으로 만들어야 한다.

### 10.10 줍기가 안 되던 이유 — 조준 보조가 없었다

E를 아무리 눌러도 줍히지 않고, 안내 문구조차 뜨지 않는다는 보고가 있었다. 실측 결과는 이랬다.

```
cam pos=(50.49, 1.64, 24.28) fwd=(-0.65, -0.76, 0.00)
지금 레이: Player 0.00      ← 캐릭터 컨트롤러 캡슐에 거리 0으로 명중
FocusedPickup=없음
```

눈높이 1.64m의 카메라는 캐릭터 컨트롤러 캡슐 **안에** 있다.
그래서 줍기 레이가 출발하자마자 자기 캡슐을 맞고 끝났고, `FocusedPickup`은 언제나 null이었다.
입력이 아니라 판정 쪽 문제라 E를 어떻게 누르든 달라지지 않았다.

**처음 고칠 때 원인을 한 번 잘못 짚었다.** 자기 캡슐에 맞는 것이 상시 일어나는 줄 알고
굵은 레이(SphereCast)로 바꿨는데, 뒤에 실측해 보니 그렇지 않았다.

| 상황 | 가는 레이 | 굵은 레이 |
|---|---|---|
| 서서 정면 | 자기 몸 안 맞음 | **Player@0.00** |
| 서서 아래 45도 | 자기 몸 안 맞음 | **Player@0.00** |
| 캐릭터 컨트롤러를 껐다 켜서 옮긴 직후 | **Player@0.00** | **Player@0.00** |

가는 레이는 시작 지점이 콜라이더 안이면 그 콜라이더를 무시하므로 평소에는 자기 몸이 잡히지 않는다.
눈높이는 서서 1.62m·앉아서 0.95m로 캡슐(1.8m / 1.1m)보다 항상 낮아 어느 자세에서도 안쪽이다.
**굵은 레이는 시작 지점이 캡슐과 겹쳐 있어 언제나 거리 0으로 자기 몸을 먼저 잡는다.**
자기 몸을 맞는 문제는 굵은 레이가 만든 것이지 원래 있던 것이 아니었다.

그러면 원래 버그의 진짜 원인은 **조준 보조가 하나도 없었던 것**이다.
조준선이 없는 상태에서 바닥에 놓인 0.3m짜리 상자를 3m 안에서 정확히 겨눠야 했다.
보고 있다고 생각한 자리와 실제 광선이 가는 자리가 달랐고, 안내 문구조차 뜨지 않으니 확인할 방법이 없었다.

지금은 이렇게 되어 있다.

```
■ 조준선 추가            겨눈 것이 주울 수 있는 것이면 색이 진해지고, 가방이 꽉 찼으면 붉어진다
                        이것 하나가 원래 문제의 대부분이었다
■ 판정은 가는 레이       화면의 조준선과 판정이 정확히 같은 선이다
■ 자기 몸 건너뛰기       캐릭터 컨트롤러를 껐다 켜서 옮긴 직후에는 물리 쪽 캡슐이 아직 따라오지 않아
                        가는 레이도 자기 몸을 맞는다. 맵을 만든 뒤 시작 칸에 놓는 것이 바로 그 방식이라
                        탐험을 시작하자마자 주우려 하면 여기에 걸린다
                        RaycastNonAlloc으로 받아 자기 몸은 건너뛰고 그 뒤를 이어서 본다
```

**성능은 판단 근거가 아니었다.** 같은 자리에서 20000회씩 재 보니
가는 레이 0.349us, 굵은 레이 0.392us로 1.12배 차이였다. 60fps 한 프레임의 0.0024%다.
가는 레이를 고른 이유는 값이 아니라 **화면에 보이는 조준선과 판정이 같은 선이어야 한다**는 것이다.

줍기 입력에 걸어 두었던 Hold도 뺐다. "들어가는 순간의 부담"은 내가 만든 것이지
기획서가 요구한 것이 아니었다. 필요해지면 그때 진행 표시와 함께 넣는 편이 낫다.

**입력 자체는 사람이 눌러 봐야 확인된다.** 에디터 게임 뷰가 포커스를 잃은 상태에서는
키 이벤트를 만들어 넣어도 액션까지 가지 않아(`Application.isFocused = False`) CLI로는 확인할 수 없었다.
그래서 겨누기와 줍기를 갈라 `PlayerPickupInteractor.TryCollectFocused()`를 열고
`pickup.take` 명령을 붙였다. 조준 → 줍기 → 가방 1개 · 월드 상자 9→8까지는 이것으로 확인했다.

### 10.11 가방은 팝업이 아니라 화면에 붙어 있다

처음에는 Tab으로 여는 팝업이었다. 그러면 남은 칸을 보려면 화면을 열어야 하고,
**한 개만 더와 지금 나가자를 저울질하는 순간이 화면 밖으로 밀려난다.**

지금은 격자가 화면 우하단에 계속 떠 있다. 평소에는 반투명하게 보기만 하고 이동을 막지 않는다.
I를 누르면 정리 모드가 되어 격자가 진해지고, 커서가 풀리고, 그때만 끌어서 옮기거나 버릴 수 있다.

정리 모드에서 이동을 막는 방법이 문제였다. 팝업이 아니므로 `SWPopupManager`의 팝업 개수로는 알 수 없다.
UI 쪽에 상태를 두고 `PlayerInputReader`가 그것을 보게 하면 참조 방향이 거꾸로 선다.
그래서 **`PlayerInputReader`에 `SetUiFocus(bool)`를 두고 UI가 그것을 켜고 끄게 했다.**
입력을 막고 커서를 푸는 책임은 원래 그 컴포넌트에 있었고, UI는 Backrooms를 참조해도 되는 방향이다.
새 전역 상태를 만들지 않았다.

격자로 보이게 하려고 칸을 2픽셀씩 띄웠다. 그 틈이 격자선 역할을 해서 선을 따로 그리지 않아도 된다.

### 10.12 팝업 컨트롤러는 하나다

옵션 팝업에 `OptionsPopupController`, 가방에 `InventoryPopupController`를 만들어 두고 있었다.
둘이 하는 일은 키를 읽어 팝업을 열고 닫는 것으로 완전히 같고, 다른 것은 키와 프리팹뿐이었다.
이대로면 팝업이 늘어날 때마다 같은 코드가 하나씩 늘어난다.

`PopupHotkeyController` 하나로 합쳤다. 키와 팝업 프리팹의 짝을 목록으로 받는다.
지금은 ESC → 옵션 하나뿐이지만, 다음 팝업은 인스펙터에서 줄 하나 추가하면 끝난다.

**직렬화 함정 하나를 여기서 밟았다.** 에디터 스크립트로 키를 넣을 때
`SerializedProperty.enumValueIndex`에 `(int)Key.Escape`를 넣었는데, `enumValueIndex`는
열거형 값이 아니라 **열거형 정의 목록에서의 순번**이다. `Key.Escape`는 값 60, 순번 58이라
실제로는 값 57짜리 엉뚱한 키가 저장되어 ESC가 먹지 않았다. `intValue`로 넣어야 한다.
`Key.I`는 값과 순번이 우연히 같아 멀쩡히 동작해서 더 헷갈렸다.

### 10.13 관리 화면에 들어가는 문을 만들었다

지금까지 백룸에 들어가는 방법은 디버그 콘솔의 `backrooms.enter`뿐이었다.
들어가는 문이 콘솔에만 있으면 **하루가 어떻게 도는지를 개발자만 볼 수 있다.**
외부 테스터에게 콘솔 명령을 알려 주고 시작하게 할 수는 없다.

`HomeScreen`이 오늘 상태(날짜·남은 방송 시간·후원금·시청자·이상물체)를 보여 주고
백룸 탐험 버튼을 놓는다. 남은 방송 시간이 모자라면 버튼이 꺼지고 이유가 적힌다.
활동이 늘어나면 이 화면이 활동 목록을 놓는 자리가 된다.

**하루를 넘기는 것은 아직 버튼이 아니다.** 방송 시간을 다 쓰면 디버그 콘솔의 `state.nextday`를 써야 한다.
하루 마감에 무엇이 걸릴지(유지비·구독자 이탈·컨디션 회복)가 아직 정해지지 않았고,
지금 버튼만 붙이면 그 자리를 미리 굳히게 되기 때문이다. 화면 아래에 그렇게 적어 두었다.

### 10.14 UI는 TMP가 아니라 legacy Text로 맞췄다

`Assets/07_Fonts/TMP` 폴더가 비어 있다. TMP를 쓰려면 한글 폰트 에셋을 먼저 구워야 하는데,
그건 진짜 폰트를 정한 뒤에 할 일이다. 지금 구우면 폰트를 바꿀 때 다시 구워야 한다.

기존 옵션 팝업이 이미 legacy `Text`를 쓰고 있어 그쪽에 맞췄다.
색·크기·패널 색도 옵션 팝업에서 그대로 가져왔다(패널 `0.13/0.13/0.15`, 글자 `0.92`, 제목 34, 버튼 24).
폰트를 정하고 나면 갈아 끼울 자리는 글상자 여덟 개뿐이다.

## 11. 구조 정리와 확인 도구 — 2026.08.28

Phase 4의 구현이 끝난 뒤, 쌓아 두었던 구조 문제를 한 번에 정리했다.
새 기능을 더한 것이 아니라 **같은 것이 여러 벌 있거나, 한 오브젝트가 너무 많은 것을 들고 있거나,
데이터를 만들기가 번거로운 자리**를 없앤 작업이다.

### 11.1 팝업은 프리팹이 아니라 카탈로그 키로 부른다

`PopupHotkeyController`가 팝업 프리팹을 직접 들고 있었다. 그러면 팝업을 여는 쪽마다
프리팹 참조가 하나씩 생기고, 씬을 옮길 때마다 그 참조를 다시 이어야 한다.

SWUtils에 `SWPopupCatalog`가 이미 있었다. 키와 프리팹을 짝지어 두면 `SWPopupManager`가
`Show("options")`처럼 키로 열어 준다. 카탈로그 에셋을 만들고 팝업 매니저에 연결했다.

```
Assets/02_Res/UI/PopupCatalog.asset
  options    → OptionsPopup
  settlement → SettlementPopup
```

키를 문자열로 직접 적으면 오타가 실행할 때까지 드러나지 않으므로 `PopupKeys` 상수로 모았다.

이 덕분에 `SettlementPopupController`를 지울 수 있었다. 정산 화면은 키가 아니라
"돌아왔을 때 결과가 있으면" 뜨는 것이라 단축키 컨트롤러에 넣을 수 없었는데,
그 판단은 원래 관리 화면의 일이므로 `HomeScreen`으로 옮겼다.
`HomeScreen`은 이미 관리 화면 전체를 맡고 있어 컨트롤러가 하나 줄었다.

### 11.2 전역 객체는 씬마다 두고 싱글톤이 정리하게 한다

`SWPopupManager`, `EventSystem`, `PopupHotkeyController`, `GameManager`가 씬마다 하나씩 있었다.
`SWSingleton`이 중복을 지우기는 하지만, **어느 씬의 것이 진짜인지 알 수 없고 설정이 갈라진다.**
그렇다고 첫 씬에만 두면 개발 중에 백룸 씬을 바로 열어 실행할 수 없다.

**처음에는 Resources로 갔다가 같은 날 되돌렸다.** 전역 객체를 프리팹 하나로 묶어
`Assets/04_Prefabs/Resources/GameBootstrap.prefab`에 두고, `GameBootstrapper`가
`[RuntimeInitializeOnLoadMethod]`로 씬이 열리기 전에 만드는 방식이었다.
한 벌만 생기는 것은 맞았지만 대가가 컸다. **하이어라키에 아무것도 보이지 않아
지금 무엇이 도는지 코드를 열어야 알 수 있고**, 프리팹을 꺼진 채로 저장해 두어야 하고
(켜진 채로 복제하면 묶음을 풀기 전에 Awake가 돌아 `DontDestroyOnLoad only works for
root GameObjects` 경고가 난다), 자식을 루트로 떼어 내는 절차가 따로 필요했다.
그 전부가 `Resources` 폴더 하나를 유지하기 위한 비용이었다.

**지금은 씬 셋에 그대로 놓는다.** 넷 다 씬을 넘어 살아남아야 하는 것들이므로
`SWSingleton`을 붙여 두면 먼저 만들어진 것만 남고 뒤에 열린 씬의 것은 스스로 사라진다.
이 참에 `PopupHotkeyController`도 `SWMonoBehaviour`에서 `SWSingleton`으로 바꿨다.
`EventSystem`은 싱글톤이 아니지만 씬과 함께 사라지므로 겹치지 않는다.

| 씬 | 씬 고유 루트 | 전역 루트 (셋 다 같다) |
|---|---|---|
| HomeScene | Main Camera, Directional Light, HomeScreen | GameManager, SWPopupManager, EventSystem, PopupHotkeyController |
| BackroomsScene | MapBuilder, GlobalVolume, Player, BackroomsHud | 〃 |
| LoadingScene | Main Camera, LoadingRunner | 〃 |

**설정이 갈라지는 문제는 프리팹으로 막는다.** `SWPopupManager`는
`Assets/04_Prefabs/Manager/SWPopupManager.prefab` 인스턴스라 세 씬이 같은 것을 본다.
`GameManager`와 `PopupHotkeyController`는 인스펙터에 값이 한두 줄뿐이라 아직 묶지 않았다.
**늘어나면 그때 프리팹으로 만든다.**

`Resources`는 이제 어디에서도 쓰지 않는다. 씬을 거치지 않고 코드에서 불러올 자리가
필요할 때만 쓰는 곳인데, 그 필요 자체가 없어졌다.

### 11.3 MapBuilder 한 오브젝트에 아홉 개가 붙어 있었다

맵 조립, 배치, NavMesh, 몬스터, 측정이 전부 `MapBuilder` 하나에 붙어 있었다.
인스펙터를 열면 무엇이 무엇인지 구분되지 않고, 하나를 끄려면 목록을 훑어야 했다.

```
MapBuilder        BackroomsMapBuilder · NavMeshSurface · BackroomsNavMeshBaker · BackroomsSoakRunner
├─ Population     BackroomsMapPopulator · BackroomsBrokenLampPlacer · BackroomsLandmarkPlacer
├─ Anomalies      BackroomsAnomalyPlacer
├─ Monsters       MonsterSpawner
└─ Testing        BackroomsSceneView
```

**전부 옮길 수는 없었다.** `NavMeshSurface`는 `CollectObjects.Children`으로 굽기 때문에
타일이 놓이는 오브젝트에 있어야 하고, `BackroomsSoakRunner`는 같은 오브젝트의 맵 조립 컴포넌트를
`GetComponent`로 찾는다. 이 둘은 자리 때문이 아니라 **기능 때문에** 거기 있어야 한다.
옮기려다 `RequireComponent`가 맵 조립 컴포넌트를 하나 더 만들어 두 번 생성될 뻔했고, 되돌렸다.

컴포넌트를 옮기면 그것을 가리키던 참조가 끊어진다.
`PlayerPickupInteractor.anomalyPlacer` 하나가 그랬고 다시 이었다.

### 11.4 이상물체에 아이콘과 모델을 붙였다

정의에 `icon`(스프라이트)과 `worldPrefab`(모델)을 더했다. 둘 다 **비워 둘 수 있다.**

- 아이콘이 있으면 인벤토리 칸에 아이콘을 그리고 이름을 뺀다. 좁은 칸에서 둘은 서로를 가린다
- 아이콘이 없으면 색과 이름을 그린다
- 모델이 있으면 상자 대신 붙이고 격자 형태에 맞게 한 축으로만 줄인다. 가로세로를 따로 늘이면 찌그러진다
- 모델이 없으면 형태와 색으로 만든 상자를 쓴다

줍기 판정에 쓰는 충돌 범위는 어느 쪽이든 격자 형태를 따른다. 종류마다 조준 느낌이 달라지지 않게 하려는 것이다.
아트가 없는 종류를 먼저 만들어 배치 규칙만 확인할 수 있고, 나중에 채워 넣어도 코드는 그대로다.

**프리팹을 코드로 고칠 때는 `PrefabUtility.LoadPrefabContents`를 써야 한다.**
`AssetDatabase.LoadAssetAtPath`로 얻은 프리팹 루트에 자식을 붙이면 오브젝트는 저장되지만
그것을 가리키는 참조는 저장되지 않는다. 아이콘 자리를 만들고도 연결이 비어 있어
아이콘도 이름도 보이지 않는 상태를 한 번 만들었다.

### 11.5 미로를 눈으로 보는 도구

백룸은 천장이 덮여 있고 어두워서 씬 창에서 위에서 내려다봐도 미로 모양이 보이지 않는다.
생성 결과가 이상해도 시드와 통계 숫자만 보고 짐작해야 했다.

`BackroomsSceneView`가 두 가지를 한다. 인스펙터 버튼과 디버그 명령 양쪽으로 부를 수 있다.

```
■ 천장 감추기      타일 안 Ceiling을 끈다                      view.ceiling
■ 밝게 보기        후처리 노출을 올린다                        view.bright
■ 미로 살펴보기    위 둘을 한 번에                             view.maze
```

**밝게 하는 데 빛을 더하지 않는다.** 벽과 바닥은 라이트맵을 구워 둔 정적 오브젝트라
실시간 빛을 더해도 거의 밝아지지 않고, 실행 중 실시간 라이트는 손전등 하나뿐이라는
규칙(8.2절)도 지켜야 한다. 대신 실행 중에만 있는 볼륨을 하나 얹어 노출을 올린다.
이미 그려진 그림을 밝히는 것이라 조명 구성을 건드리지 않는다.
**성능을 잴 때는 꺼야 한다.** 후처리가 하나 더 얹혀 있기 때문이다.

인스턴스 메서드의 `[SWCommand]`는 자동으로 등록되지 않는다.
`SWDebugConsole.RegisterInstance(this)`를 Awake에서 불러야 콘솔이 찾는다.

### 11.6 이상물체를 만들고 관리하는 창

정의를 하나 만들려면 에셋 생성, 코드명, 형태, 아이콘·모델 연결, 데이터베이스 등록까지
여섯 군데를 손대야 했다. 종류를 늘릴 때마다 반복하면 하나쯤 빠뜨리고,
빠뜨린 것은 실행해 봐야 드러난다.

`Project R > 데이터 > 이상물체` 창이 그것을 한 번에 처리한다.

**처음에는 입력란을 죽 늘어놓은 창이었다.** 값을 다 적고 버튼을 누르면 에셋이 생기는 식인데,
정의에 필드를 더할 때마다 창의 입력란도 같이 고쳐야 했고 이미 만든 것을 다시 열어 볼 수 없었다.
지금은 SWUtils의 `Stat System Editor`와 같은 배치다. 왼쪽에 만들어 둔 정의를 늘어놓고,
오른쪽에는 고른 것의 인스펙터를 그대로 띄운다. **인스펙터를 띄우므로 정의에 필드를 더해도
창은 고칠 것이 없다.** 만들기는 빈 에셋을 만들어 데이터베이스에 등록하는 데까지만 하고,
값은 오른쪽에서 채운다.

형태는 숫자만 보면 2x3과 3x2를 자주 뒤바꾸므로 오른쪽 위에 격자로 그려 보여 준다.
나머지는 **눈으로 보이지 않는 것**만 목록 아래에 알린다.

| 알림 | 그대로 두면 |
|---|---|
| 코드명 중복 | `DefinitionId`로 찾을 때 엉뚱한 것이 나온다 |
| 데이터베이스 미등록 | 만들어 두고도 백룸에 나오지 않는다 (한 번에 등록하는 버튼을 함께 띄운다) |
| 아이콘·모델 없음 | 형태대로 만든 상자가 대신 나온다(11.4절) |

**창은 SWTools 아래에 두지 않는다.** SWTools는 SWUtils의 자리이고,
이 프로젝트의 도구는 `Project R` 아래에 모은다. 타일 조명 조절 창(11.5절)도 그 아래에 있다.
생성 경로와 목록 표시 방식은 EditorPrefs에 남겨 창을 닫았다 열어도 그대로다.

### 11.7 음소거해도 소리가 들리던 이유

`GameSettings`가 음량을 `SWAudioManager.SetMasterVolume`으로만 반영하고 있었다.
그런데 발소리·형광등 웅웅거림·몬스터 소리는 각 컴포넌트가 **자기 `AudioSource`로 직접** 재생한다(8.4절).
매니저를 거치지 않으므로 매니저의 마스터 음량을 0으로 내려도 그대로 들렸다.

`AudioListener.volume`으로 바꿨다. 이것만이 재생 경로와 상관없이 모든 소리에 걸린다.
매니저 쪽 음량은 건드리지 않는다. 함께 내리면 매니저를 거친 소리만 두 번 깎인다.

### 11.8 SWUtils에서 더 쓸 것을 찾아봤다

| 도구 | 결정 |
|---|---|
| `SWPopupCatalog` | **씀**. 팝업을 키로 부르게 되어 프리팹 참조가 사라졌다(11.1절) |
| `SWDebugConsole.RegisterInstance` | **씀**. 인스턴스 메서드 명령을 등록한다(11.5절) |
| `SWPool` · `SWPoolCatalog` | **안 씀**. 지금 규모에서 이득이 없다 |

풀링을 안 쓰기로 한 근거는 이렇다. 타일은 3.2절에서 이미 미적용으로 정했다.
이상물체 상자는 맵당 아홉 개뿐이고 맵을 다시 만들 때만 사라진다.
인벤토리 물건 표시는 가방을 고칠 때마다 다시 만들지만 최대 24개이고,
그마저도 사람이 끌어 놓는 속도로만 일어난다.
**측정해서 문제가 드러난 적이 없으므로 지금 넣지 않는다.** 넣으면 풀을 비우는 자리가 새로 생긴다.

### 13.2 이상물체를 6종으로 늘렸다 — 체크리스트 3.1절

3종 전부가 등급 Common에 후원금 120 · 시청자 15로 같았다.
값이 같으면 Q4의 "좋은 물건을 주웠을 때 기쁜가"와 "무엇을 버릴지 고민이 생기는가"를
물어볼 대상 자체가 없다. 형태도 셋뿐이라 격자에 넣는 재미가 나오지 않는다.

| 형태 | 칸 | 표시명 | 등급 | 후원금 | 시청자 | 칸당 후원금 |
|---|---|---|---|---|---|---|
| 1x1 | 1 | 폭주하는 어뷰저 | 흔함 | 60 | 8 | 60 |
| 2x1 | 2 | 저주받은 USB | 드묾 | 220 | 45 | 110 |
| 1x3 | 3 | 음소거된 마이크 | 드묾 | 330 | 55 | 110 |
| 2x2 | 4 | 악플 메일박스 | 흔함 | 200 | 20 | 50 |
| 1x4 | 4 | 부러진 조명 스탠드 | 흔함 | 160 | 14 | 40 |
| 2x3 | 6 | 먹통 송출 장비 | 특별 | 960 | 150 | 160 |

수치를 정한 규칙은 하나다. **칸당 후원금이 등급을 따라간다.**
흔함은 40~60, 드묾은 110, 특별은 160이다. 그래서 이런 일이 벌어진다.

- 2x3 특별은 가방 24칸 중 6칸을 먹지만 칸당 값이 가장 높아 무조건 챙기게 된다 → "기쁜가"
- 2x2와 1x4 흔함은 4칸을 먹으면서 칸당 값이 가장 낮다 → 특별이 나왔을 때 **가장 먼저 버릴 후보**가 된다
- 1x1은 값이 작지만 어디든 끼워 넣을 수 있어 자리 메우기로 쓰인다

등급 자체는 여전히 표시 전용이다. 수치를 만들지 않는다는 `EAnomalyGrade`의 규칙은 그대로다.

기존 3종의 설명이 전부 USB 설명 복사본이었던 것도 함께 고쳤다.
테스터가 읽는 문장이므로 셋이 같은 문장을 달고 있으면 종류를 늘린 의미가 절반 사라진다.

**에디터 창 대신 CLI로 만들었다.** 체크리스트 3.1절은 `Project R > 데이터 > 이상물체` 창으로
만들라고 적어 두었는데, 창은 사람이 눌러야 하는 GUI라 여섯 개를 한 번에 맞추기 어렵다.
대신 `AnomalyMakerWindow.CreateDefinition`이 밟는 경로를 그대로 따랐다 —
`SerializedObject`로 필드를 채우고 `SWIODatabase.Add`로 등록한다.
`Add`가 id 0을 보고 다음 번호를 붙여 주는 것까지 같아서, 결과물은 창으로 만든 것과 구별되지 않는다.
id는 1~6으로 이어졌고 데이터베이스 등록 수는 6이다.
`.asset` YAML을 직접 쓰지 않았다. 에디터가 떠 있는 동안 파일을 직접 고치면 에디터가 모른다.

### 13.3 등장 가중치는 넣지 않는다 — 2026.08.29 결정

`BackroomsAnomalyPlacer`는 데이터베이스에서 균등 추첨한다.
그래서 2x3 특별이 1x1 흔함과 같은 확률로 나온다. 한 판에 특별이 여러 개 나오면
특별이 특별하지 않아진다.

**그래도 지금은 넣지 않는다.** 가중치를 넣으려면 정의에 필드를 더하고 배치기를 고쳐야 하는데,
그것은 보상 곡선을 건드리는 설계 변경이고 M0에 남은 작업은 판정뿐이다.
체크리스트 3.4절이 Q4 경계의 조치로 "인벤토리 격자 규칙 또는 보상 곡선 조정"을 이미 적어 두었다.
**Q4에서 "좋은 물건을 주웠을 때 기쁜가"가 미달로 나오면 그때 이것부터 넣는다.**
미리 넣으면 균등 추첨이 실제로 문제였는지를 영영 알 수 없다.

체크리스트 3.1절에 `◈`로 남겨 두었다.

### 13.4 CursedUSB의 코드명 불일치는 그대로 둔다 — 2026.08.29 결정

`Anomaly_CursedUSB`만 코드명이 `Anomaly_CursedUSB`이고, 나머지 다섯은 접두사가 없다
(`HateMailBox`, `LightAbuser`, ...). 창의 `CreateDefinition`이 코드명을 파일 이름으로 채우는데
나중에 손으로 지운 것이 둘, 안 지운 것이 하나 남은 모양이다.

**고치지 않는다.** 코드명은 `AnomalyDefinition.DefinitionId`가 되고 `ItemInstance`가 그 값을 들고
저장 파일에 들어간다. 지금 바꾸면 기존 저장 파일의 아이템이 정의를 못 찾는다.
프로토타입 저장 파일은 버려도 되지만, 이 상태로 외부 테스터에게 빌드를 넘기고 나면
그다음부터는 못 바꾼다. **M2에서 저장 데이터에 버전 필드와 마이그레이션 경로가 생길 때 함께 고친다.**

### 13.5 M0 관문 판정을 개발 후반으로 미룬다 — 2026.08.29 결정

체크리스트가 "관문을 통과하지 않은 채 다음 마일스톤의 구현을 시작하지 않는다"고 못 박아 두었고,
예외를 두려면 **기준을 낮추지 말고 시점만 옮기되 감수한 위험을 여기에 적으라고** 되어 있다.
v0.1에서 실제로 그렇게 했고(8.10절) 그 대가로 미판정이 셋 쌓였다.

**이번에도 예외를 둔다.** M0 관문 넷의 판정을 개발이 거의 끝나갈 무렵으로 미루고 M1을 먼저 쌓는다.

미룬 것은 판정 시점뿐이고 **판정 기준은 그대로다.** 통과 조건도, 판정하는 사람도,
미달 시 조치도 체크리스트 3.4절·3.5절 그대로 남는다. 시트(`프로젝트R_M0관문_판정시트.md`)도
채워질 때까지 지우지 않는다.

```
□ 개발자 자체 확인    몬스터와 이상물체가 다 들어간 백룸을 한 번 끝까지 돌아 본다
□ 수치 조정          어긋난 것만 인스펙터와 Blackboard Override로 고친다
□ 빌드 갱신          Builds/Win64는 08-26 빌드 그대로다
□ 관문 판정          Q1 실기 측정 · Q2 · Q3 · Q4 외부 테스터 3~5명
```

#### 감수하는 위험

미판정이 넷에서 줄지 않은 채로 M1이 그 위에 쌓인다. 질문마다 무게가 다르다.

| 질문 | 실패했을 때 M1 작업물에 미치는 영향 | 무게 |
|---|---|---|
| **Q2 공포** | **아트 방향·공간 규모·사운드 전면 재설계.** 백룸 위에 얹은 방송 겹침 UI, 방송 시작 연출, 컨디션의 3D 개입이 전부 다시 맞춰야 하는 대상이 된다 | **최상** |
| Q1 성능 | 생성 방식 전환(WFC / BSP). 맵 생성부만 갈리므로 M1은 대체로 살아남는다. 다만 겹침 UI가 프레임을 더 먹으므로 실기 여유가 줄어든 상태에서 판정하게 된다 | 상 |
| Q4 수집 | `ILossPolicy` 구현체 교체로 끝난다. 그러려고 갈라 둔 것이다(10.8절) | 중 |
| Q3 실력감 | 소리 설계와 순환로 보정. 몬스터와 생성부에 갇힌다 | 중 |

**Q2 하나가 나머지 셋을 합친 것보다 무겁다.** 다른 셋은 그 시스템만 고치면 되지만
Q2는 그 위에 쌓은 것을 함께 끌고 간다. M1에서 백룸 화면에 붙는 것
— 시청자 수 · 채팅창 · 2D 아바타 · 후원 알림 — 이 전부 Q2가 실패하면 다시 맞춰야 하는 대상이다.

#### 그래서 M1을 이 순서로 쌓는다

위험을 줄이는 유일한 방법은 **Q2에 휩쓸리지 않는 것부터 만드는 것**이다.

```
1. 데이터 계층      저장 분리 · 컨디션 계산 · 유지비 · 이탈 · 시청자/후원 계산
                   전부 순수 로직이고 EditMode 테스트로 검증된다. Q2와 무관하다
2. 관리 화면        마을 · 집 · 하루 마감. 2D이고 백룸 밖이다. Q2와 무관하다
3. 성장             업그레이드. 가방 용량부터 한다
4. 백룸에 붙는 것    컨디션의 3D 개입 · 방송 겹침 UI · 방송 시작 연출
                   ← 여기가 Q2에 휩쓸리는 구간이다. 마지막에 둔다
```

4번을 마지막에 두면, Q2가 실패해도 1~3번은 살아남는다.
**4번을 시작하기 전에 판정을 한 번 물어보는 것이 가장 싸게 막는 방법이다.**

판정을 실제로 돌릴 수 있게 측정 절차와 관찰 시트를 `프로젝트R_M0관문_판정시트.md`에 만들어 두었다.
**결과는 그 문서가 아니라 이 문서 14장에 적는다.** 시트는 한 번 쓰고 버리는 작업지이고,
판정 결과는 남아야 하는 기록이다.

## 15. M1 — 1일 시연판 · 데이터 계층 (2026.08.29)

13.5절에서 정한 순서대로 Q2에 휩쓸리지 않는 것부터 쌓았다.
여기까지는 전부 순수 로직이고 EditMode 테스트로 검증된다. 화면은 아직 하나도 만들지 않았다.

### 15.1 저장 데이터를 채널과 스트리머로 갈랐다 — 체크리스트 4.5절

기획서 11.2절과 12.3절이 요구한 분리다. **나중에 하는 것이 불가능한 종류의 작업이다.**
배포한 뒤에는 저장 파일 구조를 바꿀 수 없고, 그러면 DLC 스트리머를 추가할 수 없다.

```
GameState                       저장 파일의 최상위. 구조 번호를 들고 있다
├─ saveVersion
├─ activeStreamerId
├─ ChannelProgress              날짜 · 방송 시간 · 후원금 · 오늘 활동 횟수
└─ StreamerProgress[]           시청자 · 컨디션 · 이상물체
```

**바깥으로 보이는 프로퍼티는 나누기 전과 같다.** `State.Donation`, `State.ViewerCount`,
`State.Condition`, `State.Items`가 그대로 있고 안쪽에서 알맞은 곳으로 넘긴다.
그래서 `HomeScreen`, `SettlementPopup`, 디버그 명령은 한 줄도 고치지 않았다.
스트리머가 여럿이 되어도 부르는 코드가 바뀌지 않는다.

무엇을 어디에 둘지는 기획서 11.2절을 그대로 따랐다. 날짜와 자금은 채널이다.
하루에 방송하는 스트리머가 한 명이므로 오늘 남은 방송 시간도 채널 쪽에 두었다.
스트리머마다 날짜가 따로 흐르면 유지비를 어느 날짜로 물릴지 정할 수 없다.

#### 구조 번호에 초기값을 주지 않는다

`saveVersion` 필드에 `= CurrentSaveVersion`을 붙이고 싶어지는데, **붙이면 안 된다.**
`JsonUtility.FromJson`은 기본 생성자를 거치므로 필드 초기값이 살아 있고,
그러면 그 필드가 없던 구버전 저장 파일이 최신 버전으로 읽힌다.
구버전인 것을 알아볼 방법이 영영 사라진다.

새 진행을 시작할 때만 `MarkAsCurrentVersion()`으로 넣는다.
`GameStateTests.생성자만으로는_구조_번호가_붙지_않는다`가 이것을 못 박는다.
불러올 때 번호가 다르면 읽지 않고 새 진행으로 시작한다. 구버전을 새 구조로 옮기는 경로는 M2다.

#### 스트리머 식별자는 이 계층이 모른다

`GameState`는 어떤 스트리머 식별자도 알지 못한다. 부르는 쪽이 넘겨 주는 것만 받는다.
지금은 `GameManager`의 인스펙터 필드(`defaultStreamerId`)가 그 자리이고,
스트리머 정의 에셋이 생기는 M2에서 거기로 옮긴다.
기획서 12.3절이 "출시 스트리머 1명도 여러 명 중 하나인 것처럼 짜라"고 한 것이 이 뜻이다.

### 15.2 컨디션에는 SWStat을 쓰지 않고 스탯에는 쓴다 — 2026.08.29 결정 (재검토 완료)

체크리스트 4.2절이 "SWStat / SWStats로 갈아 끼울지 판단"하라고 했다.
처음에는 표면만 보고 판단했다가 소스를 다시 읽고 정리했다.

#### 먼저 정정 — "원본 에셋 오염 위험"은 틀렸다

처음에 든 사유 중 "상한을 바꾸면 원본 에셋을 건드릴 위험이 있다"는 **사실이 아니다.**
`SWStat.CreateRuntimeClone()`이 `Instantiate`로 복제본을 만들고, `OriginStat`으로 원본을 가리키며,
`SWStats.OnDestroy`가 복제본을 `Destroy`한다. 원본 에셋은 건드려지지 않는다.
`UpgradeStatTests.런타임_복제본은_원본_에셋을_건드리지_않는다`가 이것을 못 박아 두었다.

#### 스탯 네 축에는 쓴다

필요한 것이 이미 다 들어 있다. 직접 만들면 같은 것을 다시 짜게 된다(체크리스트 1.2절).

| 필요한 것 | `SWStat`이 이미 주는 것 |
|---|---|
| 초기값 + 성장 + 장비 + 업그레이드 합산 | `Value = Clamp(DefaultValue + BonusValue, Min, Max)` |
| **장비를 벗으면 그 보너스만 사라짐** | `RemoveBonusValue(key)` — 출처별 일괄 제거 |
| 같은 출처의 여러 효과 구분 | `SetBonusValue(key, subKey, value)` |
| 스탯 상한선 (기획서 8.4절) | `MaxValue` |
| 값이 바뀔 때 화면 갱신 | `OnValueChanged` · `OnValueMax` · `OnValueMin` |
| 스트리머마다 다른 초기 스탯 (기획서 12.4절) | `SWStatOverride.overrideDefaultValue` |
| 스탯을 늘릴 때 코드를 안 고침 | 에셋만 추가 · `SWStatSystemWindow` |

**결정적인 것은 `RemoveBonusValue(key)`다.** 손전등을 바꿨을 때 이전 손전등 몫만 걷어내는 일을
직접 짜면 결국 출처별 사전을 다시 만들게 된다.

#### 컨디션에는 쓰지 않는다

| 이유 | 내용 |
|---|---|
| 쓰지 않는 기능 | `SWStat`의 본체는 **출처별 보너스**인데 컨디션은 출처가 회복 활동 하나뿐이다 |
| 저장 | `ConditionState`는 `GameState` 안에 있어 공짜로 저장된다. `SWStats`는 `MonoBehaviour`라 씬에 살고, 저장할 때마다 동기화 코드를 새로 떠안는다 |
| 계층 | 데이터 계층이 시스템을 참조하지 않는다는 규칙(1.6절)에 걸린다 |

**둘의 성격이 실제로 다르다.** 컨디션은 하루 동안 오르내리는 *상태*이고,
스탯은 여러 출처가 붙었다 떨어지며 합쳐지는 *계산*이다.
`SWStat`은 후자를 위한 도구라 전자에 쓰면 기능의 대부분을 안 쓰면서 직렬화 문제만 떠안는다.

#### 피로도가 상한을 눌러 내리는 계산

```
상한 = 100 − (100 − 40) × 피로도 / 100

피로도   0 →  상한 100
피로도  50 →  상한  70
피로도 100 →  상한  40   ← 하한선
```

곡선이 아니라 직선을 쓴 이유는 플레이어가 "피로도를 절반 풀면 절반 돌아온다"고 예상할 수 있어야
휴방을 며칠 할지 스스로 계산하기 때문이다.

하한선 40은 설계 원칙 4번이다. 0이면 피로도가 최대일 때 아무것도 회복할 수 없어
실패가 실패를 부른다.

**피로도를 먼저 반영하고 나머지 셋을 자른다.** 순서를 바꾸면 같은 호출에서
피로도가 오르고 수면도 오를 때 새 상한이 걸리지 않는다.
`같은_호출에서_오른_피로도가_그_회복분에도_걸린다`가 이 실수를 잡는다.

### 15.3 하루 마감 — 유지비와 구독자 이탈 — 체크리스트 4.1절

기획서 8.3절이 유지비에 맡긴 역할은 하나다. **성장을 멈추면 후퇴한다.**
엔드리스에는 마감 기한이 없으므로 유지비가 그 압박을 대신한다.

```
유지비   = 고정 지출 + 시청자 × 계수        채널이 클수록 유지가 어렵다
이탈     = 시청자 × 이탈률(쉬었나 방송했나)   비율이라 큰 채널이 더 많이 빠진다
방송 시간 = 기본 + 규모 보너스 − 실패 벌점    하한선 아래로는 안 내려간다
```

이탈을 **인원이 아니라 비율로** 뺀 것이 핵심이다. 고정 인원으로 빼면 대형 채널에서는
이탈이 없는 것과 같아져 "채널이 클수록 유지 난이도 상승"이 성립하지 않는다.
반대로 올림을 쓴 이유는 시청자가 적을 때 이탈이 영영 0이 되지 않게 하기 위해서다.

#### float 0.1은 0.1이 아니다 — 버그 1건

`(double)0.1f`는 0.100000001490116이다. 시청자 1000명에 이탈률 10%를 곱하면
100.0000015가 나오고, **올림하면 101이 된다.** 테스트가 이것을 잡았다.

`decimal`로 옮겨 곱하도록 고쳤다. `float`에서 `decimal`로의 변환은 유효자릿수만 취하므로
0.1이 그대로 0.1로 옮겨진다. 올림이 걸린 계산에서는 이 차이가 그대로 결과가 된다.

**측정하지 않았으면 넘어갔을 항목이다.** 화면에서는 101명이 빠진 것과 100명이 빠진 것을
구분할 방법이 없다.

#### 오늘 방송했는지를 저장하는 쪽에 둔다

"쉬면 감소"를 판단하려면 오늘 활동을 했는지를 알아야 한다.
매니저가 들고 있으면 활동 도중 강제 종료했을 때 사라지므로 `ChannelProgress`에 두었다.
저장에서 되돌아왔을 때 오늘 이미 방송한 것이 그대로 남아 있어야 한다.

#### 아직 안 된 것 — 재미없는 방송도 감소

기획서 8.3절은 "쉬면 감소, **재미없는 방송도 감소**"라고 적혀 있다.
지금은 앞의 절반만 되어 있다. 방송 재미는 `BroadcastMeter`가 들고 있는데
하루 마감까지 넘어오지 않는다. 체크리스트 4.1절에 `◐`로 남겨 두었다.

### 15.4 ProjectR.Broadcast를 갈랐다 — 체크리스트 1.7절

**백룸과 방송은 서로를 참조하지 않는다.** 문서에 적힌 유일한 상호 금지 규칙이고,
asmdef로 막아 컴파일러가 지키게 했다. 규칙으로만 두면 지켜지지 않는다.
백룸 안에서 시청자 수를 알고 싶어지는 순간이 반드시 오고, 같은 어셈블리라면 `using` 한 줄이면 된다.

가는 길과 오는 길을 따로 만들었다.

```
백룸 ──▶ 방송   상황과 순간을 이벤트로 알린다
                 이벤트 타입은 ProjectR.Activity에 둔다. 둘 다 참조하는 가장 아래 자리다
                 상황: BackroomsBroadcastReporter가 몬스터 모드와 앉기를 한 군데서 옮긴다
                 순간: 줍기와 탈출이 벌어진 자리에서 각자 알린다

방송 ──▶ 정산   ActivitySettlingEvent
                 매니저가 결과 객체를 들고 와 "더할 것 있으면 더하라"고 알린다
                 방송은 더하기만 하고 덮어쓰지 않는다
```

**오는 길이 이 설계의 어려운 쪽이었다.** 시청자와 후원을 방송이 굴리는데
그 값이 활동 결과에 들어가야 한다. 백룸이 방송에게 물어보게 하면 금지된 방향이 생긴다.
활동 쪽이 결과를 들고 와서 알리면 그 방향이 생기지 않는다.

상황(`EBroadcastState`)과 순간(`EBroadcastMoment`)을 나눈 이유는 쓰임이 다르기 때문이다.
상황은 지속되고 시청자·후원의 흐름을 정한다. 순간은 한 번 벌어지고 채팅을 부른다.
쫓기는 것은 상황이고, 처음 본 순간은 순간이다.

#### 굴리는 시간은 실제 시간이다

활동 비용 60분은 **하루치 행동력에서 깎이는 값이지 탐험 중에 흐르는 시계가 아니다.**
백룸 안에는 제한 시간이 없다(10.9절). 그래서 `BroadcastSettings`의 분당 수치는 실제 1분 기준이다.
이것을 헷갈리면 10분짜리 탐험에서 60분치 후원이 들어온다.

#### 소수점을 잘라 버리면 시청자가 영영 안 는다

분당 2명씩 들어오기로 한 유입은 초당 0.033명이다. 매 틱 `(int)`로 자르면 언제나 0이라
시청자가 영원히 늘지 않는다. **화면에서는 "왜 안 늘지"로만 보이고 원인이 드러나지 않는다.**
남는 몫을 들고 있도록 만들었고, `잘게_나눠_굴려도_한_번에_굴린_것과_같다`가 이것을 지킨다.

후원은 시청자를 늘리기 **전에** 센다. 순서를 바꾸면 그 분에 아직 들어오지도 않은 사람이 후원을 낸다.

#### 방송 진행자는 전역 싱글톤이 아니다

`BroadcastDirector`는 활동이 도는 씬에 하나 놓는 평범한 컴포넌트다.
계획한 전역 객체 넷(11.2절) 밖으로 나가지 않으려는 것이고, 방송은 활동 씬에서만 필요하다.
같은 씬의 화면이 인스펙터로 직접 물면 된다.

### 15.5 채팅은 태그와 템플릿 조합이다 — 체크리스트 4.3절

기획서 6.3절이 정한 방식 그대로다. 실행 중에 문장을 만들지 않는다.
비용이 없고, 오프라인에서 돌고, 스팀의 AI 사용 공개 신고 대상에서도 벗어난다.

`Assets/02_Res/Broadcast/ChatTemplateSet_Default.asset`에 태그 8종 · 문장 54개 · 닉네임 15개를 채웠다.

난수 생성기를 밖에서 받는다. 백룸이 시드를 저장해 두는 것과 같은 이유다.
같은 씨앗이면 같은 채팅이 나와야 재현할 수 있다.

**문장이 없는 태그를 받으면 빈 줄을 돌려준다.** 예외를 던지지 않는 이유는
아직 문장을 안 채운 태그 하나 때문에 방송이 멈추는 것이 더 나쁘기 때문이다.
채팅은 없어도 게임이 도는 요소다.

조용할 때도 침묵 태그로 한 줄씩 올린다. 아무 일도 없을 때 채팅이 멈추면
시청자가 사라진 것처럼 보인다. "흐름이 반응하는 느낌"은 조용할 때도 흘러야 만들어진다.

### 16.1 스탯 네 축

기획서 9.1절의 네 축 중 **셋만 스탯으로 만들었다.**

```

장비 Gear       가방 가로 · 가방 세로
```

**채널 축에 빈 카테고리를 만들지 않았다.** 비어 있는 자리를 만들어 두면

### 16.2 업그레이드는 값을 바꾸지 않고 보너스로 얹는다

```
저장되는 것   보유 업그레이드 식별자 목록뿐          StreamerProgress.UpgradeIds
저장 안 되는 것 보너스 값                            불러올 때 목록으로 다시 얹는다
```

값을 저장하지 않는 이유는 **나중에 효과량을 조정했을 때 이미 산 사람에게 옛 값이 남기 때문이다.**
목록만 저장하면 조정한 값이 모두에게 그대로 적용된다.

다시 얹을 때는 업그레이드 몫을 통째로 걷어내고 시작한다.
걷어내지 않으면 두 번 부를 때 두 배가 된다. 출처 키를 `"Upgrade"` 하나로 묶고
업그레이드 식별자를 세부 키로 쓰기 때문에 `RemoveBonusValue("Upgrade")` 한 번이면 된다.
장비가 얹을 보너스와도 섞이지 않는다.

첫 업그레이드는 가방 용량이다(기획서 7.6절 — 초반 성장 체감이 가장 크다).
세로만 늘린다. 가로를 늘리면 격자가 옆으로 자라 화면 우하단에 고정해 둔 자리를 밀어낸다.

```
기본      6 x 4 = 24칸
Backpack_01  +1  →  30칸   1,500
Backpack_02  +1  →  36칸   3,500   선행 01
Backpack_03  +1  →  42칸   7,000   선행 02
Backpack_04  +1  →  48칸  14,000   선행 03
```

비용이 약 두 배씩 오르는 것은 기획서 8.4절의 "업그레이드 비용은 완만한 지수"다.
`BackpackHeight` 스탯의 상한이 8이라 네 단계를 다 사면 정확히 상한에 닿는다.

**이 업그레이드는 수치판이 아니라 백룸 플레이 감각을 바꾼다.** `HomeScreen`이 탐험을 만들 때
스탯에서 가방 크기를 읽어 넘기므로, 산 다음 탐험에서 격자가 실제로 넓어진다.
설계 원칙 1번이 요구하는 것이 이것이다.

### 16.4 Unity CLI로 자산 참조를 넣을 때 — 함정 1건

`unity command eval`에서 `SerializedProperty.objectReferenceValue`에 **자산을 대입하면 조용히 무시된다.**
씬 오브젝트 참조는 들어가는데 자산 참조만 `fileID: 0`으로 저장된다.
예외도 경고도 없어서, 씬 파일을 열어 보기 전까지는 배선이 된 줄 안다.

실제로 이 함정에 한 번 빠졌다. 배선 스크립트는 "성공"을 찍었고, 플레이 모드에서야
가방 칸 수가 대체값(-1)으로 나와 드러났다.

**자산 참조는 `unity command set_serialized_field`를 쓴다.** 배열 원소도
`statOverrides.Array.data[0].stat` 형태로 지정할 수 있다.

```
쓸 수 있는 것    eval + SerializedObject   숫자 · 문자열 · 열거형 · 씬 오브젝트 참조 · 새 에셋 생성
써야 하는 것     set_serialized_field       자산 참조 (ScriptableObject · 프리팹 · 스프라이트)
```

## 17. M1 — 마을 화면 (2026.08.29)

체크리스트 2.2절 · 2.3절 · 2.6절이다. **활동 선택을 목록 버튼이 아니라 마을 건물로 바꿨다.**
설계 원칙 5번("성장은 눈에 보여야 한다")을 수치가 아니라 그림으로 처리하기 위해서다.
해금으로 건물이 늘어나면 마을이 자라는 것이 그대로 성장의 그림이 된다.

임시 스프라이트로 다섯 채를 세우고 실제로 눌러 들어가는 것까지 확인했다.

### 17.1 마을 좌표는 씬에 둔다 — 2026.08.29 결정

체크리스트 2.6절이 M1에서 실제로 배치해 보고 정하라고 남겨 둔 결정이다.

| | 정의에 둘 때 | 씬에 둘 때 |
|---|---|---|
| 다루는 법 | 도구로 관리된다 | 눈으로 보면서 옮긴다 |
| 배치 감각 | 하늘·지면과의 관계를 숫자만 보고 맞춰야 한다 | 바로 보인다 |
| 개수가 늘면 | 유리하다 | 씬 창이 복잡해진다 |

**씬에 둔다.** 다섯 개는 눈으로 옮기는 편이 빠르고, 실제로 배치해 보니 좌표보다
"라벨이 옆 건물을 덮는가"처럼 눈으로만 보이는 것이 문제였다.
해금으로 열 개를 넘으면 그때 정의로 옮긴다.

### 17.2 방송 시간 비용은 정의가 아니라 활동이 들고 있다

체크리스트 2.6절의 건물 정의 항목에는 "방송 시간 비용"이 들어 있다. **넣지 않았다.**

비용은 활동이 정하는 값이다. 정의에도 적으면 활동의 비용을 바꿨을 때
건물에 적힌 안내가 조용히 어긋난다. `IActivityFactory.BroadcastCost`에서 가져온다.
정의는 "어떤 활동인지"만 알고 "얼마나 드는지"는 활동에게 묻는다.

### 17.3 건물이 활동을 만드는 방법 — IActivityFactory

건물을 늘리는 것이 활동을 늘리는 것과 같은 일이 되게 하려면 정의가 활동을 가리켜야 한다.
그런데 활동은 만들 때마다 다른 것을 봐야 한다. 백룸은 가방 스탯을 읽어야 한다.
그래서 활동 자체가 아니라 **만드는 방법**을 `[SerializeReference]`로 들고 있다.

```
BuildingDefinition (ProjectR.Activity)
└─ IActivityFactory                     인터페이스는 활동 어셈블리에
   └─ BackroomsActivityFactory          구현체는 자기 활동이 사는 어셈블리에 (ProjectR.Backrooms)
```

인터페이스를 활동 어셈블리에 둔 이유는 정의와 구현체가 둘 다 볼 수 있는 자리이기 때문이다.
백룸에 두면 활동이 백룸을 참조해야 한다.

**건물 종류를 보고 분기하는 `if`가 없다.** 활동을 하나 늘리는 것은
구현체를 하나 더 만들고 인스펙터에서 고르는 일로 끝난다.
그런 분기가 생기는 순간이 리스코프 치환을 어긴 지점이다(체크리스트 1.1절).

### 17.4 "활동 없음"과 "방으로 감"은 다르다 — 버그 1건

처음에는 `HasActivity == false`이면 방 화면을 열게 했다. 집만 활동이 없을 것이라 본 것이다.

**아르바이트를 눌렀더니 방이 열렸다.** 아르바이트·오락실·식당은 활동이 M3에 만들어지므로
지금은 비어 있을 뿐인데, 그것을 "원래 활동이 아닌 건물"과 같게 취급한 것이다.

정의에 `opensRoom`을 따로 두어 갈랐다. 그리고 둘 다 아닌 건물은
막힌 이유로 **"아직 만들지 않았습니다"**를 돌려준다.
조용히 아무 일도 없는 것보다 만들지 않았다고 말하는 편이 낫다.

```
1일차  집       들어갈 수 있음      방 화면
       방송국   60분               백룸 탐험
       아르바이트 막힘             아직 만들지 않았습니다
       식당     막힘               내일부터 문을 엽니다 (2일차)
       오락실   막힘               채널이 자리를 잡아야 갈 여유가 생깁니다 (3일차)
```

막는 쪽(`GetBlockedReason`)이 이유까지 함께 만든다.
버튼을 끄기만 하면 왜 안 되는지 알 수 없다(체크리스트 2.2절).
잠긴 건물은 지우지 않고 흐리게만 둔다. 없어지면 무엇이 열릴 예정인지 알 수 없고,
마을이 자라는 것도 보이지 않는다.

### 17.5 두 줄로 세웠다가 한 줄로 되돌렸다

처음에는 체크리스트 2.2절 그림대로 뒷줄 셋 · 앞줄 둘로 세웠다.
**뒷줄 건물의 라벨이 앞줄 건물을 덮었다.** 라벨은 발밑에 붙는데,
앞줄 건물이 뒷줄 발밑 높이를 그대로 차지하기 때문이다. 구조적인 문제라 위치를 미세 조정해도 남는다.

한 줄로 바꿨다. 다섯 개는 한 줄에 들어가고 라벨이 겹치지 않는다.
원경과 근경의 깊이감은 사라졌지만, 읽히지 않는 화면보다는 낫다.
건물이 늘어 두 줄이 필요해지면 그때 라벨 위치를 다시 정한다.

카메라 직교 크기는 4.7이다. 4로 두었더니 양끝 건물이 잘렸다.

### 17.6 팝업 뒤가 실제로 새는 자리가 되었다

체크리스트 2.3절이 미리 짚어 둔 자리다. `EventSystem`은 위에 덮인 것이
**레이캐스트 대상일 때만** 아래를 막는다. 옵션 팝업은 화면 일부만 덮는 패널이라 뒤가 눌린다.

그전에는 관리 화면이 Canvas 버튼뿐이라 드러나지 않았다.
건물이 `SpriteRenderer` + `Physics2DRaycaster`로 입력을 받게 되면서 실제 위험이 되었다.

`PopupBackdrop`을 팝업 캔버스 맨 아래에 한 장 깔았다.
SWUtils 원본은 고치지 않고 `PopupShown` · `PopupHidden` 알림만 듣는다(체크리스트 1.2절).
팝업을 하나 만들 때마다 챙기지 않아도 된다.

### 17.7 임시 스프라이트는 파이썬으로 만들었다

건물 다섯 · 지면 · 하늘을 색만 다른 도형으로 그렸다. 아트가 오면 통째로 갈아 끼운다.

**유니티 안에서 만들려다 실패했다.** `unity command eval`의 Roslyn 컨텍스트는
람다가 바깥 지역변수를 잡지 못하고, 스크립트에 클래스를 선언하면 반환 경로가 깨진다.
그리기 코드는 헬퍼 함수가 여럿 필요해서 이 제약에 정면으로 걸린다.

PNG는 파이썬으로 직접 썼다(zlib + struct, 외부 패키지 없음).
유니티는 임포트 설정만 한다 — 스프라이트 타입, 픽셀당 단위 100,
건물은 축을 아래 가운데(발밑)에 두어 지면에 세우기 쉽게 했다.

### 17.8 Unity CLI 함정 둘 — 16.4절에 이어

**하나. Git Bash가 `/`로 시작하는 인자를 윈도우 경로로 바꾼다.**
`--target "/Village/Building_Studio"`가 `C:/Program Files/Git/Village/...`로 도착한다.
계층 경로를 넘길 때는 `MSYS_NO_PATHCONV=1`을 붙인다.

**둘. `set_serialized_field`가 자산을 대상으로 할 때는 `SaveAssets()`가 따로 필요하다.**
씬 오브젝트는 `save_scene`이 챙기지만 `ScriptableObject`는 메모리에만 남는다.
명령은 성공을 찍고 파일은 그대로여서, 파일을 열어 보기 전까지 됐다고 착각한다.

**셋. 스프라이트는 PNG의 서브에셋이라 경로만으로는 안 잡힌다.**
`{"path": "...png"}`는 메인 에셋인 `Texture2D`를 집어 `Sprite` 필드에 들어가지 못한다.
`{"guid": "...", "fileId": 21300000}`으로 서브에셋을 직접 가리켜야 한다.

### 18.1 왜 2D를 버렸나

설계 원칙 5번이 요구하는 "성장은 눈에 보여야 한다"를 **마을이 자라는 것**으로 처리하려면
채워질 빈 자리가 있어야 한다. 2D 한 줄에서는 그 자리가 화면 폭에서 끝난다.
스케치의 "추가 공간"이 그 자리다.

대신 비용을 진다. 마을은 매일 돌아오는 화면이므로 프레임과 메모리가 상시 부담이 된다.
**Q1(성능)이 아직 미판정인 상태에서 재야 할 대상이 둘로 늘었다.**
기획서 14장에 1-2번 위험으로 올렸다.

건물 하나가 모델 조각 여럿으로 이루어지므로, 정의가 프리팹 하나를 가리키는 방식으로는 담기지 않는다.
17.1절에서 정한 "좌표와 모델은 씬에 둔다"가 3D가 되면서 더 굳어졌다.
`BuildingDefinition`이 아는 것은 <b>무엇을 하는 건물인가</b>뿐이다.

### 18.2 배치 — 스케치를 그대로 옮겼다

```
        ▮                 ║                 ▮▮▮
```

**수직 통로가 이 화면의 중심이다.** 스케치가 탐험을 도로 끝의 엘리베이터로 그린 것을 따랐다.
통로 안에서 새어 나오는 빛이 백룸으로 내려가는 입구라는 것을 말 없이 알린다.
바깥으로 나가는 길이 그것뿐이라는 것이 설정의 일부다(기획서 12.7절).

### 18.3 `?.`는 유니티 오브젝트를 막아 주지 않는다 — 버그 1건

2D 마을을 지우고 새로 만들면서 `HomeScreen.villageRoot` 참조가 끊겼다.
코드는 이렇게 되어 있었다.

```csharp
villageRoot?.SetActive(isRoom == false);
```

그런데 **`UnassignedReferenceException`이 났다.**
널 조건 연산자는 C#의 널만 보고, 유니티가 덮어쓴 `==` 연산자를 건너뛴다.
인스펙터에서 비워 둔 필드는 C#으로는 널이 아니라 "아무것도 가리키지 않는 껍데기"라서
`?.`가 그대로 통과시킨다.

예외가 `Start` 한가운데서 터지는 바람에 그 뒤의 `Refresh`가 통째로 건너뛰어졌다.
화면에는 <b>라벨이 영문 코드명으로 남고 "마을로 나가기" 버튼이 마을에서도 보이는</b> 모습으로 나타났다.
원인과 증상이 전혀 닮지 않았다.

`HomeScreen`의 유니티 오브젝트 접근을 전부 `if (x != null)`로 바꿨다.
**유니티 오브젝트에는 `?.`를 쓰지 않는다.**

### 18.4 없는 색 속성을 프로퍼티 블록에 쓰면 건물이 뭉갠다 — 버그 1건

들어갈 수 없는 건물을 어둡게 하려고 `MaterialPropertyBlock`으로 `_BaseColor`를 덮어썼다.
**건물이 전부 통째로 청록색 실루엣이 되었다.**

원인은 속성 이름이었다. 이 도시 에셋의 셰이더 그래프(`S_BasicTextured`)가 쓰는 색 속성은
`_BaseColor`가 아니라 **`_Tint`**다. 없는 이름을 블록에 써넣자 색이 깨졌다.

```
M_Concrete / Shader Graphs/S_BasicTextured
  _BaseMap  = T_old_concrete_basecolor
  _Tint     = RGBA(0.802, 0.802, 0.802, 0.000)     ← 색은 여기 있다
  _BaseColor 없음                                   ← 여기에 썼다
```

재질마다 `_BaseColor` → `_Tint` → `_Color` 순으로 실제로 가진 이름을 찾아 쓰고,
하나도 없으면 건드리지 않도록 고쳤다. 알파는 곱하지 않고 원래 값을 그대로 둔다.
재질에 따라 알파가 투명도가 아니라 다른 뜻으로 쓰이기 때문이다.

**틀린 이름을 써도 예외가 나지 않는다.** 화면이 이상해질 뿐이라 원인을 찾는 데 시간이 걸린다.
프로퍼티 블록을 지우고 다시 그려 보는 것이 가장 빠른 갈림길이었다.

### 18.5 조명 — 지면이 건물보다 밝으면 안 된다

처음에는 환경광을 올려 화면을 밝혔는데, **평평한 지면만 밝아지고 건물은 그대로 어두웠다.**
지면이 화면의 대부분을 차지하는 원판이라 눈에 먼저 들어와 대비가 뒤집혔다.

지면과 도로를 어둡게 내리고(0.065 / 0.055) 건물 가까이에 네온빛을 놓는 쪽으로 바꿨다.
건물마다 색이 다른 점광원 하나씩 여섯 개다. 그림자는 끈다.

도로가 유난히 밝게 빛나던 것은 **재질의 매끄러움이 기본값 0.5여서 주광을 그대로 반사**하고 있었기 때문이다.
0으로 내렸다. 새로 만든 재질의 기본값을 확인하지 않으면 이런 일이 난다.

### 18.6 확인한 것

```

■ 잠긴 건물이 어둡게 나오고 이유를 돌려준다
   아르바이트 "아직 만들지 않았습니다" · 미니게임/공원 2일차 · 방송국 3일차
```

## 19. 마을을 이상세계 쪽으로 채웠다 (2026.08.30)

18장의 배치는 건물만 서 있고 바닥이 비어 있었다. 밀도를 올리고 톤을 잡았다.

참고로 니케 전초기지를 봤는데, 거기서 가져온 것은 **터가 경계로 닫혀 있고 그 안이 빽빽하다**는 구성뿐이다.
니케의 기지는 사람이 살아가는 아늑한 곳이지만 이 마을은 백룸 위에 덮인 곳이라,
**풍성하되 어딘가 잘못되어 보여야 한다.** 그쪽으로 밀었다.

### 19.1 바닥을 터로 바꿨다

원판 하나를 걷어내고 조각 아홉으로 다시 짰다.

```
바닥판          윗면이 y=0. 건물이 여기 선다
파인 노면       도로를 y=−0.55로 가라앉혀 깊이를 만든다
연단 셋         좌 · 우 · 공원. 한 단 올라간 터
가장자리 벽 넷  여기가 터의 끝이라는 것을 보여 준다
```

**도로를 파고 연단을 올린 것이 가장 크게 달라진 부분이다.** 평평한 바닥에서는
건물이 떠 있는 것처럼 보였는데, 높이가 갈리자 자리마다 뜻이 생겼다.

연단 가장자리를 따라 청록 발광 띠를 둘렀다. 도시의 결을 만들면서
동시에 "이 터는 인공으로 구획된 곳"이라는 인상을 준다.

### 19.2 밀도 — 빈 바닥이 보이면 안 된다

```
배경 건물   23채    상호작용하지 않는다. 남은 SM_MERGED_BP_* 를 썼다
소품       122개   상자 · 콘 · 쓰레기 · 병 · 천. 씨앗 고정 20260830
녹지        40개   Neon Interior Props의 AlgaePlant 셋
가로등      16개
```

소품은 씨앗을 고정해 뿌린다. 다시 돌려도 같은 배치가 나와야
"어제와 다르다"는 착각이 생기지 않는다.

**남쪽은 일부러 비워 두었다.** 스케치의 "추가 공간"이고,
해금으로 건물이 들어설 자리다. 채워질 빈 자리가 있어야
설계 원칙 5번("성장은 눈에 보여야 한다")을 마을이 자라는 것으로 처리할 수 있다.

### 19.3 이상세계로 미는 장치

| 장치 | 무엇을 노렸나 |
|---|---|
| 먼 벽과 천장 턱 | 하늘이 없다. 지평선 자리가 막혀 있다 |
| 먼 벽의 형광등 띠 넷 | 백룸의 빛이 위로 새어 올라온 것처럼 |

작게 기울이면 "뭔가 이상한데 뭔지 모르겠다"가 된다. 뒤쪽이 노린 것이다.

### 19.4 재질을 건드리는 방식을 버렸다 — 2026.08.30 결정

18.4절에서 색 속성 이름을 찾아 쓰도록 고쳤는데도 **건물이 또 통째로 뭉갰다.**
두 번 연달아 같은 자리에서 터진 셈이다.

`MaterialPropertyBlock`으로 색을 덮어쓰는 방식 자체를 버렸다.

| | 재질을 덮어쓸 때 | 강조등을 껐다 켤 때 |
|---|---|---|
| 셰이더 의존 | 있다. 속성 이름이 다르면 깨진다 | 없다 |
| 실패했을 때 | 예외 없이 화면만 이상해진다 | 불이 안 켜질 뿐 |
| 에셋이 늘면 | 셰이더마다 다시 확인해야 한다 | 그대로 동작한다 |
| 네온 도시와 | 재질을 눌러 납작하게 만든다 | 어울린다 |

이 마을은 에셋 팩에서 가져온 재질을 쓰고 앞으로도 늘어난다.
**재질에 손대지 않는 방법이 유일하게 안전하다.**
들어갈 수 없는 건물은 불이 죽고, 마우스를 올리면 밝아진다.
불 꺼진 건물이 늘어서 있는 것 자체가 "아직 열리지 않았다"를 말해 준다.

### 19.5 어둡다는 것과 안 보인다는 것은 다르다

이상세계 느낌을 낸다고 주광을 0.85까지 내리고 안개를 0.0055로 올렸더니
**화면이 그냥 안 보였다.** 소품 122개와 녹지 40개를 뿌려 놓고 하나도 보이지 않았다.

되돌린 값이 지금 값이다.

```
주광        1.25
안개        지수 0.0021
환경광      하늘 0.30 / 적도 0.24 / 지면 0.11
점광원      건물 강조 6 + 배경 채움 10
```

**점광원이 처음에 너무 약했다.** 세기 42에 범위 52로는 건물에 닿지 않았다.
3.2배로 올리고서야 벽에 색이 얹혔다. URP의 점광원 세기는 감이 잘 안 오므로
숫자를 정하지 말고 화면을 보고 맞춰야 한다.

## 20. 마을을 데모 씬 자체로 바꿨다 — 2026.08.30 결정

19장까지 손으로 배치한 마을은 **건물이 섬처럼 떨어져 있어 도시로 읽히지 않았다.**
데모 씬(`LV_CyberAlley_WP`)은 건물이 맞붙어 골목을 이루는데, 그 밀도를 손으로 흉내 내는 것은
쌓아 올린 조각 수의 문제가 아니라 배치 설계의 문제였다.

**데모 씬의 도시를 통째로 가져왔다.**

```
SpotLights     25
LampHolograms  41
```

### 20.1 옮긴 방법 — 루트째 옮긴다

프리팹으로 뽑으려 했더니 5초 제한을 넘겼다. 오브젝트를 하나씩 옮기는 것도 마찬가지다.

**씬을 추가로 열고 루트를 통째로 옮기면 한 번의 호출로 끝난다.**

```
1. HomeScene 열기 (Single)
2. 데모 씬 열기 (Additive)
3. EditorSceneManager.MoveGameObjectToScene(루트, HomeScene)   ← 루트마다 한 번
4. 데모 씬 닫기 (저장하지 않음)
```

`MoveGameObjectToScene`은 계층 전체를 한 번에 옮기므로 자식 수와 상관없이 빠르다.
데모 씬은 저장하지 않고 닫아 원본이 그대로 남는다.

### 20.2 상호작용 건물은 새로 세우지 않는다

### 20.3 화면 이동 — 맵이 한 화면에 안 들어가도 된다

`VillageCameraPan`. 끌어서 카메라를 평행 이동한다.

- **회전은 허용하지 않는다.** 돌리면 건물 뒤가 보이고, 뒤를 보여 줄 생각으로 만들지 않은 배치가 드러난다
- 화면 평면이 아니라 **바닥 평면**을 따라 옮긴다. 화면 평면으로 옮기면 위아래로 끌 때 카메라가 하늘로 떠오른다
- 움직일 범위를 네모로 묶는다. 묶지 않으면 도시 밖 허공을 보게 된다
- 손을 떼면 조금 미끄러지다 멈춘다

한 화면에 맞추려고 카메라를 뒤로 빼면 건물이 작아져 무엇이 무엇인지 알아볼 수 없다.

### 22.1 데모 씬에서 가져온 것 — 밝기는 재질이 아니라 설정이었다

**안개 색이 진한 하늘색인 것이 핵심이다.** 회색 안개는 화면을 뿌옇게 죽이지만

### 22.2 ToonScapes는 스케일이 다르다

사이버펑크 건물이 12~30단위인 데 비해 ToonScapes는 폭이 넓다.

```
나무   TSI_Amberleaf_Tree_01A    18.9 x 23.7 x 17.8
절벽   TSI_Cliff_01A             36.6 x 70.0 x 38.4
배경 산 TSI_BG_Mountain_01A      10240 x 1771 x 10240   ← 스카이박스 대용
플랫폼 TSI_Stone_Platform_02A     4.0 x 0.6 x 4.0
```

나무 한 그루가 테라스(34~56)의 절반이다. 그대로 놓으면 지형이 안 보인다.
**배율을 눈대중으로 주지 말고 목표 크기에서 역산해야 한다.**

```csharp
var widest = Mathf.Max(bounds.size.x, bounds.size.z);
transform.localScale *= 목표크기 / widest;
```

이렇게 고치고서야 나무 4.5~7 · 바위 3~6 · 절벽 16~24로 정리되었다.
처음에는 0.22 같은 배율을 손으로 넣었는데, 프리팹마다 원본 크기가 달라 들쭉날쭉했다.

ToonScapes 프리팹은 그대로 쓰고, 내가 만든 프리미티브에만 단색을 쓴다.

## 23. 마을을 하늘에 뜬 섬으로 — 2026.08.31

22장에서 만든 마을은 **네모 박스에 나무를 박아 둔 것**이었다. 테라스가 직육면체이고

ToonScapes 데모 씬(`Demo_Scene_Day`)을 보니 그쪽은 완성된 자연 지형이었다.

```
Island_2            렌더러 32,929 · 366 x 434 x 760
Background_Cliffs   렌더러    190 · 855 x 554 x 944
Background          렌더러     11 · 스카이박스 대용 (37,000 규모)
```

**손으로 흉내 낼 수 있는 것이 아니었다.** 굴곡, 물길, 돌계단, 다리, 나무 배치가
전부 사람이 앉아서 배치한 결과다. 프리미티브로 만든 박스와는 종류가 다르다.

**데모의 섬을 통째로 가져왔다.** 20장에서 쓴 것과 같은 방법이다 —
씬을 추가로 열고 `MoveGameObjectToScene`으로 루트째 옮긴 뒤 데모 씬은 저장하지 않고 닫는다.

### 23.1 스케일을 바꾸지 않는다 — 2026.08.31 결정

22장에서는 ToonScapes 프리팹을 목표 크기에 맞춰 줄였다(나무 18.9 → 4.5~7).
**그럴 필요가 없었다.** 데모의 스케일이 이미 맞춰져 있다.

줄여야 했던 것은 내가 만든 테라스가 작았기 때문이고, 그 테라스가 문제였다.
**지형을 에셋에 맞추는 것이 아니라 에셋의 지형을 그대로 쓰는 것이 맞다.**

지금은 나무도 바위도 절벽도 원본 크기 그대로다.

### 23.2 건물 자리는 지형을 재서 고른다

섬은 굴곡이 심해 좌표를 손으로 찍으면 파묻히거나 공중에 뜬다.
**레이캐스트로 평평한 곳을 찾아 앉혔다.**

```
1. x 330~570 · z 290~540을 14단위 격자로 훑는다
2. 각 점에서 아래로 쏘고, 둘레 네 점도 쏜다
3. 높이 차가 5.5 이내면 후보
4. 평평한 순으로, 서로 46단위 이상 떨어지게 여섯 곳을 고른다
```

후보 79곳 중 여섯을 골랐다. 처음에는 높이 차 2.2로 잡았더니 후보가 2곳뿐이었다.
**자연 지형에는 완전한 평지가 거의 없다.**

건물은 아직 없다. 자리에 노란 테두리와 콜라이더, 라벨만 있다.
나중에 `Village/Building_*`의 자식으로 모델을 붙이면 그대로 연결된다.

### 23.3 씬을 다시 열면 5초를 먹는다

스크립트마다 `EditorSceneManager.OpenScene`으로 시작했는데,
렌더러 6만 개짜리 씬은 **여는 것만으로 5초 제한을 넘긴다.**

### 24.4 세 번 연속 크기를 틀렸다

이번 작업에서 시간을 가장 많이 먹은 것은 배치가 아니라 **크기 판단 실패**였다.

| # | 무엇을 | 왜 틀렸나 | 얼마나 |
|---|---|---|---|
| 1 | `Background` 산 11개 | 원래 먼 배경인데 섬을 줄이면서 마을 옆으로 끌려왔다 | 3,400단위 (마을의 16배) |
| 2 | `Nature`에 섞인 절벽 | 이름 필터 `StartsWith("TSI_Rock")`이 `TSI_Background_Cliff`를 놓쳤다 | 333단위 |
| 3 | 밑면 절벽 | `GetComponentInChildren<Renderer>()`가 **첫 렌더러 하나만** 재서 높이를 작게 봤다 | 목표의 5배 |

셋 다 증상이 똑같았다 — **화면이 바위로 가득 찼다.** 그래서 1번을 고쳐도
2번 때문에 그림이 안 변했고, 2번을 고쳐도 3번이 남아 있었다.
같은 화면을 네 번 보고서야 "원인이 하나가 아니다"를 의심했다.

#### 이름 대신 크기로 걸러야 했다

두 번을 이름 필터로 틀린 뒤 방법을 바꿨다.

```csharp
// 이름은 두 번 틀렸다. 실제 크기로 본다.
var b = crs[0].bounds;
for (int i = 1; i < crs.Length; i++) b.Encapsulate(crs[i].bounds);
if (b.size.y > 26f || b.size.x > 26f || b.size.z > 26f) doomed.Add(c.gameObject);
```

한 번에 24개가 걸렸다. **에셋 팩의 이름 규칙을 믿지 않는다.**

#### 렌더러는 전부 합쳐서 재야 한다

```csharp
// 틀림 — 첫 렌더러 하나만 잰다
var h = go.GetComponentInChildren<Renderer>().bounds.size.y;

// 맞음 — 전부 합쳐서 잰다
var rs = go.GetComponentsInChildren<Renderer>(false);
var b = rs[0].bounds;
for (int k = 1; k < rs.Length; k++) b.Encapsulate(rs[k].bounds);
```

그리고 **스케일은 덮어쓰지 않고 곱한다.** 프리팹 루트가 자체 스케일을 갖고 있으면
`localScale = s`는 그 값을 지운다. `localScale *= s`여야 한다.

### 24.5 지형 메시를 잃었다

마을에 걸치는 섬 물체를 렌더러 경계로 지우다가 `Terrain_01`/`Terrain_02`의
메시까지 지웠다. 앞선 스크립트는 이름으로 "Terrain"을 걸렀지만,
경계로 거르는 스크립트에는 그 예외를 옮겨 적지 않았다.

복구하지 않고 **의도적으로 다시 지었다.** 남은 것은 흩어진 거대 바위뿐이었고,
기획서가 요구하는 것은 "하늘에 뜬 섬"이라 통제된 밑면 절벽이 오히려 맞았다.

> **거르는 조건을 바꿀 때는 기존 예외도 함께 옮긴다.**
> 이름 필터에 있던 `Terrain` 예외가 경계 필터에는 없었다.

#### 화면 이동 범위

```

```
