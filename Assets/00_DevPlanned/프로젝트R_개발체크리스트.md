# 프로젝트 R — 개발 체크리스트

기획서 v0.2 · 프로토타입 문서 v0.2 기준
Version 0.1 · 2026.08

---

## 이 문서 사용법

작업할 때 옆에 띄워두고 항목을 지워나가는 용도다. 무엇을 만드는지는 기획서, 무엇을 검증하는지는 프로토타입 문서를 본다.

- 2~4장은 작업 내내 반복해서 확인하는 상시 항목이다
- 5장은 순서대로 진행하는 단계별 항목이다
- 6장 이후는 해당 시점에만 확인한다

앞 단계를 건너뛰고 뒤 단계를 시작하지 않는다. 특히 5장 Phase 1의 성능 판정이 끝나기 전에는 다른 시스템을 만들지 않는다.

```
□ 목표 프레임 결정 (Phase 1 판정 기준이 됨)
```

## 2. 상시 확인 — 코딩 규약

새 클래스나 파일을 만들 때마다 확인한다.

```
□ SWUtils에 같은 기능이 이미 있는지 먼저 확인했는가
□ SWUtils 원본을 수정하지 않았는가 (상속하거나 감싸서 사용)
□ 네임스페이스가 폴더 구조와 일치하는가
□ 참조 방향이 asmdef 의존 규칙에 맞는가
□ 클래스가 한 가지 책임만 갖는가
□ 교체 가능성이 있는 부분을 인터페이스로 분리했는가
```

### 2.1 주석

```
□ 모든 public 타입에 <summary> 주석을 달았는가
□ 모든 public 필드, 프로퍼티, 메서드에 <summary> 주석을 달았는가
□ 매개변수에 <param>, 반환값에 <returns>를 달았는가
□ 문장을 한국어 높임말로 끝맺었는가 ("~합니다", "~입니다")
□ 부가 설명이 필요한 클래스에 <remarks>를 달았는가
□ #region 이름을 한국어로 썼는가
□ #endregion에 이름 주석을 붙였는가 (#endregion // 필드)
```

### 2.2 명명

```
□ 클래스, 인터페이스, public 멤버가 PascalCase인가
□ private 필드가 camelCase이고 접두사가 없는가
□ 직렬화 필드에 [SerializeField]를 붙였는가
□ 이벤트 데이터 이름이 "동작 + Event" 형태인가
```

### 2.3 코드 습관

```
□ Debug.Log 대신 SWLog를 썼는가
□ 로그 메시지에 [클래스명] 접두사를 붙였는가
□ 이벤트 구독을 OnEnable에서 하고 OnDisable에서 해제했는가
□ GetComponent를 Awake에서 캐싱했는가
□ 반복 생성되는 오브젝트를 SWPool로 처리했는가
□ 목록 반환 시 null 대신 빈 목록을 반환하는가
□ using 정렬이 System → Unity → SW.* → 게임 순인가
```

## 3. 상시 확인 — 모듈 분리

```
□ 시스템끼리 직접 참조하지 않고 SWEventBus로 통신하는가
□ UI가 게임 로직을 갖고 있지 않은가
□ 데이터 계층이 시스템을 참조하지 않는가
□ 백룸 모듈이 방송 모듈을 직접 참조하지 않는가
□ 전역 싱글톤이 계획한 개수를 넘지 않았는가
□ 한 클래스가 500줄을 넘지 않았는가 (넘으면 책임 분리 검토)
```

### 3.1 의존 방향

```
Core          ← 의존 없음
Data          ← Core
Streamer      ← Core, Data
Inventory     ← Core, Data
Activity      ← Core, Data
Backrooms     ← Core, Data, Activity, Inventory
Broadcast     ← Core, Data, Activity
UI            ← 위 전부
```

Backrooms와 Broadcast는 서로를 참조하지 않는다. asmdef로 강제한다.

## 5. 단계별 체크리스트

### Phase 0 — 환경 세팅

```
□ 1장 착수 전 세팅 전체 완료
□ 활동 공통 인터페이스 정의 (내용은 비어 있어도 됨)
□ 활동 결과 데이터 구조 정의
□ 게임 상태 데이터 구조 정의
□ 전역 매니저 배치 (진행 관리, 상태 보관)
□ 씬 3개 생성 (관리 화면, 로딩, 백룸)
□ 씬 전환 동작 확인
□ 씬 전환 후 상태가 유지되는지 확인
```

**완료 기준**: 빈 씬 사이를 오갈 수 있고 상태가 유지된다.

주의: 백룸을 게임 전체로 만들지 않는다. 처음부터 여러 활동 중 하나로 취급한다. 내용이 비어 있어도 규격을 먼저 만든다.

---

### Phase 1 — 맵 생성과 조명 성능

이 단계가 프로젝트 최대 기술 위험이다. 다른 것보다 먼저 끝낸다.

#### 구현

```
□ 맵 생성 인터페이스 정의 (교체 가능하게)
□ 재귀적 백트래킹 생성 구현
□ 순환로 추가 보정 (벽 일부 무작위 제거)
□ 막다른 길 비율 상한 보정
□ 탈출 경로 도달 가능성 검증
□ 검증 실패 시 재생성, 재시도 횟수 상한 설정
□ 방·복도 프리팹 3~5종 제작 (형태만 잡은 박스)
□ 프리팹별 조명 굽기
□ 프리팹 조립 방식으로 실행 중 배치
□ 이음새 라이트 프로브 보정
□ 조립을 프레임 분할 처리 (한 프레임에 전체 조립 금지)
□ 시드 저장 및 재현 기능
□ 인스펙터에 생성 설정 노출 (SWGroup으로 그룹화)
□ 맵 재생성 버튼 추가 (SWButton)
```

#### 측정

```
□ 최악 구간(넓은 홀, 시야 개방) 프레임레이트 측정
□ 맵 1개 생성 소요 시간 측정
□ 드로우콜 측정
□ 장시간 플레이 시 메모리 증가 확인
□ 막다른 길 비율 통계 확인
□ 순환로 개수 통계 확인
```

#### 판정

```
□ 목표 사양에서 목표 프레임 유지되는가
   → 통과: Phase 2 진행
   → 경계: 프리팹 수 감소 또는 오클루전 컬링 강화 후 재측정
   → 실패: 생성 방식 전환
           1순위 WFC / 2순위 BSP + 순환로 연결 / 3순위 방 이어붙이기
```

이 단계에 배정한 기간의 절반이 지나도 성능이 안 나오면 붙잡지 말고 전환한다.

**완료 기준**: 랜덤 맵이 생성되고, 목표 프레임을 유지하며, 시드로 재현된다.

### Phase 2 — 1인칭 이동과 분위기

몬스터 없이 무서운지 검증하는 단계다.

#### 구현

```
□ 1인칭 캐릭터 조작 (걷기, 달리기, 앉기)
□ 손전등 (배터리 소모, 흔들림)
□ 발소리 재질별 구분
□ 형광등 환경음
□ 공간 잔향 (방 크기 반응)
□ 랜드마크 오브젝트 제작 (손상, 오브젝트, 조명, 흔적 유형)
□ 구역별 랜드마크 배치
□ 탈출 지점 배치
□ 탈출 처리
```

#### 사운드

아트는 박스 수준이어도 되지만 사운드는 근사치 이상이어야 한다. 소리 없이 테스트하면 판정이 나오지 않는다.

```
□ 형광등 웅웅거림
□ 발소리 (카펫, 타일, 콘크리트)
□ 공간 잔향 동적 변화
□ 미세 환경음 (환풍기, 물방울, 먼 소리)
□ 정적 구간 설계 (소리를 빼는 것도 설계)
```

#### 테스트

```
□ 외부 테스터 3~5명 확보 (개발자 아닌 사람)
□ 설명 없이 10분 플레이
□ 관찰: 몇 분에 지루해하는가
□ 관찰: 뒤를 돌아보는가
□ 관찰: 소리에 반응하는가
□ 관찰: 길 잃음이 긴장인가 짜증인가
□ 관찰: 랜드마크를 알아채는가
□ 질문(유도 없이): 어떤 느낌이었나요 / 다시 하고 싶나요
```

#### 판정

```
□ 긴장감이 유지되는가
   → 통과: Phase 3 진행
   → 경계: 사운드와 랜드마크 보강 후 재테스트
   → 실패: 아트 방향, 공간 규모, 사운드 전면 재설계
           몬스터를 넣어도 해결되지 않는다
```

**완료 기준**: 외부 테스터가 몬스터 없이도 긴장한다.

### Phase 3 — 몬스터 1종

#### 구현

```
□ Behaviour Tree 에셋 생성 (SWTools > Behaviour Tree)
□ 행동 노드 구성: 배회, 감지, 추격, 수색, 매복, 복귀
□ 필요한 사용자 노드 스크립트 생성 (Action / Composite / Decorator)
□ Blackboard 키 정의 (플레이어 위치, 마지막 목격 위치, 감지 범위, 이동 속도 등)
□ 몬스터에 Runner 부착 및 트리 연결
□ 실행 중 NavMesh 굽기 (생성 완료 후 1회)
□ 은신 시스템 (앉기, 오브젝트 뒤, 시야 차단)
□ 소음 반경 이벤트 (걷기 < 달리기, 앉기는 무음)
□ 조우 시 실패 처리
□ 그래프 검증 통과 확인 (연결되지 않은 노드 없음)
```

#### 판단력 있어 보이게 만들기

```
□ 기억: 마지막 목격 위치 주변 수색 가중치
□ 매복: 추격 포기 후 출구 근처 대기
□ 학습한 척: 자주 쓴 은신처 우선 확인
□ 정보 노출: 행동 모드가 바뀌는 노드 진입 시 소리 발생
```

마지막 항목이 핵심이다. 상태가 바뀌었는데 소리가 없으면 플레이어는 무슨 일이 일어났는지 모르고, 그러면 대처가 실력이 될 수 없다.

#### Behaviour Tree 사용 규칙

SWUtils에 Behaviour Tree(`SW.BehaviourTree`)가 이미 구현되어 있으므로 이를 사용한다. 그래프 편집 창, 자동 배치, 그래프 검증, 실행 중 노드 상태와 Blackboard 값을 보여주는 Runtime Debug 탭까지 갖춰져 있다.

```
BT를 쓰는 이유
□ 도입 비용이 없다 (라이브러리와 에디터가 이미 있다)
□ Blackboard Override로 트리 하나를 여러 몬스터에 재사용할 수 있다
□ 행동이 에셋이 되어 층 정의, 몬스터 정의와 같은 데이터 중심 구조에 맞는다
□ Runtime Debug 탭으로 실행 중 어느 노드가 도는지 직접 확인할 수 있다
□ 수색, 매복 같은 하위 행동을 몬스터 사이에 공유할 수 있다

지켜야 할 규칙
□ 행동 모드가 바뀌는 액션 노드는 진입 시 반드시 소리 이벤트를 발행한다
□ 소리 재생을 Decorator 노드로 분리해 재사용 가능하게 만든다
□ Blackboard 키 이름을 상수로 관리한다 (문자열 직접 입력 금지)
□ 몬스터 유형별 차이는 트리 복제가 아니라 Blackboard Override로 처리한다
□ 트리가 지나치게 깊어지면 서브트리로 분리한다

FSM을 쓰는 경우
□ 행동이 아니라 단순 상태 전이인 경우 (UI 화면, 방송 진행 단계 등)
□ 이때는 SWMonoStateMachine 또는 SWMonoStackStateMachine을 쓴다
```

몬스터 유형이 늘어나도 트리를 복제하지 않는다. 감지 범위, 이동 속도, 수색 지속 시간, 매복 확률 같은 수치는 Blackboard Override로 빼고, 감지 방식 자체가 다른 경우(소리 추적, 시각 추적)만 서브트리를 갈아 끼운다.

#### 판정

```
□ 도망쳐 살아남았을 때 내가 잘했다고 느끼는가
   → 통과: Phase 4 진행
   → 경계: 소리로 정보를 더 노출
   → 실패: 막다른 길에서 죽으면 순환로 보정 강화
           무슨 일인지 모르겠으면 소리 설계 재작업
```

**완료 기준**: 실패했을 때 운이 나빴다가 아니라 내가 실수했다고 느낀다.

### Phase 4 — 수집과 정산

#### 구현

```
□ 격자 인벤토리 계산부를 Unity와 분리해 작성
□ 인벤토리 화면 (드래그, 회전, 배치)
□ 이상물체 5~8종, 형태를 제각각으로 (1x1, 2x1, 2x3, 1x4)
□ 습득, 배치, 버리기
□ 방송 시간 제한 타이머
□ 탈출 시 정산 화면
□ 손실 정책을 인터페이스로 분리
□ 전량 소실 정책 구현
□ 활동 결과 반환 및 관리 화면 복귀
□ 활동 도중 강제 종료 시 되돌리기
□ 시간대는 소비 처리 (되돌려도 복구되지 않음)
```

#### 확인

```
□ 좋은 물건을 주웠을 때 기쁜가
□ 무엇을 버릴지 고민이 생기는가
□ 타이머가 실제로 결정을 바꾸는가
□ "한 개만 더"와 "지금 나가자"가 충돌하는가
□ 정산 화면이 보상으로 느껴지는가
□ 전부 잃었을 때 다시 하겠다인가 그만두겠다인가
```

마지막 항목에서 부정적 반응이 나오면 아래 순서로 완화한다.

```
□ 1단계: 방송 사고 클립 보상
□ 2단계: 회수 기회 (기절 지점 도달 시 일부 회수)
□ 3단계: 보험 업그레이드
□ 4단계: 일부 소실로 전환
```

손실 정책을 인터페이스로 분리해뒀으면 구현체 교체로 끝난다.

**완료 기준**: 탐험 1회가 시작과 중간과 끝을 가진 완결된 경험이 된다.

## 6. 프로토타입 이후 체크리스트

프로토타입 4단계를 통과한 뒤 진행한다.

### 6.1 1일 시연판

```
□ 하루 시간대 구조
□ 활동 선택 화면
□ 컨디션 4수치 (수면, 배고픔, 기분, 피로도)
□ 피로도가 나머지 수치 상한을 누르는 계산
□ 컨디션이 백룸 성능에 반영되는 것 확인
□ 시청자 수와 후원금 계산
□ 채팅 최소 구현 (상황 태그 × 템플릿)
□ 방송 화면 겹침 표시
□ 업그레이드 1종 이상
□ 하루 종료 및 유지비 차감
□ 저장과 불러오기
```

**완료 기준**: 아침에 일어나 방송하고 백룸에 들어가고 정산받고 업그레이드하고 잠드는 하루가 온전히 돌아간다.

### 6.2 데이터 에셋화

콘텐츠 확장 속도가 여기서 갈린다. 프로그래머 없이 층을 추가할 수 있어야 한다.

```
□ 스트리머 정의 (초기 스탯, 성장 계수, 상한, 고유 특성, 아바타, 컨셉 유형)
□ 층 정의 (생성 설정, 적용 규칙, 몬스터 구성, 아이템표)
□ 몬스터 정의 (감지 방식, 속도, 수색 시간, 매복 확률, 사운드)
□ 몬스터 Behaviour Tree 에셋 (유형별 서브트리, 공통 수색·매복 트리)
□ 아이템 정의 (격자 크기, 등급, 판매가, 공개 효과, 제작 용도)
□ 미션 정의 (발생 조건, 목표, 제한 시간, 보상, 위험도)
□ 업그레이드 정의 (대상, 비용, 효과, 선행 조건)
□ 시그널 등급 정의 (명칭, 조건, 트로피, 해금)
□ 채팅 템플릿 세트 (상황 태그별)
□ 층 규칙을 조합 가능한 형태로 분리 (어둠, 배터리, 구조 변경, 신호 불안정)
```

### 6.3 확장성 확인

DLC 스트리머 추가를 막지 않기 위한 항목이다. 하나라도 어기면 이후 추가가 불가능해진다.

```
□ 스트리머 정의가 전부 ScriptableObject로 외부화되었는가
□ 저장 데이터가 채널 진행도와 스트리머별 진행도로 분리되었는가
□ 출시 스트리머 1명도 여러 명 중 하나인 것처럼 짜였는가
□ 스트리머 관련 하드코딩이 하나도 없는가
□ 저장 데이터에 버전 필드가 있는가
```

마지막 항목을 빠뜨리고 배포하면 구조 변경 시 기존 세이브를 살릴 방법이 없다.

## 7. 성능 점검

측정 없이 최적화하지 않는다. 프로파일러로 확인한 뒤 손댄다.

```

□ UI 수치를 변경 시에만 갱신하는가
□ 매 프레임 갱신이 불필요한 로직을 주기 갱신으로 돌렸는가
□ NavMesh 굽기가 생성 후 1회만 실행되는가
□ 장시간 플레이 시 메모리 누수가 없는가
```

## 8. 테스트

### 8.1 단위 테스트

Unity에 의존하지 않게 설계한 부분만 대상으로 한다.

```
□ 맵 생성: 순환로 최소 개수
□ 맵 생성: 막다른 길 비율 상한
□ 맵 생성: 탈출 경로 존재
□ 맵 생성: 시드 고정 시 동일 결과
□ 인벤토리: 배치 가능 판정
□ 인벤토리: 경계 조건
□ 인벤토리: 형태별 회전
□ 컨디션: 피로도가 상한을 누르는 계산
□ 활동 결과 반영: 상태 변동 정확성
□ 손실 정책: 정책별 손실 목록
```

맵 생성 테스트는 시드를 여러 개 돌려 통계로 확인한다. 한 번 통과했다고 안심할 수 없는 영역이다.

### 8.2 인게임 디버그 명령

`SWDebugConsole`에 등록한다.

```
□ 지정 시드로 맵 재생성
□ 현재 시드 출력
□ 좌표 이동
□ 몬스터 소환
□ 몬스터 정지
□ 아이템 지급
□ 남은 시간대 설정
□ 컨디션 수치 설정
□ 후원금 지급
```

상태 감시 항목:

```
□ 현재 시드
□ 층 번호
□ 시청자 수
□ 컨디션 4수치
□ 몬스터 현재 실행 노드 (BT Runtime Debug 탭 병행 확인)
□ 몬스터 Blackboard 값
□ 이벤트 버스 리스너 수 (누수 확인)
```

### 8.3 회귀 확인

```
□ 씬을 여러 번 오갔을 때 이벤트 리스너가 누적되지 않는가
□ 활동 도중 강제 종료 후 정상 복구되는가
□ 저장 후 불러오기로 상태가 완전히 복원되는가
□ 맵 생성 실패 시 무한 재시도에 빠지지 않는가
```
