## 이 문서 사용법

작업할 때 옆에 띄워두고 항목을 지워나가는 용도다. 무엇을 만드는지는 기획서, 무엇을 검증하는지는 프로토타입 문서를 본다.

- 2~4장은 작업 내내 반복해서 확인하는 상시 항목이다
- 5장은 순서대로 진행하는 단계별 항목이다
- 6장 이후는 해당 시점에만 확인한다

앞 단계를 건너뛰고 뒤 단계를 시작하지 않는다. 특히 5장 Phase 1의 성능 판정이 끝나기 전에는 다른 시스템을 만들지 않는다.

> **지금 열려 있는 예외 (2026.08.28)**: Phase 2의 판정(Q2)과 Phase 3의 판정(Q3)을 받지 않은 채
> **Phase 4의 구현까지 진행했다**(진행기록 9장·10장). 판정(Q4)도 아직 받지 않았다.
> 외부 테스터를 부르는 것과 빌드를 기능 완성 시점으로 몰았기 때문이다.
> 판정 기준을 낮춘 것이 아니라 시점만 옮긴 것이며, 감수한 위험은 진행기록 8.10절에 적어 두었다.
> **Phase 1의 실기 프레임 판정도 같은 빌드 시점까지 미뤄져 있다**(5장 Phase 1 판정란).
> **미판정이 Q2·Q3·Q4 셋으로 늘었다. 다음은 구현이 아니라 빌드다.**

표기: `□` 미완 · `■` 완료 · `✕` 하지 않기로 결정(사유는 개발진행기록 참조)
각 단계의 측정값과 판정, 결정 사유는 `프로젝트R_개발진행기록.md`에 적는다.

## 2. 상시 확인 — 코딩 규약

새 클래스나 파일을 만들 때마다 확인한다.

```
□ SWUtils에 같은 기능이 이미 있는지 먼저 확인했는가
□ SWUtils 원본을 수정하지 않았는가 (상속하거나 감싸서 사용)
□ 네임스페이스가 폴더 구조와 일치하는가
□ 참조 방향이 asmdef 의존 규칙에 맞는가
□ 클래스가 한 가지 책임만 갖는가
□ 교체 가능성이 있는 부분을 인터페이스로 분리했는가
□ 한 오브젝트에 컴포넌트가 너무 많이 붙지 않았는가 (진행기록 11.3절)
□ 전역 객체를 Resources로 불러오고 있지 않은가 (씬에 두고 SWSingleton이 정리한다 · 11.2절)
□ 팝업을 프리팹이 아니라 카탈로그 키로 부르고 있는가 (11.1절)
```

### 2.1 주석

```
□ 모든 public 타입에 <summary> 주석을 달았는가
□ 모든 public 필드, 프로퍼티, 메서드에 <summary> 주석을 달았는가
□ 매개변수에 <param>, 반환값에 <returns>를 달았는가
□ 문장을 한국어 높임말로 끝맺었는가 ("~합니다", "~입니다")
□ 부가 설명이 필요한 클래스에 <remarks>를 달았는가
□ #region 이름을 한국어로 썼는가
□ #endregion에 이름 주석을 붙였는가 (#endregion // 필드)
```

### 2.2 명명

```
□ 클래스, 인터페이스, public 멤버가 PascalCase인가
□ private 필드가 camelCase이고 접두사가 없는가
□ 직렬화 필드에 [SerializeField]를 붙였는가
□ 이벤트 데이터 이름이 "동작 + Event" 형태인가
```

### 2.3 코드 습관

```
□ Debug.Log 대신 SWLog를 썼는가
□ 로그 메시지에 [클래스명] 접두사를 붙였는가
□ 이벤트 구독을 OnEnable에서 하고 OnDisable에서 해제했는가
□ GetComponent를 Awake에서 캐싱했는가
□ 반복 생성되는 오브젝트를 SWPool로 처리했는가
□ 목록 반환 시 null 대신 빈 목록을 반환하는가
□ using 정렬이 System → Unity → SW.* → 게임 순인가
```

## 3. 상시 확인 — 모듈 분리

```
□ 시스템끼리 직접 참조하지 않고 SWEventBus로 통신하는가
□ UI가 게임 로직을 갖고 있지 않은가
□ 데이터 계층이 시스템을 참조하지 않는가
□ 백룸 모듈이 방송 모듈을 직접 참조하지 않는가
□ 전역 싱글톤이 계획한 개수를 넘지 않았는가
□ 한 클래스가 500줄을 넘지 않았는가 (넘으면 책임 분리 검토)
```

### 3.1 의존 방향

```
Core          ← 의존 없음
Data          ← Core
Streamer      ← Core, Data
Inventory     ← Core, Data
Activity      ← Core, Data
Backrooms     ← Core, Data, Activity, Inventory
Broadcast     ← Core, Data, Activity
UI            ← 위 전부
```

Backrooms와 Broadcast는 서로를 참조하지 않는다. asmdef로 강제한다.

#### 사운드

아트는 박스 수준이어도 되지만 사운드는 근사치 이상이어야 한다. 소리 없이 테스트하면 판정이 나오지 않는다.

```
■ 형광등 웅웅거림                    120Hz + 배음, 1초 무이음 반복
■ 발소리 (카펫, 타일, 콘크리트)       재질 3종 × 변형 4개, 걸은 거리로 걸음 판정
■ 공간 잔향 동적 변화                 좁은 복도 0.7초 ↔ 넓은 홀 2.6초
■ 미세 환경음 (환풍기, 물방울, 먼 소리) 9~26초 간격, 5~18m 떨어진 곳에서 3D 재생
■ 정적 구간 설계 (소리를 빼는 것도 설계) 22% 확률로 12~30초 무음 구간
```

전부 코드로 합성한 **임시 소리**다. 진짜 음원이 준비되면 SWAudioLibrary에 키로 넣고
SWAudioManager로 갈아 끼운다. 재생 지점은 두 곳뿐이다. (진행기록 8.4절)

#### 테스트

**어두운 구역 주의**: 라이트맵은 프리팹 단위로 구워져 있어 같은 프리팹을 쓰는 칸은 전부 같은 밝기다.

#### Behaviour Tree 사용 규칙

SWUtils에 Behaviour Tree(`SW.BehaviourTree`)가 이미 구현되어 있으므로 이를 사용한다. 그래프 편집 창, 자동 배치, 그래프 검증, 실행 중 노드 상태와 Blackboard 값을 보여주는 Runtime Debug 탭까지 갖춰져 있다.

```
BT를 쓰는 이유
□ 도입 비용이 없다 (라이브러리와 에디터가 이미 있다)
□ Blackboard Override로 트리 하나를 여러 몬스터에 재사용할 수 있다
□ 행동이 에셋이 되어 층 정의, 몬스터 정의와 같은 데이터 중심 구조에 맞는다
□ Runtime Debug 탭으로 실행 중 어느 노드가 도는지 직접 확인할 수 있다
□ 수색, 매복 같은 하위 행동을 몬스터 사이에 공유할 수 있다

지켜야 할 규칙
■ 행동 모드가 바뀌는 액션 노드는 진입 시 반드시 소리 이벤트를 발행한다
                                     행동마다 넣지 않고 Decorator를 반드시 거치게 해서 빠뜨릴 수 없게 했다
■ 소리 재생을 Decorator 노드로 분리해 재사용 가능하게 만든다
■ Blackboard 키 이름을 상수로 관리한다 (문자열 직접 입력 금지)
■ 몬스터 유형별 차이는 트리 복제가 아니라 Blackboard Override로 처리한다
                                     감지 거리·시야각·속도·수색 시간·매복 확률·조우 거리 전부 Key로 뺐다
✕ 트리가 지나치게 깊어지면 서브트리로 분리한다   깊이 4단이라 아직 나눌 것이 없다. 2종째에서 다시 본다

FSM을 쓰는 경우
□ 행동이 아니라 단순 상태 전이인 경우 (UI 화면, 방송 진행 단계 등)
□ 이때는 SWMonoStateMachine 또는 SWMonoStackStateMachine을 쓴다
```

몬스터 유형이 늘어나도 트리를 복제하지 않는다. 감지 범위, 이동 속도, 수색 지속 시간, 매복 확률 같은 수치는 Blackboard Override로 빼고, 감지 방식 자체가 다른 경우(소리 추적, 시각 추적)만 서브트리를 갈아 끼운다.

#### 판정

```
■  도망쳐 살아남았을 때 내가 잘했다고 느끼는가       ← 미판정. 구현은 끝났고 사람이 해 봐야 답이 나온다
   → 통과: Phase 4 진행
   → 경계: 소리로 정보를 더 노출
   → 실패: 막다른 길에서 죽으면 순환로 보정 강화
           무슨 일인지 모르겠으면 소리 설계 재작업
```

**완료 기준**: 실패했을 때 운이 나빴다가 아니라 내가 실수했다고 느낀다.

□ 저장과 불러오기
```

**완료 기준**: 아침에 일어나 방송하고 백룸에 들어가고 정산받고 업그레이드하고 잠드는 하루가 온전히 돌아간다.

### 6.2 데이터 에셋화

콘텐츠 확장 속도가 여기서 갈린다. 프로그래머 없이 층을 추가할 수 있어야 한다.

```
□ 스트리머 정의 (초기 스탯, 성장 계수, 상한, 고유 특성, 아바타, 컨셉 유형)
□ 층 정의 (생성 설정, 적용 규칙, 몬스터 구성, 아이템표)
□ 몬스터 정의 (감지 방식, 속도, 수색 시간, 매복 확률, 사운드)
□ 몬스터 Behaviour Tree 에셋 (유형별 서브트리, 공통 수색·매복 트리)
□ 아이템 정의 (격자 크기, 등급, 판매가, 공개 효과, 제작 용도)
□ 미션 정의 (발생 조건, 목표, 제한 시간, 보상, 위험도)
□ 업그레이드 정의 (대상, 비용, 효과, 선행 조건)
□ 시그널 등급 정의 (명칭, 조건, 트로피, 해금)
□ 채팅 템플릿 세트 (상황 태그별)
□ 층 규칙을 조합 가능한 형태로 분리 (어둠, 배터리, 구조 변경, 신호 불안정)
```

### 6.3 확장성 확인

DLC 스트리머 추가를 막지 않기 위한 항목이다. 하나라도 어기면 이후 추가가 불가능해진다.

```
□ 스트리머 정의가 전부 ScriptableObject로 외부화되었는가
□ 저장 데이터가 채널 진행도와 스트리머별 진행도로 분리되었는가
□ 출시 스트리머 1명도 여러 명 중 하나인 것처럼 짜였는가
□ 스트리머 관련 하드코딩이 하나도 없는가
□ 저장 데이터에 버전 필드가 있는가
```

마지막 항목을 빠뜨리고 배포하면 구조 변경 시 기존 세이브를 살릴 방법이 없다.

## 7. 성능 점검

측정 없이 최적화하지 않는다. 프로파일러로 확인한 뒤 손댄다.

```
□ 실행 중 실시간 라이트를 추가하지 않았는가       손전등 1개만 예외 (진행기록 8.2절)
□ 맵 조립을 프레임 분할로 처리했는가
□ 반복 생성 오브젝트를 전부 풀로 처리했는가
□ 채팅 항목을 풀로 처리했는가
□ Update에서 GetComponent를 호출하지 않는가
□ 매 프레임 문자열을 조합하지 않는가
□ UI 수치를 변경 시에만 갱신하는가
□ 매 프레임 갱신이 불필요한 로직을 주기 갱신으로 돌렸는가
■ NavMesh 굽기가 생성 후 1회만 실행되는가          맵 조립 완료 알림에서 1회. 몬스터는 굽기 완료를 따로 기다린다
□ 장시간 플레이 시 메모리 누수가 없는가          맵 재생성은 확인 완료 (500회 +3.6MB)
                                                이동·오디오는 빌드 시점에 다시 확인
                                                몬스터는 재생성 5회에서 NavMeshData 1개 유지 확인
□ 실행 중에 만든 메시와 텍스처를 직접 지웠는가    정적 배칭 메시가 재생성마다 쌓였다 (진행기록 5.8절)
```

## 8. 테스트

### 8.1 단위 테스트

Unity에 의존하지 않게 설계한 부분만 대상으로 한다.

```
■ 맵 생성: 순환로 최소 개수
■ 맵 생성: 막다른 길 비율 상한
■ 맵 생성: 탈출 경로 존재
■ 맵 생성: 시드 고정 시 동일 결과
■ 맵 생성: [추가] 고립된 구역 없음
■ 맵 생성: [추가] 넓은 홀 존재
■ 맵 생성: [추가] 만족 불가 설정에서 재시도 상한 후 실패 처리
■ 맵 생성: [추가] 어두운 칸 비율 상한
■ 맵 생성: [추가] 시작 칸과 탈출 칸은 어두워지지 않음
■ 맵 생성: [추가] 시드 고정 시 같은 어두운 칸
□ 인벤토리: 배치 가능 판정
□ 인벤토리: 경계 조건
□ 인벤토리: 형태별 회전
□ 컨디션: 피로도가 상한을 누르는 계산
□ 활동 결과 반영: 상태 변동 정확성
□ 손실 정책: 정책별 손실 목록
```

맵 생성 테스트는 시드를 여러 개 돌려 통계로 확인한다. 한 번 통과했다고 안심할 수 없는 영역이다.

### 8.2 인게임 디버그 명령

`SWDebugConsole`에 등록한다.

```
■ 지정 시드로 맵 재생성                map.regenerate
■ 현재 시드 출력                      map.seed
■ 좌표 이동                          player.teleport
■ 몬스터 소환                        monster.spawn <거리>
■ 몬스터 정지                        monster.freeze <0|1>
□ 아이템 지급                        Phase 4
■ 남은 시간대 설정                    state.slots
□ 컨디션 수치 설정                    1일 시연판
□ 후원금 지급                        1일 시연판
■ [추가] 게임 상태 출력                state.print
■ [추가] 다음 날로                    state.nextday
■ [추가] 백룸 진입 / 종료             backrooms.enter, backrooms.exit
■ [추가] 라이트맵 상태 출력            map.lightmaps
■ [추가] 재생성 메모리 측정            map.soak <횟수>
■ [추가] 손전등 켜고 끄기              player.flashlight
■ [추가] 손전등 배터리 충전            player.battery
```

빌드한 실행 파일은 명령줄 인자로도 확인할 수 있다. `-projectr-verify`(라이트맵 확인 후 종료 코드 반환),
`-projectr-screenshot <경로>`, `-projectr-soak <횟수>`. 사람이 화면을 보고 판단하지 않아도 된다.

상태 감시 항목:

```
■ 현재 시드
■ [추가] 플레이어 속력 / 자세
■ [추가] 손전등 배터리
□ 층 번호                            층 개념 도입 시
□ 시청자 수                          1일 시연판
□ 컨디션 4수치                        1일 시연판
■ 몬스터 현재 실행 노드                실행 중인 Action 노드의 한국어 이름
■ 몬스터 Blackboard 값                모드 / 시야 / 목격 / 소리
■ [추가] 플레이어 소음 반경             자세에 따라 12 / 22 / 0m
□ 이벤트 버스 리스너 수 (누수 확인)     상시 감시 항목 미등록 (Phase 0에서 1회 수동 확인)
```

### 8.3 회귀 확인

```
■ 씬을 여러 번 오갔을 때 이벤트 리스너가 누적되지 않는가   Phase 0에서 확인 (리스너 0)
□ 활동 도중 강제 종료 후 정상 복구되는가                  Phase 4

■ [추가] 맵을 여러 번 다시 만들어도 메모리가 쌓이지 않는가   map.soak 500회로 확인
■ [추가] 빌드에서 프리팹 라이트맵이 살아남는가              -projectr-verify 종료 코드 0
