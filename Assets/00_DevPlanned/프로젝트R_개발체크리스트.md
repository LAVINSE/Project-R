# 프로젝트 R — 개발 체크리스트

기획서 v0.3 기준 · **본개발**
Version 1.2 · 2026.08.29

프로토타입 체크리스트 v0.1을 대체한다. v0.1은 "이 게임을 만들어도 되는가"를 묻는 문서였고,
이 문서는 "이 게임을 어디까지 만들었는가"를 묻는 문서다.

---

## 이 문서 사용법

작업할 때 옆에 띄워두고 항목을 지워나가는 용도다.
무엇을 만드는지는 기획서, 무엇을 했는지는 `프로젝트R_개발진행기록.md`를 본다.

1장은 작업 내내 반복해서 확인하는 상시 항목이다.
2장은 무엇을 어디에 놓을지를 적어 둔 참조용 장이라 순서 없이 필요할 때 본다.
3장부터 9장까지는 순서대로 진행하는 마일스톤이다.
10장 이후는 해당 시점에만 확인한다.

### 표기

```
□   아직 하지 않음
◐   하는 중 — 무엇이 남았는지 옆에 적는다
■   끝남 — 무엇으로 끝났는지 옆에 적는다
◈   구현은 끝났고 판정 대기 — 사람이 해 봐야 답이 나온다
✕   하지 않기로 결정 — 사유는 진행기록에
```

### 완료로 치는 기준

항목을 지우는 규칙은 셋뿐이다.

1. **■ 옆에는 증거가 있어야 한다.** 클래스명, 에셋 경로, 측정값 셋 중 하나다.
   증거 없는 ■는 ■가 아니라 ◐다.
2. **◈는 ■가 아니다.** 관문을 셀 때 ◈는 통과로 세지 않는다.
   v0.1은 미판정 셋을 문서 앞머리의 주석으로 알렸다. 표기로 갈라 두면 항목마다 드러나므로 주석이 필요 없다.
3. **✕에는 사유가 붙어야 한다.** 사유가 없으면 다음 사람이 그것을 다시 만든다.
   진행기록 10.9절의 없어진 타이머가 그 예다.

### 관문

각 마일스톤 끝에는 관문이 하나씩 있다. 관문에는 통과 조건, 판정하는 사람, 미달 시 조치가 적혀 있다.
**관문을 통과하지 않은 채 다음 마일스톤의 구현을 시작하지 않는다.**

예외를 두려면 두 가지를 함께 한다. 기준을 낮추지 말고 시점만 옮길 것,
그리고 감수한 위험을 진행기록에 적을 것. v0.1에서 실제로 그렇게 했고(진행기록 8.10절),
그 대가로 미판정이 셋 쌓였다.

## 1. 상시 확인

새 클래스나 파일을 만들 때마다 본다.

### 1.1 SOLID

원칙 이름만 외우는 것은 소용이 없으므로 이 프로젝트에서 그것이 무엇인지 적어 둔다.

| 원칙 | 이 프로젝트에서 | 어겼을 때 나타나는 모습 |
|---|---|---|
| 단일 책임 | 한 클래스 500줄, 한 오브젝트 컴포넌트 다섯 개가 상한 | `MapBuilder`에 아홉 개가 붙어 있던 상태 (진행기록 11.3절) |
| 개방-폐쇄 | 완화·변주는 구현체 교체로 끝나야 한다 | 손실 완화 4단계마다 `BackroomsActivity`를 고치게 됨 |
| 리스코프 치환 | 백룸도 미니게임도 알바도 같은 `IActivity` 자리에 꽂힌다 | 활동 종류를 보고 분기하는 `if`가 생김 |
| 인터페이스 분리 | `IActivity`가 커지면 활동마다 빈 구현이 생긴다 | 알바가 쓰지 않는 멤버를 억지로 채움 |
| 의존 역전 | 시스템끼리 `SWEventBus`로만 말한다 | 백룸이 방송을 직접 부름 |

```
□ 이 클래스가 바뀌는 이유가 하나뿐인가
□ 규칙이 바뀔 자리를 인터페이스로 빼 두었는가 (ILossPolicy가 기준선이다)
□ 새 활동을 하나 더 넣어도 기존 코드를 고치지 않아도 되는가
□ 구현하면서 빈 채로 남긴 멤버가 없는가
□ 구체 클래스가 아니라 인터페이스나 이벤트에 기대고 있는가
```

가장 잘 지켜진 예가 `ILossPolicy`다. `BackroomsActivity.Settle()`이 성공했을 때의 결과를 다 만든 뒤
규칙에 통째로 넘기므로, 기획서 7.7절의 완화 4단계가 전부 구현체 교체로 끝난다.
새로 만드는 것도 이 모양을 따른다.

| 팝업 | `SWPopupBase`, `SWPopupCatalog` | ■ 프리팹이 아니라 키로 부른다 (11.1절) |
| 모듈 간 통신 | `SWEventBus` | ■ |

풀링은 채팅 항목이 들어오는 M1에서 다시 판단한다. 채팅은 초당 여러 개가 생기고 사라지므로
지금까지의 근거(타일·이상물체·인벤토리는 개수가 적고 드물게 생긴다)가 그대로 적용되지 않는다.

```
□ SWUtils에 같은 기능이 이미 있는지 먼저 확인했는가
□ SWUtils 원본을 수정하지 않았는가 (상속하거나 감싸서 쓴다)
□ 원본을 고쳐야 한다면 SWUtils 쪽에 고치고 태그를 올렸는가 (v1.1.1이 그 예다 · 5.7절)
```

### 1.3 주석

```
□ 모든 public 타입에 <summary>를 달았는가
□ 모든 public 필드·프로퍼티·메서드에 <summary>를 달았는가
□ 매개변수에 <param>, 반환값에 <returns>를 달았는가
□ 문장을 한국어 높임말로 끝맺었는가 ("~합니다", "~입니다")
□ 왜 그렇게 짰는지를 <remarks>에 적었는가
□ #region 이름을 한국어로 썼는가
□ #endregion에 이름 주석을 붙였는가 (#endregion // 필드)
□ [SerializeField]에 [Tooltip]을 달았는가
```

`<remarks>`가 이 규약의 핵심이다. `<summary>`는 무엇인지를 적고, `<remarks>`는 왜인지를 적는다.
`GameSave`와 `ILossPolicy`가 기준선이다. 둘 다 기획서 몇 절의 어떤 요구 때문에 그 모양인지가 적혀 있어서,
읽는 사람이 기획서를 다시 뒤지지 않아도 된다.

### 1.4 명명

```
□ 클래스·인터페이스·public 멤버가 PascalCase인가
□ private 필드가 camelCase이고 접두사가 없는가
□ 직렬화 필드에 [SerializeField]를 붙였는가
□ 이벤트 데이터 이름이 "동작 + Event" 형태인가
□ 문자열 키를 상수로 모았는가 (PopupKeys, MonsterBlackboardKeys가 그 예다)
```

문자열 키는 오타가 실행할 때까지 드러나지 않는다. 상수로 모으는 것이 유일한 방어다.

### 1.5 코드 습관

```
□ Debug.Log 대신 SWLog를 썼는가
□ 로그 메시지에 [클래스명] 접두사를 붙였는가
□ 이벤트 구독을 OnEnable에서 하고 OnDisable에서 해제했는가
□ GetComponent를 Awake에서 캐싱했는가
□ 목록 반환 시 null 대신 빈 목록을 반환하는가
□ using 정렬이 System → Unity → SW.* → ProjectR 순인가
□ 전역 객체를 Resources로 불러오고 있지 않은가 (씬에 두고 SWSingleton이 정리한다 · 11.2절)
□ 팝업을 프리팹이 아니라 카탈로그 키로 부르고 있는가 (11.1절)
□ 프리팹을 코드로 고칠 때 PrefabUtility.LoadPrefabContents를 썼는가 (11.4절)
□ 에디터 도구를 SWTools가 아니라 Project R 메뉴 아래에 두었는가
```

### 1.6 모듈 분리

```
□ 시스템끼리 직접 참조하지 않고 SWEventBus로 통신하는가
□ UI가 게임 로직을 갖고 있지 않은가
□ 데이터 계층이 시스템을 참조하지 않는가
□ 한 클래스가 500줄을 넘지 않았는가
□ 한 오브젝트에 컴포넌트가 다섯 개를 넘지 않았는가 (기능상 필요하면 사유를 적는다 · 11.3절)
□ 전역 싱글톤이 계획한 개수를 넘지 않았는가 (지금 넷: GameManager · SWPopupManager · PopupHotkeyController · EventSystem)
```

### 1.7 의존 방향

asmdef로 강제한다. 규칙으로만 두면 지켜지지 않는다.

```
Inventory   ← 없음                                    ■ noEngineReferences: true
Core        ← SWUtils.Runtime                         ■
Data        ← Core, Inventory                         ■
Activity    ← Core, Data                              ■
Backrooms   ← Core, Data, Inventory, Activity         ■ + InputSystem, AI.Navigation, URP
UI          ← 위 전부                                  ■ + InputSystem, UnityEngine.UI
Broadcast   ← Core, Data, Activity                    ■ Backrooms를 참조하지 않는다
Editor      ← 전부 + SWUtils.Editor                    ■ Editor 전용
Tests.EditMode ← 전부                                  ■ Editor 전용
```

**어셈블리를 새로 만드는 기준은 하나다. 어기면 안 되는 참조 방향이 문서에 적혀 있는가.**
적혀 있으면 asmdef로 막고, 없으면 폴더로 나눈다. 코드가 없는 asmdef는 빈 어셈블리만 늘린다.

그래서 이렇게 갈랐다.

```
Broadcast   □ 만든다.  Backrooms와 서로 참조 금지가 기획서에 적힌 유일한 상호 금지 규칙이다
                      백룸 안에서 시청자 수를 알고 싶어지는 순간이 반드시 오고,
                      그때 using 한 줄이면 조용히 넘어간다. 컴파일러가 막아야 한다
Streamer    ✕ 안 만든다. Data 안 폴더로 둔다. 스탯·컨디션·스트리머 정의는 전부 데이터이고
                      참조하면 안 되는 대상이 없다
Minigame    ✕ 안 만든다. Activity 안 폴더로 둔다. 백룸과 섞일 위험은 씬이 달라 애초에 없다
                      커져서 나눌 이유가 생기면 그때 뗀다
```

지켜야 할 세 가지:

- **Backrooms와 Broadcast는 서로를 참조하지 않는다.** Broadcast를 만드는 시점에 asmdef로 막는다.
  백룸에서 벌어진 일이 시청자와 후원에 닿는 경로는 `SWEventBus` 한 방향뿐이다.
  백룸이 이벤트를 발행하고 방송이 듣는다. 백룸은 시청자 수를 모른다.
- **아무도 UI를 참조하지 않는다.** 백룸이 옵션 값을 알아야 하면 `Core`의 `GameSettings`와 이벤트 버스를 거친다.
- **Inventory는 아무것도 참조하지 않는다.** 계산부와 유니티의 분리가 규칙이 아니라 컴파일 오류로 지켜진다.
  같은 방식이 필요한 계산부가 또 생기면 이 어셈블리에 넣는다.

## 2. 화면 구조

씬과 화면 배치를 여기에 모아 둔다. 무엇을 만들지 정하기 전에 어디에 놓일지를 먼저 본다.

### 2.1 씬은 셋뿐이다

```
HomeScene ──── 활동 선택 ────▶ LoadingScene ────▶ BackroomsScene
    ▲                          방송 시작 연출          3D 1인칭
    │                                                     │
    └──────────────── 정산 결과를 들고 복귀 ────────────────┘

전역 (씬 셋에 똑같이 놓임 · SWSingleton이 정리)
  GameManager · SWPopupManager · PopupHotkeyController · EventSystem
```

**씬을 더 늘리지 않는다.** 늘리면 전역 객체 네 벌과 로딩 구간이 따라붙는다.
관리 화면 안의 화면 전환(마을 ↔ 방)은 씬이 아니라 카메라와 루트 오브젝트 전환으로 처리한다.

미니게임과 알바는 2D이고 백룸만큼 무겁지 않으므로 `HomeScene` 안에서 처리할지
씬을 하나 더 둘지는 M3에서 판단한다. 지금 정하면 근거 없이 굳힌다.

### 2.2 HomeScene — 마을 화면

활동 선택을 목록 버튼이 아니라 **마을에 선 건물을 눌러 들어가는 방식**으로 만든다.
플레이어가 목록에서 항목을 고르는 것이 아니라 어딘가로 걸어 들어가는 감각이 되고,
기획서 설계 원칙 5번("성장은 눈에 보여야 한다")을 수치가 아닌 그림으로 처리할 수 있다.

### 2.3 마을은 SpriteRenderer, 겹치는 것은 Canvas

```
Canvas (ScreenSpaceOverlay)   상단 상태 표시 · 하단 버튼 · 팝업 전부

### 2.4 집 안 — 성장이 쌓이는 화면

기획서 9.3절과 13.1절이 요구하는 것은 **성장이 공간으로 보이는 것**이다.
마을이 그 자리를 통째로 가져가면 그 장치가 사라지므로 두 층으로 둔다.

```
마을 화면 ──[ 집 클릭 ]──▶ 방 화면 ──[ 나가기 ]──▶ 마을 화면
                            시그널 트로피가 놓임
                            물건이 늘수록 방이 미묘하게 이상해진다
                            조명 색 · 벽 얼룩 · 창밖 풍경
```

두 층으로 두면 얻는 것이 하나 있다. **소포가 집 앞에 도착한다는 설정이 실제로 보인다.**
마을 화면의 집 앞에 상자 하나가 놓이고, 눌러 들여놓으면 방에 트로피가 하나 는다.
방만 있으면 트로피가 그냥 나타날 뿐이다.

```
■ 방 화면을 씬이 아니라 루트 오브젝트 전환으로 만들었는가   Village / Room 루트를 껐다 켠다
                                                     그 층에서만 쓰는 버튼도 함께 켜고 끈다
□ 트로피 배치가 하드코딩이 아니라 시그널 등급 정의에서 오는가   시그널 등급 정의가 M2다. 방은 지금 비어 있다
□ 방의 변화(조명 색 · 얼룩 · 창밖)가 물건 수에 따라 단계로 정의되어 있는가
□ 소포가 마을 화면에 놓이고 눌러서 들여놓을 수 있는가
```

### 2.6 건물 정의

건물을 늘리는 것이 활동을 늘리는 것과 같은 일이 되게 한다.

└─ 시간대별 겉모습                  낮 · 밤 (선택)

```

**좌표를 정의에 둘지 씬에 둘지는 M1에서 실제로 배치해 보고 정한다.** 정의에 두면 도구로 관리되고,

해금으로 늘어나 열 개를 넘으면 정의 쪽이 낫다. 지금은 몇 개가 될지 모른다.

그래서 테스트 순서도 Q2를 먼저 본다. 몬스터 없는 빌드를 따로 만들 필요는 없고,
같은 빌드에서 `monster.freeze 1`로 멈춰 두고 앞부분을 관찰한다.

프로토타입 문서(`프로젝트R_프로토타입_문서.md`)의 역할은 이 관문에서 끝난다.
그 뒤로는 기획서와 이 문서만 본다.

## 5. M2 — 데이터 에셋화와 확장성 잠금

콘텐츠 확장 속도가 여기서 갈린다. **프로그래머 없이 층을 추가할 수 있어야 한다.**
그리고 이 마일스톤을 넘기고 나면 되돌리는 비용이 급격히 커진다.

### 5.1 정의 에셋

`SWIdentifiedObject` + `SWIODatabase`를 그대로 쓴다. 이상물체가 이미 그 방식이다(10.3절).

```
■ 아이템 정의                           AnomalyDefinition — 형태 · 등급 · 색 · 아이콘 · 모델 · 정산 수치

□ 층 정의                               생성 설정 · 적용 규칙 · 몬스터 구성 · 아이템표
□ 몬스터 정의                           감지 방식 · 속도 · 수색 시간 · 매복 확률 · 사운드

```

### 5.2 편집 도구

정의를 하나 만들 때 손댈 곳이 여러 군데면 반드시 하나를 빠뜨린다.
`Project R > 데이터 > 이상물체` 창이 그 문제를 푼 방식이다(11.6절). 새 정의도 같은 모양으로 만든다.

```
■ 이상물체 창                           왼쪽 목록 + 오른쪽 인스펙터. 정의에 필드를 더해도 창은 안 고친다
□ 층 창
□ 몬스터 창
□ 업그레이드 창
□ 공통 알림                             코드명 중복 · 데이터베이스 미등록 · 아트 없음
```

**인스펙터를 그대로 띄우는 방식이어야 한다.** 입력란을 늘어놓으면 정의에 필드를 더할 때마다 창도 고쳐야 한다.

### 5.3 확장성 잠금

DLC 스트리머 추가를 막지 않기 위한 항목이다. **하나라도 어기면 이후 추가가 불가능해진다.**

```
□ 스트리머 정의가 전부 ScriptableObject로 외부화되었는가
□ 저장 데이터가 채널 진행도와 스트리머별 진행도로 분리되었는가
□ 출시 스트리머 1명도 여러 명 중 하나인 것처럼 짜였는가
□ 스트리머 관련 하드코딩이 하나도 없는가
□ 저장 데이터에 버전 필드가 있는가
□ 저장 데이터 마이그레이션 경로를 실제로 한 번 돌려 봤는가
```

마지막 항목은 v0.1에 없었다. 필드만 있고 마이그레이션을 한 번도 돌려 보지 않으면
필드가 있는 것과 없는 것이 같다.

### 11.2 디버그 명령

`SWDebugConsole`에 등록한다. 인스턴스 메서드는 `RegisterInstance(this)`를 Awake에서 불러야 한다.

```
■ state.print · state.time · state.nextday · state.reset
■ backrooms.enter · backrooms.exit
■ map.regenerate · map.seed · map.lightmaps · map.soak <횟수>
■ player.teleport · player.flashlight · player.battery
■ monster.spawn <거리> · monster.freeze <0|1>
■ backpack.print · pickup.take
■ view.ceiling · view.bright · view.maze
■ condition.set <수치> <값>              sleep / hunger / mood / fatigue
                                        직접 넣지 않고 차이를 적용한다. 그래야 피로도 상한이 걸린다
■ donation.add <금액>                    음수면 차감
■ viewer.set <수>                        유지비와 이탈이 규모에 비례하는지 보려면 큰 수를 넣어야 한다

```

빌드 실행 파일의 명령줄 인자: `-projectr-verify`(라이트맵 확인 후 종료 코드),
`-projectr-screenshot <경로>`, `-projectr-soak <횟수>`. 사람이 화면을 보고 판단하지 않아도 된다.

상태 감시 항목:

```
■ 백룸 시드 · 타일 수
■ 플레이어 속력 · 자세 · 손전등 배터리 · 소음 반경
■ 몬스터 실행 노드 · Blackboard 값
□ 층 번호                               M3
□ 시청자 수 · 컨디션 4수치                M1
□ 이벤트 버스 리스너 수                   상시 감시에 등록한다. 지금은 Phase 0에서 1회 수동 확인뿐이다
```

리스너 수는 상시 감시에 올려 둔다. 시스템이 늘어날수록 누수가 조용히 생기고,
1회 확인으로는 그때 그 씬 조합만 본 것이다.
